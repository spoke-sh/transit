# M2 — Board: system inspection for operators and agents

[Roadmap](README.md)

Status: bounded inspection profile implemented and verified on Linux x86_64. Inspection only; operational controls come later.

Scope: make the running kernel comprehensible through a logistics-inspired UI
and a reusable OpenAPI surface. Ship a Zig `transit-board` executable containing a static
TypeScript/TanStack Router app built with Vite+, plus the API that serves it.
The browser is the first Board API client; agents and later clients get the same
structured evidence. [BOARD.md](../BOARD.md) owns the design and proposed boundaries.

## Design gates

| Gate | Decision and evidence required |
| --- | --- |
| Public reads | Define scoped discovery, mailbox/outbox/effect inspection, and retained history through `transit-protocol`/`transit-client`; prove current read authorization and bounded scans without exposing raw storage |
| Observation truth | Define read cuts, continuation expiry, retained gaps, causal links, and freshness; prove a partial/stale view cannot appear complete or live |
| Access profile | Qualify the proposed single-realm, shared inspection-principal profile, private viewer admission, signed upstream reads, and private/TLS deployment boundary; no runtime mutation grants |
| Contract ownership | Reuse public Transit types in a generated OpenAPI contract; validate schemas, generated client, runtime data validation, and API version compatibility |
| Embedded distribution | Prove TanStack Router/Vite+ compatibility with pinned tools and a standalone Zig binary serving nested routes, API, and every required static asset |
| Enrichment | Define versioned, provenance-bearing lenses that preserve kernel facts and permissions; prove known/unknown schema behavior without Station or executable plugins |

These gates extend M1's read surface; they do not weaken its authority, retention,
or isolation guarantees. The additive [inspection v1](../../contracts/INSPECTION_V1.md) surface preserves
existing service v2 command signatures.
Record failed proofs in the owning design before widening the implementation.

## Implementation sequence

1. **Inspection contract.** Define public read models, query limits, permissions,
   coverage and error semantics. Extend node/client and shared fixtures first.
   Existing counter and byte-log programs supply real activity and opaque state.
2. **Board API.** Introduce its typed contract and OpenAPI generation, bounded
   client calls, explicit capabilities, and private read-only hosting.
   Prove a non-browser client can discover and explain the same state as the UI.
3. **Embedded frontend.** Establish the Vite+/pnpm workspace, pin dependencies,
   generate the API client, and build/embed all assets. Add namespaced `just`
   tasks and owning READMEs with actual runnable workflows as code lands.
4. **Kernel views.** Implement the overview, arrivals/departures, process detail,
   and bounded journey. Include freshness, retained gaps, blocked work, effect
   uncertainty, and activation history before adding higher-level presentation.
5. **Lenses and qualification.** Demonstrate optional example enrichment and
   fallback; exercise worker/node/storage failure, revocation, trim, restart,
   slow readers, and deployment isolation against the real M1 reference.

## Exit criteria

- [x] Discover only authorized processes and inspect their lifecycle, ownership,
  state revision, mailbox progress, outboxes, effects, payload lifecycle metadata,
  and runtime bindings through public client operations.
- [x] Expose paginated, filtered retained history with bounded work, explicit
  current read authorization, continuation semantics, and evidence references.
  No raw storage or core-internal access from Board is needed.
- [x] Generate/serve a versioned OpenAPI schema and typed browser client from
  owned contracts. Detect drift, validate runtime responses, preserve identity
  and integer semantics, and demonstrate an independent scripted API consumer.
- [x] A clean build produces one `transit-board` binary serving API and static UI with
  no Node.js runtime, source checkout, external asset files, or runtime downloads.
  Deep links work; API errors and missing assets never become HTML successes.
- [x] Operators can explain a blocked input, distinguish admission from turn
  completion and effect settlement, and follow a committed output to its recorded
  delivery using the overview/detail/journey views and the same API evidence.
- [x] Worker replacement preserves displayed PID while updating activation and
  binding evidence. Disconnection/lag cannot appear as empty backlog or success;
  expiry remains distinct from physical cleanup, and closed-unknown from failure.
- [x] Race reads with revocation, policy changes, and trim; enforce current scope
  across lists, payload previews, relationships, counts, and cached results.
  Show checkpoint coverage and missing history without fabricating causal edges.
- [x] Admit viewers through the private deployment boundary, authenticate and
  authorize upstream reads, keep seeds out of assets/URLs/logs, reject unsafe
  host/origin/proxy use, and verify Board cannot submit mutations or reach raw
  storage/provider APIs. The [current access profile](../BOARD.md#access-and-trust)
  replaces the original experimental Board key/session layer.
- [x] Bound polling, concurrent reads, buffers, history scan work, and graph size;
  demonstrate slow readers and refresh load do not prevent M1 control progress
  within the declared reference profile. State measured limits.
- [x] Provide accessible table/detail navigation, textual statuses, reduced-motion
  behavior, and shareable URLs containing view identity/filters but no credentials
  or payload bodies. Polling does not disrupt keyboard focus or selection.
- [x] A versioned example lens enriches the API/UI with source-linked facts;
  unknown/malformed descriptors fall back safely to kernel inspection. No lens
  can grant privileges, override lifecycle, or invoke application handlers.
- [x] Preserve all applicable M1 proofs and document actual Board build, contract,
  frontend, API, and reference checks. Mark later Station/HTTP enrichment as
  unsupported until its corresponding milestone supplies working evidence.

## Recorded evidence

`just ci`, `just transit-board::browser`, `just doctor`, and the complete
`launchers::reference::infra-up` / `launchers::reference::images` / `launchers::reference::test` / `launchers::reference::infra-down`
workflow passed with the pinned toolchain. [The proof guide](../../tests/README.md#board-qualification)
owns measurements, failure findings and limits. The reference includes fresh
activation/binding observations, expiry and retained gaps after recovery, plus
Board-specific raw-storage/provider egress denial.

Board is usable through `just transit-board::install` then `just launchers::local::up`,
through the disposable `just transit-board::demo`, or with an
explicitly provisioned [installation config](../../apps/transit-board/README.md).
Operational controls, Station/HTTP interpretations and per-user identity mapping
remain outside this completed profile.

## Boundaries

M2 provides current and retained inspection, not a complete historical archive,
control console, scheduler, monitoring database, or general framework. It does
not implement GenServer or registry semantics early. Inspection gaps must be
visible. Later controls require separate scope and authorization design; planned
Station and HTTP lenses land with [M8](M8.md) and [M9](M9.md).

The development launchers and service instrumentation have their own scope and
evidence in [M3](M3.md) and [M4](M4.md). They build on this completed inspection
profile without expanding its original criteria.
