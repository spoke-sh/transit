# M14 — Bounded publication for larger Station records

[Roadmap](README.md)

Status: Complete within the qualified growing Zig profile; follows [public query access M13](M13.md), before
[HTTP/shared exchanges M15](M15.md).

## Review of M13 and the original Document plan

M13 qualified signed retry identity, retained source versions, bounded Arrow
delivery and current authorization. These are reusable foundations. Its storage
and query representations are narrower than the original Document plan needs:

- KV values are 256 bytes, with four mutations in one writable resource per
  turn. Even 1 KiB of content requires four values before any descriptor,
  causal metadata, materialized state or response correlation.
- Growing queries already stage chunks and publish a complete manifest, but
  their keys, progress, digests and lifecycle belong to query results. They are
  not a general atomic Document-change or checkpoint interface.
- Public plans have 207 encoded bytes inside the Station request. Fuze v1
  schemas have two scalar columns. Neither represents the proposed nested
  Document projection and its missing/null/conflict/error distinctions.

The original M14 explicitly required a prerequisite milestone if useful records
could not fit. This milestone supplies that prerequisite without increasing the
kernel limits. The Document/text/SDK obligations now belong to M17, with unified
queries and their SDK extensions in M18. HTTP and gRPC are M15/M16; Arrow
interoperability and clustering are M22/M23. M17 must qualify its CRDT layout
and M18 must version the wider query contract; opaque publication alone cannot
establish those semantics.

## Scope and sequence

Implement a Zig Station `Publication` interface over growing KV: immutable,
application-versioned records staged in bounded chunks, published by one final
turn, read incrementally from an exact source, and explicitly retired or
abandoned with resumable cleanup. Keep total retained record count independent
of worker memory. Record identities cannot be reused after cleanup.

1. Specify the versioned layout, digest, capacities, visibility, quotas and
   lifecycle; document the Document handoff before fixing a CRDT API.
2. Implement private-turn operations and source-bound readers with rollback,
   strict decoding, duplicate checks and bounded reclamation.
3. Qualify independent fixtures and real signed service calls against disk
   Ursula, with uncertainty, fencing, failures and current access checks.
4. Record measurements, recovery instructions and precise limits; preserve M13
   query compatibility and all existing default profiles.

## Exit criteria

- [x] Publish a versioned layout and neutral digest fixture; reject invalid,
  changed or oversized identities/content before publication.
- [x] Stage and publish records larger than both one KV value and one turn's
  mutation budget. The publication marker, application head, input progress
  and outputs share the final turn; staged bytes alone are not accepted content.
- [x] Enforce explicit durable staging byte/count quotas before beginning work;
  keep each operation's reads, writes and memory independent of retained count.
  Keep unlimited retention as the default; quota refusal cannot authorize expiry.
- [x] Stream verified bytes from an exact captured or retained source. Reject
  mixed revisions, missing/corrupt chunks, expired views and revoked reads;
  distinguish a provisional prefix from verified completion.
- [x] Preserve exact duplicate handling, permanent terminal identities and
  atomic rollback on errors. Recover after worker/node/store restart before
  and after publication, including lost acknowledgements and stale owners.
- [x] Explicitly abandon unpublished work or retire published content; resume
  bounded cleanup after failure while retaining identity rejection evidence.
  Do not reclaim bytes still visible through protected historical sources.
- [x] Exercise useful record sizes and more records than the legacy 32-key
  limit with a one-page authority cache on recovery. Report logical storage
  overhead and operation/memory bounds separately from measured timings.
- [x] Ship runnable focused tasks, integrate the proof into applicable CI,
  update component recovery documentation, and pass `just check` and the
  relevant growing service proofs.

## Boundaries

This is an explicit growing Zig framework primitive. It does not add a kernel
blob type, a new database, an automatic job scheduler, a Document implementation,
an SDK ABI, a remote upload service or an Arrow type. It does not widen M13's
plan/request limits. Applications still own authenticated ingress, continuation
scheduling, publication references and dependency/lifetime policy. M15/M16
qualify connector capture; M17/M18 qualify Document and query
compositions across the public SDKs.

## Qualification

`just check`, independent Station package tests, `just test::publication` and
`just test::growing-query` passed on Linux x86_64. The
[test guide](../../tests/README.md#m14-immutable-publication) and
[retained measurement](../../tests/verification/results/m14-publication-2026-09-26.json)
record the 64 KiB/42-publication workload, four worker SIGKILLs, node/store
restarts, exact retries, source protection and 170.979s total phase time.
One-page recovery and ordinary 64-page operation are measured separately.
Physical erasure, host power loss, larger configured records, production capacity
and the expanded hosted CI budget remain unqualified.
