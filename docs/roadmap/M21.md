# M21 — Reactive interfaces over reactive APIs

[Roadmap](README.md)

Status: Planned; follows [M20 reactive APIs](M20.md). The selected scope remains
**live views with resumable change notifications and snapshot refresh**, shared
by Board and an application interface. The server protocol is now an explicit
prerequisite rather than part of this frontend milestone.

Scope: consume M20's qualified APIs to build view lifecycles, bounded refresh
scheduling and presentation. [Reactive interfaces](../REACTIVE.md) owns these
rules and the relationship to D4. Finite snapshots retain M13/M18 query identity,
source evidence, admission and retention. [Flight interoperability M22](M22.md)
follows; none of these milestones supplies incremental continuous-query semantics.

## M18 findings applied to refresh

The [shared workspace](../../packages/zig/transit-query/docs/unified-client.md)
already compiles SQL without admitting work or retaining a source cut. Capture
chooses the committed basis when the source admits the call. A displayed atlas
revision or a compilation response therefore cannot promise the refresh's source
position. Preserve the submitted declaration/plan and use the actual manifest
basis with M20's coverage relation; do not infer an executable `AS OF` operation.

Use two different identities: a new namespace/correlation for a deliberately
admitted refresh, and unchanged frozen bytes for retry of that refresh. The
M18 browser proof found that failed atlas refresh could remount the query view
and lose uncertain work. Keep operation recovery outside disposable atlas/render
state. Draft edits, reconnects and failed metadata reads must not submit a
replacement query or replace a newer displayed generation.

The first Table view keeps the existing one-active-query-per-requester constraint. A
browser-local queue is insufficient when tabs share Board's query principal:
use the admission/coordination owner qualified in M19/M20. One pending dirty
position is scheduling state, not another durable busy query. M20's adapter must
exclude query bookkeeping from data invalidation or prove equivalent convergence;
otherwise each refresh can trigger its own successor under a quiescent source.

M18 verifies complete coverage incrementally while retaining one bounded page.
Preserve that property when switching snapshots: use a bounded verification pass
and then read the visible page from the same immutable result under current
authority, or qualify another bounded strategy explicitly. Do not collect every
page just to swap a UI atomically. Account for verification and reread costs;
visible prefixes and manifest existence alone are not verified complete coverage.
The [proof ledger](../../tests/README.md#m18-qualification) records finite recovery
durations, not refresh latency or sustainable query rates.

## Entry gates

| Gate | Required decision / evidence |
| --- | --- |
| Reactive API | M20's executed SSE/WebSocket, typed client, current-authority, snapshot/watch, resume/reset, lifecycle and deployment proofs; no UI-owned substitute protocol |
| Initial view matrix | Select a Board inspection projection, a declared Table query view and the application example; qualify any added public source adapter under M20's contract |
| Refresh contract | Fixed query/source/schema generation, actual captured result basis related to M20 coverage, one newest dirty position and new finite query identities; uncertainty recovers the original submission |
| Lifecycle and cost | Share M20 leases/close semantics and per-principal quotas; define fair visible-view scheduling and retained-query accounting across tabs/viewers |
| UX | Distinguish displayed snapshot, pending refresh, disconnected/gap, paused and denied states; Follow changes is not D4's continuous Stream mode |

## Implementation sequence

1. Bind the selected views to M20's generated/runtime-validated client and
   capability matrix. Use the shared snapshot/watch and reset operations without
   copying SSE/WebSocket framing or cursor semantics into a UI package.
2. Add the application live view and Board inspection refresh, including basis,
   loading, gap, denied and reconnection states. Preserve Board's private access
   and metadata-only inspection boundary.
3. Add refresh of an eligible already-submitted Table query with one active
   evaluation and a newest pending invalidation, complete-result verification,
   generation fencing and explicit Pause/Follow changes controls. Preserve pending
   mutation recovery across component remount and metadata failure; bound result
   verification, visible-page ownership and shared-principal scheduling separately.
4. Qualify race, revocation, multi-viewer, overload and browser/server recovery
   schedules against real M20 APIs. Add each further source only with its own
   decoder/schema/lifetime and view evidence.
5. Publish measured freshness/cost and browser/deployment limits for local,
   Compose and reference placements; keep server API qualification attributable
   to M20 and end-to-end presentation evidence here.

## Exit criteria

- [ ] Board inspection, a declared Table query view and an application view use
  M20's shared API/client contract. Each presents its actual snapshot/source basis;
  independent panels do not imply one globally consistent cut.
- [ ] The interface consumes the qualified snapshot/watch handshake, duplicate
  positions and explicit reset outcomes. A reset performs a visible authorized
  resnapshot; the browser never invents a latest cursor or complete change history.
- [ ] Refreshes preserve the submitted query/source/schema identity while acquiring
  new finite query/result IDs. Uncertain submission or cancellation recovers its
  exact frozen operation rather than automatically creating another query.
- [ ] A commit during refresh remains dirty until a qualified snapshot covers it.
  Coalescing keeps one newest unsubmitted invalidation. Under quiescence and
  available capacity, the view converges without promising every intermediate state.
  Prove both sides: a relevant write during capture causes the next refresh,
  while the refresh's own request/capture/cleanup commits do not perpetuate work.
- [ ] Rows and profiles switch together only to a complete verified result with
  one source basis. Late replies cannot replace a newer generation; changing query
  or scope starts a new explicit generation. Paged results never mix snapshots.
  Traverse a result larger than the browser's resident-page budget and inject
  denial between verification and visible-page fetch. Keep the candidate bounded
  and clear protected old/candidate pages on known denial or source retirement.
- [ ] Render current, refreshing, paused, disconnected, reset-required and denied
  states honestly. Known denial clears protected state; old permitted data keeps
  its original basis and cannot appear current merely because reconnect succeeds.
- [ ] Pause, hide, close, expiry and resume use M20's lifecycle and stop unwanted
  refresh scheduling. Socket closure does not claim cancellation of accepted work;
  abandoned views cannot renew leases or create durable queries indefinitely.
- [ ] Multiple tabs/viewers sharing a principal respect aggregate query/admission
  budgets. One active refresh and one latest pending invalidation cooperate with
  current query limits rather than flooding durable busy outcomes or starving peers.
- [ ] Bound browser state/rendering, pending requests, refresh starts and retained
  query cost. Explicit opt-in retention governs accepted results; a newer refresh
  does not implicitly delete older accepted evidence.
- [ ] Real browser tests cover source changes during acquisition/refresh, duplicate
  notifications, gap/resnapshot, schema and generation changes, revocation, pause/
  hide, lost replies and server/node/store restart. Use M20's actual transport and
  failure outcomes, not only mocked success events.
  Retain M18's accepted-but-lost submission and failing-atlas-refresh regressions,
  including navigation/remount while uncertain. Test shared-principal tabs and
  expired/retired request or source resources after a real displayed prefix.
- [ ] Prove a lost SSE connection can resume/reset through the advertised profile;
  WebSocket may be selected only through the same qualified API capabilities.
  M20's independent protocol tests remain regression evidence, not duplicated
  frontend implementations or a requirement to expose a transport selector.
- [ ] Provide real browser/application examples in all three placements, accessible
  controls/status, usage/recovery docs and reproducible `just` proofs. Measure
  source-commit-to-visible-snapshot latency, query/retention cost, fairness and
  resident bounds at declared load without claiming an unmeasured latency target.

## Outside this milestone

New session/message protocols, incremental continuous SQL, joins/retractions,
event-time windows, external connector polling, exactly-once event consumption,
cross-source snapshots and offline data caching. D4's automatic execution while
typing, speculative predictions and Live scheduling require separate numbered
implementation scope. No SUBSCRIBE grammar or general administrative SQL is added.
M20 owns bounded bidirectional WebSocket APIs; that capability alone does not
supply continuous query results or qualify a new application message family.
