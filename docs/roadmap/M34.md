## Question, baseline and scope

What does a declarative join or aggregation guarantee when inputs change,
intermediate state exceeds memory, work retries, or physical placement changes?
The answer must precede enabling syntax or selecting a shuffle implementation.

Its recorded 75-task clean coverage spans several revisions, so same-revision

This milestone selects a first relational profile and a single-authority
implementation sequence. It specifies the semantic obligations that M35 must
preserve when introducing query exchanges and worker/authority rebalancing.
M35 owns the distributed mechanism and its partition-failure qualification.
M36 owns general declarative composition; it must reuse these definitions.

| Selected profile | Scope |
| --- | --- |
| Finite inputs | One or two declared Tables in one realm, exact schemas and independently retained resource cuts; two aliases of one resource share its cut |
| Operators | One inner or left equijoin on an int64 column pair, optional grouping by declared int64 columns, projection, `COUNT(*)`, `COUNT(column)` and ordered checked int64 `SUM(column)` |
| Composition | Scan/filter → optional join → optional grouping/aggregation → projection; existing single-source plans retain their meanings |
| Maintenance | The same relation at explicitly published source-basis vectors, driven by complete committed Table changes, including updates and deletes |
| Distribution handoff | Placement-independent logical identities, exchange coverage, bounded work and fenced ownership transfer; implementation belongs to M35 |

The new profile has no LIMIT, HAVING, arbitrary ORDER BY, implicit coercion,
DISTINCT, non-equality/full/right joins, more than one join, recursion, UDFs,
float aggregation, window functions or event-time windows. Existing single-source
LIMIT remains supported under its existing semantics. KV/Document joins and
maintenance, cross-realm queries, global snapshots and cross-resource transactions
need separate capability selection and proofs. Syntax and typed-plan budgets
must be explicit; operator count/column bounds do not cap retained groups or rows.

### Declarative guarantee descriptor

SQL, typed callers and Board must validate the same neutral definition. The
following are semantic fields to specify in the owning public types, not a new
wire encoding or accepted SQL option syntax:

| Declaration | Required meaning |
| --- | --- |
| Inputs | Authorized source identities/aliases, exact schema contracts and required finite/change-capture capabilities |
| Consistency | Explicit per-resource snapshot-vector mode; reject a requested common snapshot |
| Operators | Typed expressions, bag multiplicity, null rules, canonical order and aggregate error semantics |
| Execution lifetime | Interactive finite, durable captured or maintained; disconnect/retry/publication behavior follows that choice |
| Maintained output | Complete revisions per relevant source transaction, paired changes, recorded input merge order and reset policy |
| Resources | Resident work, durable state/spill/output, source-pin and active-work budgets, with explicit failure disposition |
| Dependencies | Transitive source permissions and lifetime requirements, independent of definition publication permission |

Offline validation reports unsupported combinations before admission. Binding
resolves current source capabilities and validates them again against the sealed
basis; schema replacement cannot silently rebind a saved plan. Explain/inspection
must distinguish these logical guarantees from proposed physical partitioning,
exchange strategy and observed lag. A physical optimizer may choose among legal
plans, but cannot weaken the descriptor to fit available capacity. No declaration
promises a freshness deadline or authorizes effects by default.

## Logical contract

### Identity, source basis and consistency

Let `Q` be the validated logical definition, including schemas, expression
semantics and canonical ordering. Let `B = {resource_i: revision_i}` be its source
basis, with each alias bound to its source contract. A complete answer means
`R = Q(T_1@B_1, ..., T_n@B_n)` under current authorized disclosure.

The first multi-source consistency mode is **per-resource snapshot vector**.
Acquisition pins every selected resource cut, records the whole vector and seals
it before computation. Cuts may be acquired at different times: the vector
does not claim a common instant or causal consistency across resources. Clients
must explicitly select this mode; a request for an atomic multi-resource snapshot
rejects. Self-joins reuse one cut rather than sampling the same resource twice.
Resource, realm, Table identity, schema and decoder/contract definition are bound
alongside each revision. Failed acquisition closes its partial pins.

A query execution identity binds Q, the complete B, result schema, compatibility
definition, execution lifetime and budgets. A prepared request has a distinct
identity while B is being captured; it cannot publish rows as a bound execution.
Durable recovery reuses the sealed B and original accepted request/call. It never
substitutes a newer source because an old pin is missing. Interactive queries
retain session cancellation and lease cleanup; their deadline cannot exceed the
earliest source lease/lifetime. Pin renewal cannot revive retired state.

Placement, partition assignment, task attempts and transport connections are
physical identities. They cannot change Q, B, row identity or accepted call
identity. A schema/definition replacement creates a new query generation and
requires an explicit rebuild/activation boundary.

### Multiplicity, cells, order and arithmetic

Relations use bag semantics: equal projected values remain distinct rows. Join
row identity is the ordered pair of source-qualified stable Table row identities;
left unmatched rows use a distinct unmatched marker. Two left rows and three
right rows with one matching value produce six pairs. Retries of one pair do
not add another occurrence. Projection never implicitly deduplicates.

Join equality matches equal non-null int64 values; null never matches null.
A left join emits one null-extended row only after proving there is no right
match at B. Grouping puts explicit null keys in one group; it does not apply
join-null equality rules. The first Table profile has values and explicit null;
future source profiles must define missing/conflict/type-error behavior without
collapsing them into null. Unsupported key/cell states reject before execution.

Canonical order in the new relational profile is stable Table row-identity order
for a scan, and left-row-identity then right-row-identity order for a join.
Group output is ordered lexicographically by its typed key tuple, with null
before int64 values; each group's contributors
retain canonical input order. Hidden row identities survive projection and
physical partitioning. These rules define reproducible results and errors without
advertising arbitrary SQL sorting. An external merge may be needed to recover
that order after a hash exchange.

COUNT returns checked uint64: star counts rows; column counts non-null values.
SUM skips nulls and applies checked int64 addition in canonical contributor
order. No contributing values gives null. An ungrouped empty aggregate produces
one row (count zero, sum null); grouped empty input produces no groups. For an
unmatched left row, COUNT(*) includes it while COUNT(right.id) does not.
Every selected non-aggregate column must be a declared group key in a grouped
query; mixed ungrouped columns and aggregates reject. Source aliases resolve
unambiguously before execution, including self-joins and repeated column names.

SUM is deliberately **not freely reassociable**. Inputs `[MAX_I64, 1, -1]`
overflow at the second row even though their mathematical total fits. Reordering
to `[MAX_I64, -1, 1]` or summing partitions first can change the outcome. Preserve
the current contract; a wider/exact accumulator or changed overflow rule requires
its own explicitly selected semantic change and compatibility cutover. A stored
group total alone cannot support arbitrary deletions while preserving ordered
overflow behavior. Initially retain ordered contributors and recompute affected
groups with bounded scans. Any prefix-summary optimization needs a proof of both
result and first-error equivalence before use.

Define logical evaluation stages and first-error order in the typed contract,
with independent fixtures before lowering SQL. Stable semantic errors follow
canonical evaluation; operational denial, unavailable storage, cancellation and
quota failure remain separate outcomes. Placement invariance is conditional on
successful authorized execution within budgets; it is not a promise of identical
timing, operational failures or byte-identical batch boundaries.

### Completion and authorization

A finite manifest binds Q, B, schema, ordered row coverage and the closed set of
required input partitions. Every input must prove end-of-cut and every exchange
must prove coverage; an empty queue or transport acknowledgement is insufficient.
Canonical output and its completion evidence may be paged. A visible prefix is
incomplete until the owning profile's completion check succeeds. Early interactive
rows need explicit incomplete framing if a later group overflows or access fails.

Computation and disclosure require current rights to **every contributing source**
and the result, including an input that contributes no matching rows. Aggregation
does not declassify data. Retain the transitive source dependency set with a
materialized result; a grant on the derived resource alone cannot disclose it.
Register dependency/lifetime obligations before publishing the result root.

Multi-source reads must define where each check linearizes. Sequential checks
establish per-authority observations, not simultaneous global authorization.
Revalidate the complete dependency set at the public release boundary under the
selected authority profile; if that profile cannot establish the required checks,
fail closed. Cached pages, tickets and transferred checkpoints confer no rights.
Revocation stops later disclosures and activation; it cannot retract bytes already
returned. Denial, failed computation and unavailable input never become empty
successful relations. Cleanup remains possible without disclosing source data.

## Maintained relations

A maintained relation publishes immutable revisions `R_k = Q(B_k)`. Each B is a
componentwise monotone vector of **data-change** positions with corresponding
resource cuts. Source revision, change position, query publication revision,
processing time and event time are different coordinates. A revision is complete
at B; it makes no assertion about unseen future changes or event-time finality.

### Change capture and deterministic revisions

The source contract must provide an atomic snapshot/change handoff and a complete
ordered changelog. Each accepted resource transaction supplies a stable identity,
before/after row values, primary-key identity, schema and a data progress position.
No-op/framework writes need explicit coverage without inventing row changes.
Updates are a paired removal/insertion; deletes remove the exact prior row.
All changes from one source transaction, including changes to multiple aliased
Tables within that resource, advance together. Current invalidation watches
cannot be used as that log.

Capture B0 and coverage beginning immediately after each component. Backfill
uses bounded pages while later input remains durable. Record the chosen order
of eligible source transactions in the maintenance ledger; different resources
have no implied global order. Each relevant source transaction produces one
logical successor basis. Physical batching or a rebalance cannot coalesce these
bases away, introduce a transient half-update, or change replay's recorded order.
This is an explicit initial policy; changing observable revision granularity
requires a separate contract.

Changes to an inner join preserve pair multiplicities. For a left join, the
first right match retracts the unmatched row, and the last match's removal
restores it. Recompute affected join-key ranges and aggregate groups initially;
incremental algorithms must match full recomputation at every recorded basis.
When both inputs change, tests must detect omission or double inclusion of pairs
formed by both changes. A replayed input/change identity has one logical inclusion.

### Atomic publication over bounded work

One change can affect more rows than one turn permits. Stage immutable operator
pages, output pages and delta segments over bounded turns. A single conditional
commit in the query's own state resource publishes a root/manifest binding the
new B, operator state, accepted input progress and output/delta coverage together.
Until then the old revision remains current. This does not atomically mutate
the source resources. Large fanout is durable staged work, never a larger native
mutation batch or an in-memory queue.

Station/query owns this ledger and uses the public native commit boundary.
Generic verified publication and dependency/pin operations must be specified
before implementation; the existing single-source result manifest does not
already implement a multi-source/operator-state root. The committed root must
retain every page needed for recovery before old roots become reclaimable.
Consumers accept only complete revisions or complete delta transactions against
their exact prior revision. Lost acknowledgements recover the original root and
delta identities; they cannot create a second logical revision.

On semantic failure, retain the last complete revision with its old B, record
the failed successor and stop advancement. Expose failure and lag explicitly.
Recovery cannot skip the bad basis because later changes would make its sum fit.
A reviewed new definition or explicit rebuild/reset generation is required to
choose another basis. On missing retained input, report a gap and require an
authorized rebuild; never claim uninterrupted incremental recovery.

Subscription delivery and named SQL activation are M36 work. Its envelope must
bind definition/generation, previous and new revisions, source vectors, stable
row identities, insert/remove multiplicities, segment coverage and completion.
Partial delta delivery cannot mutate a consumer's exact displayed relation.
Sink effects require separate explicit activation and recorded intent semantics;
neither a retraction nor a rebalance can undo or safely redispatch an external
effect. Materialization correctness supplies no external exactly-once guarantee.

## Query exchanges and rebalancing: M35 handoff

### Exchange during computation

A physical plan may colocate compatible inputs, repartition by a join/group key,
or broadcast a bounded input. Logical equality and the canonical key encoding
must agree with partition routing, including null grouping. Bind the routing
algorithm/version, partition set and physical-plan epoch in exchange metadata.
No optimization may alter the chosen consistency or arithmetic semantics.

Every exchange segment needs query/generation, source-basis and operator identity,
logical producer/destination partitions, stable ordinal, digest and coverage.
Attempts have distinct fencing identities but retries of the same segment retain
its logical identity. Receivers acknowledge durable acceptance separately from
consumption. Stage result publication behind complete input coverage, including
explicit evidence for empty partitions. Retain deduplication/retirement evidence
through the supported retry horizon. An old physical-plan epoch cannot feed a
replacement exchange or publish a second copy of its results.

Credits bound resident/in-flight data; durable backlog and spill have separate
quotas. Fuze describes operators and consumes bounded batches; authorized hosts
own filesystem/network I/O and spill lifetimes. Interactive spill can be discarded
when its session closes. Captured jobs and maintained operators require durable
recoverable spill/state through public storage/publication operations. Workers
do not receive raw Ursula credentials. No successful result may omit spilled
rows after disk exhaustion.

Partition membership, coverage and deduplication ledgers are paged durable
collections. Schedule bounded fan-in subsets instead of retaining a buffer or
connection for every producer/destination pair. Empty-partition certificates
remain part of complete coverage even when no data segment was sent.

### Transfer of execution responsibility

Use stable logical partitions with a recorded mapping to eligible workers.
Changing worker count should move selected assignments rather than reinterpret
every key through `hash(key) % worker_count`. Changing the logical partition/key
scheme is a separate physical-plan migration requiring a recorded cut and complete
coverage; a scheduler update cannot perform it implicitly.

Proposed conservative first handoff for each affected partition:

1. Record the transfer intent, old/new mapping generations and immutable logical
   query identity. Reserve control/recovery capacity before beginning.
2. Quiesce the old partition at a recorded input vector/barrier. Checkpoint its
   operator roots, consumed offsets, deduplication facts, pending outbox/exchange
   segments and published revisions. New source inputs remain durable backlog.
3. Commit a conditional fence bound to that exact checkpoint and consumed cut,
   preventing the old ownership generation from advancing input or publishing
   progress/results. If the old owner advanced after checkpoint preparation,
   the condition fails: reconcile the newer committed work and prepare again.
   A crashed or unreachable old worker requires recovery from already committed
   evidence and retained input/output, not its cooperation.
4. The new owner validates checkpoint/dependencies, obtains current grants and
   eligible ownership, and restores bounded state. Checkpoint possession grants
   neither rights nor authority. Block while evidence is unavailable.
5. Activate routing under the committed mapping, replay only the unconsumed tail
   and reconcile pending outputs by original identity. Delayed old packets must
   be deduplicated or rejected, never silently lost after acceptance.
6. Retire the old mapping and reclaim transferred roots only after the recorded
   recovery/read dependencies and retry horizons permit it.

This transfers worker responsibility against an established authority. Moving
the authority itself additionally requires M35's coordination/failure model:
the partition containing stale authority must not authorize fresh commits or
disclosure. The exact consensus/transfer protocol, availability under partition
and adapter proofs are entry gates; a routing table, Kubernetes placement or
consistent hash is insufficient. The first policy pauses affected work during
handoff; live dual execution is unselected. Disjoint work may continue only where
its dependency and authorization checks remain available.

## Resource and progress obligations

| Resource | Bound or obligation |
| --- | --- |
| Resident work | Explicit page/cache, active-partition, fan-in, batch, merge-buffer and network-credit budgets |
| Durable work | Quotas for source pins, operator indexes, join fanout, result/staging/spill bytes and retained changes; cardinality independent of RAM |
| Hot keys | Measure one-key skew and many-to-many output separately; a key with L and R rows can require L × R pairs |
| Ordered aggregation | No salted partial SUM until canonical error-preserving merge is proved; a hot ordered group can remain serial |
| Catch-up | Measure arrivals λ and sustained service μ; backlog drains only when μ exceeds λ, including restore, warmup and continuing shuffle load |
| Retention | Unlimited by default; no implicit TTL, watermark expiry or data loss under quota pressure |
| Failure/control | Reserve admission, revocation, cancellation, transfer and cleanup capacity; pressure pauses/refuses work explicitly |

An unwindowed maintained join may retain all live rows and indexes indefinitely.
An event-time watermark does not exist in this profile. Future windows must
define timestamp/interval representations, late-data/retraction policy, idle
inputs, terminal closure and retention independently before claiming finality
or state eviction. Repeated finite refresh remains a separate observable profile.

## Owners and implementation sequence

1. **Neutral semantics and fixtures:** Fuze owns the typed relational plan,
   canonical evaluation/errors and capability validation. Query owns multi-source
   capture, dependencies and result completeness. Specify public v1 changes and
   independent truth-table fixtures before any grammar or consumer enables them.
2. **Finite single-authority execution:** implement paged join/group state,
   bounded spill/merge and both interactive and captured lifetimes. Start with
   deterministic recomputation; preserve source/permission checks and exact retry.
3. **SQL and callers:** lower the selected JOIN/GROUP BY/aggregate forms into the
   same plan; update grammar, assistance, CLI, Board and native/SDK capabilities.
   Flight stays at its declared subset until separately qualified. Parser
   acceptance must not enable a missing runtime operator.
4. **Maintained typed execution:** Station/Table owns complete change capture;
   query/Station owns operator state, progress and atomic publication. Qualify
   backfill, paired updates, retractions, rebuild, failure and lifetime behavior.
   Typed activation does not depend on M36's named SQL declaration grammar.
5. **Distribution and composition:** M35 implements and qualifies exchanges and
   transfers under this contract. M36 binds the qualified operators to declarative
   definitions, subscriptions and separately activated effects.

The kernel remains generic: it validates authority, resources and conditional
publication, never application joins or operator computation. Fuze remains Zig
native. SDKs share Zig semantics through the established binding boundary.
Incompatible plan/progress/manifest/ABI changes replace current v1 definitions,
regenerate schemas/signing fixtures and reject missing/foreign definitions before
execution. No v2, fallback decoder or automatic reinterpretation of saved work.

## Alternatives and unresolved implementation choices

| Alternative | Decision and tradeoff |
| --- | --- |
| Require an atomic cross-resource snapshot first | Select explicit snapshot vectors; useful reproducibility without claiming a transaction or solving distributed snapshots |
| Widen SUM and parallelize freely | Preserve ordered checked int64; slower hot groups, but existing accepted semantics remain understandable and testable |
| Keep all hash tables in memory or expire old join state | Select paged durable state/spill and quotas; operational pressure cannot change an exact answer |
| Only refresh complete finite queries | Keep refresh as its own profile; complete change capture and revisions are required for maintained semantics |
| Move workers using only consistent hashing | Use hashing for placement, with durable fences/coverage for correctness; more control work during transfer |
| Adopt an upstream execution engine | Reuse published ideas and independent oracles; preserve the Zig-native ownership/dependency boundary |

Hash versus merge/index join, page layout, exact buffer defaults and broadcast
thresholds remain measurement decisions. Stable partition encoding and complete
wire schemas are implementation entry gates, not specified byte formats here.
Cross-authority release checks and coordination are M35 gates. These unresolved
choices cannot weaken the logical invariants. No throughput, latency or hosted
CI-cost result is claimed by this design.

## Qualification plan

All rows below are **planned evidence**, not passing tests. Begin with an
independent finite oracle, then reuse its results for maintenance and distributed
fault schedules. Record source revision, definition, fixture/seed, topology,
budgets and actual outcomes in the [proof ledger](../../tests/README.md).

| Invariant | Counterexample or required schedule | Gate |
| --- | --- | --- |
| Exact basis | Change either source during capture; reject atomic-snapshot requests; self-join uses one cut; missing pin cannot become latest | Finite |
| Multiplicity/nulls | 2 × 3 duplicate-value join yields six pairs; null join gives no match; null group is one group; left unmatched COUNT variants differ | Finite |
| Empty and checked arithmetic | Empty/all-null inputs, uint64 count bounds, `[MAX_I64, 1, -1]` overflow across pages; rebatching and partition permutation preserve logical outcomes | Finite/distributed |
| Complete result | Empty input/partition, truncated exchange, missing end marker, corrupted digest, late overflow after visible prefix; none completes successfully | Finite/distributed |
| Current dependencies | Revoke either source before capture, mid-spill, after a returned prefix, at publication and on result reread; derived grant alone cannot disclose | All |
| Maintained equivalence | At every recorded B, compare with full finite recomputation; insert/update/delete, first/last outer match, both-side changes and all-null transitions | Maintained |
| Atomic revisions | Crash before/after staging, progress/root acceptance and lost receipt; paired changes cannot appear partially; source schema replacement rejects continuation | Maintained |
| Exact recovery | Duplicate/reordered packets, accepted-but-lost acknowledgements, worker/node/store restart; no extra pairs, counts, revisions or external dispatch | Maintained/distributed |
| Transfer safety | Partition old/new owners at every handoff step; delayed segments, stale grants, pending outbox, retired query and corrupt/missing checkpoint | Distributed |
| Bounds and liveness | Groups/state/results exceed RAM; all keys equal; oversized fanout; slow receiver; ENOSPC; control progress and eventual catch-up under declared capacity | All |
| Lifetime/reset | Released pins, source expiry, cleanup during transfer, unavailable changelog prefix; explicit failure/reset and no revived identity | All |
| Surface agreement | SQL and typed clients produce identical logical plans/results; unqualified SDK/Flight/source profiles reject; incompatible saved artifacts reject | Finite/composition |

Run existing native, publication, query, reactive and recovery proofs unchanged
as regression gates before extending them. Proposed new semantic/model checks
must become real tasks; do not add success-only placeholders. Physical and
all-language coverage, fault models and CI costs are separately recorded before
advertising them. Document validation of this proposal proves none of the runtime
rows above.

## Exit criteria

- [ ] Publish the neutral finite/maintained contracts, exact type/budget/error
  rules, schemas and independent semantic fixtures before enabling consumers.
- [ ] Qualify the selected finite Table profile through interactive and captured
  execution, with paged state/spill, current dependencies and complete results.
- [ ] Qualify complete Table change capture and maintained revisions through
  update/delete, failure, disk recovery, overflow, gap/reset and bounded cleanup.
- [ ] Migrate enabled SQL/CLI/Board/SDK consumers together with capability checks,
  compatibility rejection and public interface/usage documentation.
- [ ] Record executed finite/maintained cases and measured costs separately from
  M35's distributed cases. Deliver the oracle, fixtures and exchange/transfer
  requirements to M35 without claiming its execution or partition proofs passed.

M34 completion requires the finite and maintained gates, including their relevant
"All" cases. M35 owns the distributed column; M36 owns named composition and
subscription/effect exposure. This division avoids making M34 depend on a later
cluster or language milestone while preserving their required entry evidence.

## Primary sources and reasoning limits

The current sum implementation is
[UnifiedStream.step](../../packages/zig/transit-fuze/src/UnifiedStream.zig);
the [rewrite account](../../contracts/sql/README.md#lean-scope) already excludes
general reassociation of checked sums. Those are the basis of the arithmetic
decision, not a claim of PostgreSQL execution equivalence.

[Spark's shuffle description](https://spark.apache.org/docs/latest/rdd-programming-guide.html#shuffle-operations)
identifies network, serialization and disk costs.
[Flink's rescalable-state account](https://flink.apache.org/2017/07/04/a-deep-dive-into-rescalable-state-in-apache-flink/)
motivates separating logical key groups from worker assignments.
[Differential dataflow](https://www.cidrdb.org/cidr2013/Papers/CIDR13_Paper111.pdf)
(CIDR 2013) supplies context for incremental changes and progress. These are
mechanism references, not Transit dependencies or evidence of equivalent
semantics, distributed recovery or performance. This design selects acyclic
Table relations and recorded revision vectors; it does not adopt nested iteration
or claim a general progress-frontier implementation.
