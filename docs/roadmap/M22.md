# M22 — Arrow Flight, Flight SQL and ADBC interoperability

[Roadmap](README.md)

Status: Planned; follows [M21 reactive interfaces](M21.md), reusing the
[M19 serving foundation](M19.md) alongside [M16 gRPC transport](M16.md),
[M13 public queries](M13.md), [M18 unified source contracts](M18.md) and the
exchange/reference/lifetime components introduced by M15.

Scope: a Zig-native Flight gateway to authorized Station Table services, a
bounded read-only Flight SQL frontend to the same Fuze query plans, and tested ADBC
access using an existing Flight SQL driver. [ARROW.md](../ARROW.md) owns layering,
query/result identity, ticket lifetime and gateway failure semantics. Flight
reuses M19's identity, admission, budgets and result-delivery contracts, plus
M20's session/delivery rules where applicable. Its gRPC and Arrow semantics need
independent qualification. M21 does not make continuous Flight queries a
prerequisite or supply their semantics.

## Evidence carried from M15–M18

Use the [implemented query compatibility matrix](../../packages/zig/transit-query/docs/compatibility.md)
and the [M18 proof ledger](../../tests/README.md#m18-qualification) at entry.
The minimum remains one finite Table source, not automatic exposure of every
M18 adapter. Name the chosen query protocol explicitly: public Table v1 has
primitive nullable columns; unified v2 has nested cells preserving missing,
null, type error and conflict. A gateway may expose a qualified profile of either
or both, but cannot silently flatten v2 into v1 or infer SQL support from typed
plan support. KV/Document Flight exposure needs separate client/source evidence.

| Existing component and limit | Consequence for the Flight plan |
| --- | --- |
| M16's [gRPC client](../../packages/zig/transit-grpc/README.md) performs a finite preconstructed call; it has no inbound server | Reuse codecs, framing and tested transport pieces where applicable; implement and qualify server scheduling, authentication and ownership through M19's seams |
| The qualified outbound profile defaults to 16 KiB messages, 64 messages per direction and 256 KiB incoming framed bytes | Fit and measure the selected outbound Flight example, or explicitly qualify a bounded transport extension. Four RPC shapes do not establish indefinite or application-driven duplex streaming |
| M18 permits 64 KiB Arrow segments and a 4 MiB caller workspace | Budget FlightData protobuf/IPC overhead, decoded buffers and concurrent readers; a query segment does not automatically fit the qualified gRPC message profile |
| All ten SDKs consume owned v2 values and independent Arrow readers check its nested layout | Reuse those codecs and ownership fixtures; ADBC lifetime, standard Flight SQL metadata schemas and inbound protocol support remain new obligations |
| Source pins release at capture completion; reads still require current source/request availability | Resolve tickets through the public result reader after restart, pin release, grant withdrawal and permanent retirement; a retained result or valid digest is not a read grant |

Choose standard-conforming bounded batch/message construction at entry; never
split opaque IPC bytes into arbitrary Flight messages to evade a frame limit.
Keep new wire/decoded bounds local to the protocol adapter and qualify them
without raising kernel frames, weakening Publication coverage or buffering a
whole retained result. Flight SQL's metadata encoding needs separate fixtures
even when ordinary Table batches fit.

## Entry gates

| Gate | Required decision / evidence |
| --- | --- |
| Serving reuse | Review M19's qualified service bindings, provenance, acceptance/retry and result interfaces; implement Flight as a specialized protocol adapter rather than a separate gateway authority |
| Client/protocol profile | Pin Flight/Flight SQL protobuf versions and independent Arrow/ADBC client versions; enumerate required RPCs, metadata schemas, errors and unsupported features |
| SQL | Reuse the M12 compiler and M18 capability matrix; map the supported Flight SQL subset to the same [Fuze](../FUZE.md) plans, with no second parser/engine or implicit transaction extension |
| Native implementation | Qualify the inbound Zig gRPC server adapter over M16 transport; outbound connector success does not prove server support. Reuse M18 Arrow codecs while independently proving the standard metadata union/list/map schemas |
| Identity | Bind Flight credentials to M19's qualified scoped-principal and service mapping; prove Flight-specific authentication and provenance without inventing general delegation |
| Result and capacity | Resolve tickets through durable evidence; select v1/v2 schema exposure and fit SQL/protobuf/metadata/batches/handles to measured transport and reader budgets; insert a prerequisite if larger resource guarantees are necessary |

## Implementation sequence

1. Review M16/M18/M19's executed compatibility matrices, M20's reusable session/
   delivery contracts and M21's consumer evidence; pin independent Flight clients.
   Specify the minimum RPC, SQL, metadata and optional prepared-statement profile
   those clients require before implementing the gateway. Record query-version,
   source/type, RPC direction, client version and placement as independent matrix
   dimensions; passing one combination does not qualify the others.
2. Qualify the inbound gRPC/Flight adapter using M16's reusable transport pieces
   and M19's serving contracts, then compose it with the M13/M18 query client.
   HTTP server qualification alone does not prove inbound gRPC. Reuse exact
   retry/result references and availability checks; add Flight-specific tickets,
   status/metadata and lifecycle here.
3. Prove discovery, statement execution and interrupted `DoGet` with independent
   clients, then add the outbound Flight adapter over the existing gRPC connector.
   Inbound query authorization and outbound effect authorization remain distinct.
4. Qualify restart, revocation, slow clients, launchers and client cleanup. Record
   source/type/protocol coverage, operational limits and measured CI costs.

## Exit criteria

- [ ] Reuse serving contracts qualified through HTTP for published service scope,
  identity, admission, budgets and result recovery. Run shared conformance cases
  against both adapters; extend common seams only for demonstrated differences.
- [ ] Expose authorized Table discovery/schema and Flight result retrieval.
  Start with a single endpoint per result and specify the supported protocol
  surface. Return explicit unsupported errors for other methods/actions.
- [ ] Implement bounded read-only SQL statement queries by translating into the
  existing structured plan. Prove the same snapshot/rows/schema as the Station
  API; the gateway and engine never execute inside Transit authority.
- [ ] Return correct Flight SQL catalog/schema/capability metadata, including
  required union/list/map encodings. Advertise the actual SQL/type profile and
  absence of writes, transactions/savepoints and bulk ingestion accurately.
  Preserve the selected v1 or v2 value semantics, including full-width integers,
  negative zero and binary/Unicode where those types are advertised, and empty
  results. Reject unqualified conversions and
  unsupported SQL/type combinations explicitly; metadata discovery must not
  advertise the wider typed-plan surface as executable SQL.
- [ ] Qualify independent Arrow Flight clients and the existing ADBC Flight SQL
  driver through pinned C and Python consumers, including schema discovery,
  null/empty results, aggregates, error/status mapping and explicit cleanup.
  Record any required prepared-statement subset and prove its scoped lifecycle.
- [ ] Resolve accepted queries to exact result/schema/resource revisions and
  persist the evidence needed to retrieve the same result after gateway/worker
  restart. A connection-local buffer cannot be the only result copy.
- [ ] Reject tampered, foreign-scope, revoked and expired tickets; recheck current
  data-sharing/read policy for metadata and every bounded result read. Prove
  pooled connections and caches cannot cross principal/resource boundaries.
  Revoke after an actual returned batch, release the capture pin, retire the
  request/source and restart the gateway/node/store. Each unavailable path must
  fail closed without requerying or translating missing authority into empty data.
- [ ] Exercise dropped `DoGet` connections, duplicate fetches and restart.
  Retrieval restarts the same captured result or reports its unavailability;
  never substitute a fresh query or claim standard offset resumption.
- [ ] Define new-query versus explicit retry identity. Repeated SQL text alone
  cannot deduplicate; re-executing a read does not revive an expired result.
- [ ] Prove slow-client backpressure, bounded query concurrency, cancellation,
  malformed IPC/protobuf, decompression limits and control progress. Transport
  disconnect and ticket expiry cannot silently delete retained durable results.
  Include delayed upstream reads and lost mutation receipts; retry observations
  within policy while retaining exact uncertain admissions. Qualify aggregate
  Arrow/protobuf workspace and control progress under simultaneous fetches.
- [ ] Demonstrate an outbound call to an independent Flight service through the
  gRPC connector, with recorded schema/batches/outcome and network-free replay;
  ordinary Flight client use cannot bypass the application effect boundary.
  Fit the declared finite message/byte/deadline budget and preserve unknown
  remote outcomes. Do not apply the inbound gateway's read-retry policy to a new
  outbound connector attempt; follow M15/M16's recorded reconciliation policy.
- [ ] Package the gateway with explicit TLS/authentication, budgets and discovery
  configuration in all three launchers. Add metrics/logs and Board query metadata
  with provenance, retained-result gaps and no application-value interpretation.
- [ ] Expose reproducible interoperability checks through `just` and CI. Document
  the qualified client/protocol matrix and scale limits beside the owning code.
- [ ] Reuse M15/M16 exchange capture for outbound calls and M13/M18 durable query
  identity and M19 serving admission for inbound work; there is no Flight-specific
  retry database, capture subsystem or alternate Fuze engine. Run the common
  regression suites unchanged.

## Outside this milestone

Full SQL/dialect compatibility, Flight SQL writes, cross-table/resource or remote
database transactions, continuous `DoExchange`, multi-endpoint distributed query
execution, federation, general user-code execution, and a dedicated native ADBC
driver are separate work. M9's co-located Table batches retain their existing
atomicity; the read-only gateway does not expose a transaction API. General
Transit/Station language bindings and public SDKs belong to M9 and M11.
Interoperability does not imply production-scale storage or support for every
Arrow client.
