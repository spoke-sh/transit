# M23 — Clustered execution and portability

[Roadmap](README.md)

Status: Planned; follows [Flight interoperability M22](M22.md) and extends the
kernel, framework, connector, serving/reactive, Document/query and reference-runtime
proofs. Clustering follows the serving, reactive and Arrow milestones.

Scope: extend the reference slice to distributed supervision and lifecycle
management, while preserving a portable protocol. Build on
[M10](M10.md)'s growing-state profile, workload matrix and verification harness;
single-authority growth and multi-node execution are separate qualifications.

## Entry gates and reuse

| Gate | Required decision / existing component |
| --- | --- |
| Authority domains | Specify partition keys, owner/grant authority, revocation propagation, routing and rebalance protocol. M10 growing storage is not distributed write authority |
| Recovery roots | Reuse M14 publication, M15/M16 exchange evidence, M17 causal checkpoints and M18/M22 exact query references; define which authority protects every root and retirement decision across movement |
| Serving and watches | Reuse M19's fixed admission targets, M20's session/watch generations and M21's view recovery; specify route and subscription recovery across partition/placement changes without treating reconnect as new authority |
| Runtime | Reuse the M8 runtime contract and provider controller. Separate sandbox movement, code migration and logical ownership; no provider snapshot grants execution rights |
| Failure model | Declare tolerated partitions/failures and availability tradeoffs before selecting coordination mechanisms; prove stale authorities cannot authorize new work |
| Capacity | Derive workload and control-reserve budgets from the completed single-authority components. Measure skew/hot actors, replica lag, retained pins and recovery, without choosing trading latency targets |

## Implementation sequence

1. Revisit the completed M15–M22 evidence and define a concrete cluster topology,
   authority/placement protocol and generic adapter conformance suite. Keep
   higher-level component APIs unchanged unless a versioned contract is necessary.
2. Implement routing/ownership transfer and provider recovery over durable
   authority; qualify process/grant/mailbox safety before moving connector work.
3. Exercise common publication, cleanup, connector reconciliation, Document merge
   windows, serving admission, watch resumption and query-ticket suites across
   failure/partition schedules. Extend generic seams instead of adding a separate
   clustering path to each protocol.
4. Qualify backup/restore/migration, Board partial observations and the portable
   local adapter. Publish measured topology/workload limits and operational steps.

## Exit criteria

- [ ] Specify authority partitioning, routing and rebalancing before claiming
  horizontal write scaling. Preserve PID/mailbox order, fencing, grant/revocation
  authority and cross-partition delivery; independent appends do not create a
  cross-partition transaction. Measure hot-PID/partition behavior as well as
  aggregate throughput against the M10 workload matrix.
- [ ] Exercise Substrate suspend/resume, worker migration, and stale snapshots
  against kernel ownership and history validation.
- [ ] Recover `transit-runtime-controller` state and wakeups from backlog after controller
  failure; test ownership transfer during partitions and worker-pool changes.
- [ ] Prove cluster-scoped registry uniqueness, conditional rebinding, and
  lookup consistency during partitions; unavailable mutation authority fails
  closed. Rebuild lookup projections from recorded registry history.
- [ ] Extend M1/M15/M16 sandbox, credential, and egress proofs, and M22 gateway
  access/result-recovery proofs, across supported cluster topologies and provider revisions.
- [ ] Extend M19 request/route/provenance recovery, M20 session/watch/resume and
  cross-protocol retry, and M21 live-view proofs across movement and partitions.
  Old route revisions retain accepted destinations; stale watch owners cannot disclose after their policy boundary.
  Missing cross-partition coverage produces explicit resynchronization, not an
  invented global cursor, snapshot or automatic command retry.
- [ ] Define and test runtime-adapter conformance independently of Kubernetes
  resource types; prove a lightweight local adapter can preserve PID, mailbox,
  fencing, and recovery semantics without provider snapshot support.
- [ ] Evaluate whether multiplexing processes within a sandbox is useful;
  document shared failure, suspension, snapshot, and isolation consequences
  before extending the initial one-process-per-Substrate-Actor mapping.
- [ ] Extend M7's proven KV compaction, tombstone cleanup, bounded reader
  dependencies, and resynchronization to distributed consumers and supported
  cluster topologies. Exercise consumer watermarks/pins and retry horizons under
  partitions; preserve no-resurrection guarantees and bounded GC resources.
- [ ] Extend M17 Document checkpoint/causal retention and replica resynchronization
  proofs across supported topologies; partitions cannot renew merge windows,
  revive retired documents or allow stale replicas to bypass current grants.
- [ ] Extend M14 publication and M18 unified source/read/result proofs across
  movement and partitions: no mixed revision, lost staging reservation, early
  root reclamation or permanent-identity reuse. Cross-resource/partition snapshots
  and transactions remain unsupported unless separately specified and proved.
- [ ] Document backup/restore, post-termination retention, and code/schema
  migration with tested procedures, preserving policy, expiry, and deletion
  generations. Fence old deployments and reconcile external effects before
  allowing any restored history to authorize new live work.
- [ ] Extend Board qualification to distributed observations and provider
  changes; show independent read positions, uncertainty, and partial visibility
  without inventing a globally consistent snapshot or exposing hidden resources.
- [ ] Measure representative mailbox, turn, effect, and recovery workloads;
  establish latency/throughput targets from those measurements.
