# M46: General typed Tables and schema lifecycle

Status: implementation in progress; tracked by [issue #75](https://github.com/rupurt/rey/issues/75).
This additional work follows the completed M45 baseline and establishes the
Table foundation required before enabling M34's relational implementation.
Earlier milestones retain their recorded profiles and evidence.

## Outcome and owners

Replace the physical two-column Table assumption with stable schema and row
identities, shared logical types, bounded storage and a coherent CREATE/ALTER/DROP
lifecycle. Generalize INSERT/UPDATE/DELETE and authorized catalog routing over
that same foundation. SQL, typed callers and enabled transports share semantics;
parser acceptance never substitutes for execution or storage support.

Fuze owns pure schemas, values, declaration/mutation compilation and semantic
validation. Station owns Table storage and staged changes over public state
operations. Catalog owns names, immutable definitions, current scoped policy
and attributed outcomes. Query/client owners retain snapshot cuts, bound schema
identity, exact saved work and current disclosure. Hosts own lifecycle and I/O.
The kernel retains its generic one-mutated-resource atomic publication boundary.

## Selected decisions

- Columns default to nullable; PRIMARY KEY implies NOT NULL and is explicit.
  A Table without a declared key has a stable internal row identity, preserving
  duplicates without turning the first column into a constraint.
- Column IDs survive renames and are never reused after removal. Application
  schema revisions are distinct from protocol definitions and resource cuts.
- Reuse all existing Fuze logical type families. Aliases normalize to exact
  descriptors; VARCHAR length, integer width, decimal and temporal parameters
  have explicit semantics. Storage and operator/transport capabilities differ.
- Typed defaults, nullability, single/composite keys, wide rows and nested values
  need shared validation, bounded work and atomic publication. Ordinary Table
  writes cannot persist unresolved source errors/conflicts as successful values.
- Basic ALTER covers add/drop/rename, defaults/nullability and admitted type
  changes. Rewrite old rows through a frozen basis and qualified staged successor;
  never reinterpret a retained snapshot with the newest schema.
- DROP separates live-name removal, write admission, dependencies and retained
  evidence from physical reclamation. Name reuse cannot redirect saved work.
- Incompatible stored/ABI definitions use one coordinated current-v1 cutover,
  mandatory rejection and matching consumers. No fallback decoder or implicit
  reset/conversion of an existing installation is permitted.

## Checkpoints

1. **Contracts and independent semantics:** schema/row identity, type and alias
   matrix, default/key rules, canonical encoding, ownership and adversarial oracle.
2. **Storage:** bounded immutable schema/value/index representation, exact roots,
   revision-aware reads, wide/nested values and disk-backed failure recovery.
3. **Creation and routing:** shared CREATE, discovery, existing scoped permissions
   and public multi-Table reader/writer resolution without private-file edits.
4. **DML:** typed insert/assignment/delete, point then selected predicate work,
   complete validation, precise counts and durable original-operation recovery.
5. **Schema lifecycle:** ALTER/DROP, prepared/saved work, retained readers,
   concurrent changes, dependency checks and interrupted rewrites.
6. **Qualification:** finish the logical-type matrix, enabled consumers,
   diagnostics, performance controls, documentation and committed-source CI.

Issue #75 retains the full acceptance matrix and links implementation commits.
Initial finite joins require the qualified multi-column/scalar profile, stable
identities, schema-bound snapshots, usable routing/DML and basic lifecycle.
Remaining rich-type operators, advanced constraints and branching need not block
that explicit handoff; they cannot be silently counted as completed here.
