# M1 — Transit sequence enforcement and Kubernetes recovery

[Roadmap](README.md)

Status: Implemented and verified within the bounded experimental reference profile.

Scope: one minimal Transit process with a durable mailbox, running in the reference
Kubernetes environment. Prove the kernel's protocol before building applications.

## Design gates before expanding the slice

M1 is proof work as well as implementation. Start with one security realm,
explicit test/service principals, minimal grants, fixed workload code, and a
synthetic effect executor. Keep Kubernetes/Substrate and worker failure within
M1; this boundary does not defer them to a later milestone.

| Gate | Decision and evidence required |
| --- | --- |
| Durable authority | Select framing, authoritative reads, conditional append/coordination, and recovery of uncertain operations; prove one accepted successor despite competing authorities |
| Identity and policy | Select credential validation, principal/realm mapping, grant representation, and revocation ordering; prove impersonation and stale-policy rejection |
| Handler execution | Select runtime I/O isolation and resource limits; keep application computation in callers, prove protocol fencing and recorded-state recovery, and state which code is trusted |
| Time and dispatch | Define work cutoffs, bounded settlement/reconciliation, clock error bounds, and acceptance/closure ordering; prove late-result rejection without claiming cancellation of possibly in-flight work |
| Bootstrap and capacity | Define realm/control catalog recovery, idempotent spawn, and reserved control/maintenance capacity under full-store conditions |

Do not build Station or real external-effect integrations on an unproved gate.
Track evidence using [CONFORMANCE.md](../history/CONFORMANCE.md); documentation agreement
does not mark these gates complete.

## M1 completion and limits

The bounded experimental M1 profile is implemented. Its completed outcomes are:

- Signed ingress and scoped reads, current grants/revocation, ordered opaque
  state turns, fenced ownership, and durable uncertain-operation recovery.
- Independent Zig callers against one generic authority, shared public contracts,
  atomic outboxes, visible blocked failures, and no application code in replay.
- Authorized synthetic effects with bounded settlement, irreversible unknown
  closure, and rejected late results without claiming remote cancellation.
- Opt-in process expiry, checkpoint/trim, immutable-payload deletion, and a
  separate finite-admission profile with reserved physical control capacity.
- Kubernetes/Substrate reconciliation, PID-preserving worker recovery, fresh
  activation, authority/storage restart, and reference sandbox bypass rejection.

[The test guide](../../tests/README.md) owns commands, exact failure schedules,
measurements, and qualification limits. [The v2 profile](../../contracts/TRANSIT_V2.md)
owns supported protocol bounds; [the component map](../history/ARCHITECTURE.md#planned-monorepo-decomposition)
links implementation and operating guides.

These results cover a pinned single-node disk backend, one realm, fixed workloads,
a trusted synthetic executor, and the reference runtime. They do not establish a
general HTTP connector, arbitrary native computation correctness, multi-node
storage availability, host/disk-loss recovery, or production scaling. The
physical-capacity envelope and synchronized-clock requirements are explicitly
qualified in the proof guide. M2 and later work must preserve M1's guarantees and
add evidence for each expanded profile.
