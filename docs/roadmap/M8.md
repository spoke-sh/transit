# M8 — Transit runtime readiness

[Roadmap](README.md)

Status: Planned. This milestone addresses the runtime prerequisites identified
by the [pre-Station review](../reviews/PRE_STATION.md), after [M7](M7.md) and before
[Station](M9.md). It does not introduce a behavior framework.

## Scope and design

- **Authenticated input origins:** publish a versioned, authority-derived envelope
  for external admissions, process outputs and effect results. Payloads never
  choose their origin. Preserve evidence independently of working catalog cleanup.
- **Automatic delivery:** a Zig service uses the public client and a dedicated
  delivery capability. It scans bounded authorized outboxes, preserves route
  order, reconciles exact retries and runs in all three launchers. Credentials,
  readiness, shutdown and uncertainty have explicit owners.
- **Sustained operation:** opt-in reclamation releases resolved outboxes, settled
  effects, retired processes and reclaimed resources from bounded working
  catalogs. Logical identities are never reused. The durable allocation frontier
  and retained live catalog reject old identities after checkpoint/trim;
  historical detail and receipt horizons remain explicit retention choices.
  Pending work and uncertain external attempts cannot be collected.
- **Lifecycle controls:** an initializing process cannot run handlers before its
  required associations exist and initialization is explicitly completed. Scoped
  administration provides generation-fenced suspension/resumption and retry of a
  recorded blocked input. Suspension fits required resource/process lifetimes.
  These are generic operations; Station owns child policies, subscriptions,
  timers, schema initialization and restart limits. Root credentials stay in
  trusted provisioning; behavior workers receive execution rights only.

Default retention remains unlimited. Reclamation requires recorded application
opt-in and the existing last-per-principal receipt horizon; it never silently
changes an existing realm. Quiescent whole-realm checkpoints, one-resource turn
transactions, finite principal/view catalogs and the one-shot finite-admission
reserve remain declared limits. M8 does not promise production HA, unrestricted
throughput, unbounded principal counts or bounded recovery time.

## Exit criteria

- [ ] Publish neutral contracts/schema and caller APIs for authenticated origins;
  reject forged source claims and preserve origin after reclamation/recovery.
- [ ] Run an independently restartable delivery service with scoped credentials,
  exact uncertain retries, observable progress and bounded scans; real Zig callers
  exchange without the test harness delivering their outputs.
- [ ] Release working slots under explicit retention policy; exceed previous
  lifetime output/effect/process/resource limits without reusing IDs or allowing
  old execution, duplicate admissions or late effect results. Prove recovery and
  checkpoint behavior; preserve default unlimited retention.
- [ ] Prove initialization barriers, crash/retry-safe provisioning receipts,
  scoped administration, blocked-input retry and bounded suspension. Reject stale
  generations, missing dependencies and expired resumption; preserve the PID for
  recovery and retire it permanently for logical termination.
- [ ] Qualify delivery and lifecycle/capacity contracts with failure injection,
  lost acknowledgments and revocation. Wire local, Compose and reference profiles;
  verify Board still exposes generic protocol evidence through authorized reads.
- [ ] Update component guides, conformance evidence and Station entry gates with
  supported limits and actual validation results.

## Implementation order

1. Contract and authenticated origins.
2. Scoped delivery service and automatic caller exchange.
3. Explicit catalog collection and sustained-operation proofs.
4. Lifecycle operations and adversarial recovery proofs.
5. Launcher qualification and documentation of evidence/remaining limits.

Each slice receives a scoped conventional commit. Public contract changes are
additive operations; historical signed command encodings must remain stable.
New read envelopes require matching clients. A realm using new operations cannot
be downgraded to an authority that does not understand them.
