# M6 — Persistent reference and incremental development

[Roadmap](README.md)

Status: implemented for the bounded counter scenario on Linux x86_64.
Builds on the [M3 development launchers](M3.md), [M4 instrumentation](M4.md),
and [M5 Kubernetes tooling](M5.md).
The [launcher guide](../../launchers/README.md) owns commands, configuration and
failure recovery; the [test guide](../../tests/README.md#incremental-development-and-workload-upgrades)
owns qualification evidence and limits.

## Outcome

`up` gives a developer a persistent Transit installation: authority, durable
Ursula, maintenance, Board and an example process. Reference also includes an
in-cluster controller and real Substrate sandbox execution. Its application,
provider infrastructure and destructive recovery proofs have separate lifecycles.

Developers can build candidates without changing running services, apply selected
changes, and restart the selected version. Native artifacts use identified paths;
Compose uses image IDs; reference deploys registry digests through the checked-in
Helm chart. Ordinary application updates do not rebuild Kind, Ursula or Substrate.
Zig/Vite+ retain responsibility for source dependency tracking.

All profiles preserve realm/PID, mailbox, committed state, credentials and
storage across supported updates. Reference supports a recorded same-PID workload
change that preserves the Substrate Actor identity too. State conversion,
failed-process repair and arbitrary application compatibility are outside this
profile.

## Delivered boundaries

| Capability | Implementation boundary |
| --- | --- |
| Complete reference application | Named namespace, explicit bootstrap, private credentials, persistent WAL, Board and controller; isolated from proof installations |
| Candidate builds | Requested artifact graphs, immutable native paths/image identities, toolchain and source provenance; candidates separate from selected deployment |
| Compatible updates | Saved target/configuration, affected-service replacement, readiness, explicit retry of interrupted plans and no automatic history rollback |
| Service restart | Reuse selected artifact/configuration; fresh ownership for an application caller |
| Application stop/start | Retain PID, Actor, storage and keys; recorded reference suspension precedes scaling services/workers down |
| Infrastructure teardown | Explicit `infra-down` destroys the owned cluster; ordinary `down` never does |
| Foreground operation | Local and Compose follow replacement services; reference offers an independent access/log manager through `attach` |
| Same-PID workload upgrade | Public protocol transition, guarded provider template switch and fresh worker activation |

Node and maintenance share a binary and update together. Board rebuilds its
frontend assets and embedded API together. Build failure leaves deployed services
alone; identical artifacts/configuration are a no-op. Failed readiness leaves a
visible pending update with its exact target. A replacement plan cannot erase an
unresolved durable workload switch or an uncertain signed request.

Status reports candidate/selected artifacts and manager/container/Kubernetes
observations. These observations do not grant execution authority or establish
application progress. Successful provisioning and updates check the public
protocol and service readiness rather than treating resource creation as success.

## Same-PID upgrade contract

Changing infrastructure code and changing code assigned to a durable process are
separate operations. The [public protocol](../../contracts/TRANSIT_V2.md) records
an authorized old/new workload transition against the stopped binding revision,
application code and committed state revision. It fences prior ownership and
preserves pending input, turn permits, committed outputs and effect identities.
The transition neither extends lifetime nor redispatches external effects.

The first profile keeps the application's declared code/state contract unchanged
and performs no state conversion. It requires a live, unblocked PID and a stopped,
reconciled binding before authorizing the switch. The deployer remains responsible
for compatibility of new code with opaque state; builds and healthy pods cannot
prove that compatibility. Retired processes cannot be upgraded back into life.

The pinned Substrate server already supports `UpdateActor` for suspended Actors
with compatible sandbox/storage definitions and UID/version preconditions. Its
CLI lacked that operation. A narrow, versioned
[packaged extension](../../nix/ate-upgrade/README.md) exposes it without changing
the server API. The adapter checks both old and target identities, performs one
guarded switch, and observes the result on a later scan. A lost response is
resolved by readback. Stale controllers and replacement Actor UIDs are rejected.

The new immutable template gets a version-specific WorkerPool. A fresh pod/key
and activation generation are required; reusing the previous worker UID does not
become safe merely because its template changed. The PID and Actor UID remain
stable. Details belong to the
[runtime contract](../../contracts/RUNTIME_SUBSTRATE_V1.md#same-pid-workload-changes).

## Reference deployment choices

The controller runs inside the chart with a separately scoped Transit principal.
Projected provider tokens and public trust discovery replace a personal
administrator kubeconfig. Kubernetes rights are limited to its namespace's worker
logs and public cluster trust bundles. The pinned provider API lacks per-Actor
authorization, so its credentials remain a trusted controller boundary.

Application updates push only previously unpublished images, retain the one-writer
and Recreate constraints, and keep bootstrap disabled. Controller readiness
checks provider configuration and signed Transit access without advancing the
protocol. Service replacement can interrupt availability; rolling availability
and distributed transactions across provider and authority are not promised.

Host forwarding/log attachment is separate from Kubernetes service lifetime.
Native and Compose profiles remain trusted developer environments. Kind's default
CNI does not enforce NetworkPolicy; the persistent launcher is not the separate
adversarial proof's additional Board isolation fixture.

## Qualification and remaining scope

Local and Compose proofs cover isolated candidates, no-op updates, retained
selections across restart, pending-plan retry, Board-only replacement, same-PID
counter replacement and foreground continuity. Kernel and adapter proofs cover
stale ownership, incompatible declarations, expiry, checkpoint recovery with an
unfinished upgrade, and loss of the provider response.

The real reference proof upgrades Board without replacing unrelated services,
changes the counter image with admitted work waiting, and checks unchanged
PID/Actor, a fresh worker/generation and exactly-once recorded progress. It then
restarts the authority and stops/starts the installation before deleting only
its owned resources. These results qualify the declared counter contract, not
arbitrary code or state migrations.

Capabilities outside M6 require new numbered milestones when selected:

- Source watching after the manual update loop; frontend HMR as a separately
  configured authenticated dev-server mode.
- Application catalogs and versioned state/schema migration contracts.
- Artifact garbage collection and broader host/engine qualification.
- Provider-independent workload replacement, multiple application controllers,
  production authorization/isolation and availability guarantees.

Process Compose topology changes require a full application stop/start. Image
rollback cannot roll back protocol history or completed external effects.
