# M20 — Reactive APIs: SSE, WebSocket and API contracts

[Roadmap](README.md)

Status: Planned; follows [M19 serving](M19.md), before
[M21 reactive interfaces](M21.md). This milestone formalizes hosting reactive
APIs independently of the frontend that consumes them. No implementation or
new generated API compatibility is claimed.

Scope: qualify SSE and a bounded bidirectional WebSocket subprotocol over one
shared typed session/message/subscription contract. Publish accurate OpenAPI
HTTP/SSE and AsyncAPI WebSocket descriptions from the same owning definitions.
[Reactive APIs](../REACTIVE_API.md) owns these semantics; M19 owns base serving
and durable operation admission, while M21 owns live-view refresh and presentation.

## Hosted API surfaces

Hosting a reactive API means publishing a typed, versioned interaction contract
and enforcing it throughout each session. A connection, logical session,
subscription, accepted command and event cursor have separate identities and
lifetimes. Applications can consume this API independently of Board.

| Surface | What Transit hosts |
| --- | --- |
| HTTP with SSE | HTTP commands/control and server-to-client events, with authorized subscriptions and resume or explicit reset |
| WebSocket | Bounded bidirectional commands, receipts/results, subscription control and events under a versioned subprotocol |
| OpenAPI | Generated HTTP/SSE descriptions tied to the accepted service revision, including security, streaming item schemas and errors |
| AsyncAPI | Generated WebSocket channel/message/operation descriptions from the same public types and operation metadata |

Both transport bindings share command identity, authorization and recovery.
If a WebSocket reply is lost, retrying through HTTP recovers the original
accepted command. A notification can trigger an exact snapshot refresh; it does
not imply every intermediate state was delivered or a continuous query was
maintained. M21 owns the view scheduling and presentation that consume this API.

## Entry gates

| Gate | Required decision / evidence |
| --- | --- |
| Serving | M19's executed identity, admission, concurrency, response, cancellation and deployment proofs; long-lived responses cannot monopolize control capacity |
| API model | Version sessions, connections/attachments, subscriptions, message directions, operation/event IDs, correlation, codecs, errors and supported delivery classes |
| Provenance and authority | Preserve current service/resource checks per message/read; pin browser and service-client admission, renewal, revocation and replacement-attachment fencing |
| Source/watch owner | Define the missing bounded public snapshot/change handshake and retained resume/reset contract; existing inspection cursors are not watch APIs |
| Bindings | Pin SSE and RFC 6455 server profiles, versioned WebSocket subprotocol, framing/compression limits, heartbeats, close behavior and real proxy support |
| Descriptions | Propose OpenAPI 3.2.1 for HTTP/SSE and AsyncAPI 3.0 for WebSocket; qualify pinned validators/generators and compatibility with Board's current OpenAPI 3.1 publication |
| Durability and capacity | Distinguish command acceptance, response writes, event delivery and client processing; specify finite leases, aggregate quotas, replay coverage, coalescing/reset and control reserve |

## Implementation sequence

1. Define neutral typed reactive API contracts and independent fixtures before
   adding transport conveniences. Reuse M19's operation identities and Station
   public owners for durable metadata; sockets and local queues are disposable.
2. Qualify one source/watch adapter, including compatible snapshot/change
   acquisition, current reads, retained cursors and explicit reset outcomes.
3. Implement SSE with ordinary HTTP commands/control and WebSocket with typed
   bidirectional commands/control/events. Run the same semantic traces against
   both, including exact operation recovery across a transport change.
4. Generate and validate OpenAPI/AsyncAPI descriptions, shared schemas and runtime
   validators. Publish versioned capability/discovery metadata without exposing
   hidden service definitions or silently upgrading existing Board clients.
5. Prove server/peer recovery, authentication, overload and local/Compose/reference
   placement with independent non-UI clients and a minimal browser transport
   harness. Hand M21 an executable API instead of moving protocol design into UI code.

## Exit criteria

- [ ] A versioned published API declares operations, messages/directions, codecs,
  source bindings, security, delivery classes, lifecycle and budgets. Accepted
  definitions, observed listeners and draft configuration remain distinct.
- [ ] SSE and WebSocket host the same authorized non-trading service: HTTP or
  WebSocket command submission, correlated accepted-stage receipts/results, and
  resumable source invalidations/operation-outcome notifications. A UI is not
  required to exercise or prove the API.
- [ ] WebSocket commands reuse M19's stable request identity and canonical meaning
  across reconnect and HTTP fallback. Duplicate admission returns the original
  receipt; conflicting content, stale bindings and expired retry horizons reject.
  No acknowledgement claims durable acceptance before the owning commit.
- [ ] Define separate connection, session, subscription, operation and event
  identities. Version open/subscribe/renew/resume/unsubscribe/close and typed
  errors; a connection replacement cannot grant new scope or erase accepted work.
- [ ] Prove the snapshot/watch handoff under concurrent commits, policy changes,
  schema changes and retirement. Notifications name exact source/generation and
  covered progress; there is no raw-store tail or invented global ordering.
- [ ] Resume produces duplicate-safe continuation within retained coverage or an
  explicit reset-required outcome. Reject forged, foreign, future and incompatible
  cursors. Source unavailability, gap, denial, expiry and transport loss differ.
- [ ] Reauthenticate new attachments and recheck authority per new command and
  bounded disclosure, including idle sessions. Fence stale attachments at the
  declared boundary; preserve private Board access without adding human sign-in.
- [ ] Qualify browser Origin/proxy/TLS and the selected service-client credentials.
  The WebSocket browser bootstrap must work without assuming arbitrary handshake
  headers or putting credentials in URLs/subprotocol names. Bound unauthenticated
  bootstrap and avoid hidden-resource disclosure in discovery, events and errors.
- [ ] Independently test SSE UTF-8/framing/event IDs/reconnect and deployed proxy
  buffering/timeouts; test WebSocket upgrade, masking, fragmentation, control
  frames, message decoding, subprotocol negotiation, ping/pong and close races.
  Decline unqualified extensions during negotiation; reject frames that use
  unnegotiated compression and reject unsupported codecs/transports explicitly.
- [ ] Bound directional buffers, fragments, messages, connections, subscriptions,
  retained resume work and aggregate per-principal capacity across transports.
  Slow readers/reconnect storms cannot block revocation or other admitted clients.
- [ ] Specify which events can coalesce and their covered-through positions;
  messages requiring complete history cannot silently use that policy. Receipts
  and results remain recoverable when an outcome notification is missed. Neither
  TCP credit, pong nor event receipt is durable client-processing acknowledgement.
- [ ] Recover session/subscription meaning, accepted commands and event source
  references after gateway/worker/node/store loss. Finite leases bound abandoned
  live work without deleting retained history or silently cancelling commands.
- [ ] Generate OpenAPI HTTP/SSE and AsyncAPI WebSocket descriptions from the same
  public definitions used by runtime codecs/validation. Validate examples and
  wire traces against the pinned specifications and independent tooling; prove
  streaming item handling and reject schema drift or unsupported advertised features.
- [ ] Publish compatibility, source/message/transport matrices, bounded diagnostics,
  usage/recovery docs and real local/Compose/reference examples. Add reproducible
  `just` proofs and measured costs under M10, with deterministic models for new
  admission/resume/fencing races and actual independent protocol peers.
- [ ] Hand M21 qualified API/client primitives, snapshot/watch evidence, reset,
  lifecycle and budgets. M21 chooses views and scheduling; it does not invent a
  second SSE/WebSocket subscription implementation.

## Outside this milestone

Board/application live-view UX, automatic query refresh scheduling, predictive
editing, incremental continuous SQL, exactly-once client consumption, a general
lossless message broker, arbitrary user-defined socket handlers, external-source
polling and general operator sign-in. Domain event-log delivery beyond the stated
invalidation/outcome profile, WebSocket compression/binary codecs/HTTP/2 upgrade,
and other protocols require explicit later qualification. OpenAPI callbacks do
not introduce autonomous webhook dispatch; that remains a connector operation.
