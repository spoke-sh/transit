# M12 — Board relief atlas and public query access

[Roadmap](README.md)

Status: Planned; follows [idiomatic SDKs M11](M11.md), before [Documents M13](M13.md).
Its real technical dependency is [verification and scale foundations M10](M10.md),
specifically the qualified growing-query capture/delivery/flow-control protocol;
it does not require M11's language SDKs and can proceed independently of them.
Builds on [Board's public inspection contract](../BOARD.md#public-inspection-contract),
[growing Station query capture](../../contracts/STATION_QUERY_V2.md) and the
[design review sequence](../design/README.md) (D1–D8), none of which is an
implemented UI, capacity claim or accepted final interaction today.

Scope: a bounded public **query** capability — categorically new, not an
extension of Board's existing read-only inspection grant — exposed through two
frontends that share one query/result state: Board's relief-atlas visual
workspace (D7's neighborhood → resource → data workspace, Canvas/Browse of one
query) and a new `transit-cli` executable's interactive `query` shell. Both
consume the same growing-query capture/delivery protocol M10 qualified; neither
adds a query language, a KV/Document adapter or write/export capability. Host
the first real growing `GenServer` process capable of running one, since none
exists outside test harnesses today.

D7 states this precisely: *"The data workspace requires a separately scoped
public query/read capability and an explicit decision about its service
boundary before implementation... Scope any implementation through a new
numbered milestone."* This is that milestone. It does not retroactively accept
D7 or D8's proposed interactions; Auto emphasis, resource-entry transitions,
venue layout (stadium/park/fairground) and growth/readiness horizons remain
open design questions this milestone must resolve through further review, not
by implementing the still-unselected parts of the mockups as drawn.

## Entry gates

| Gate | Required decision / evidence |
| --- | --- |
| Query capability boundary | Specify exactly what Board/CLI may request: qualified Fuze operations only (rows/count/sum, typed predicates, no SQL dialect), authorized typed projections, explicit source/schema revision, bounded execution and result delivery. Board must not decode opaque application values, invent column meanings, dispatch handlers, write results into source resources or access providers directly |
| Growing host | Wire `GrowingGenServer`/`QueryDelivery.Context` into a real running process — `Abi.zig`'s C-ABI export currently aliases `GenServer.Legacy` only, so no foreign host, `transit-station-host`, Board or CLI can drive a growing behavior today. Decide whether this extends the existing ABI/host or ships as a dedicated example first |
| One query state, two frontends | Fix the shared draft/result model D7 requires — typed draft, identified result, source/descriptor revisions, sample/page boundaries, completion state — so Board Canvas, Board Browse and `transit-cli`'s shell edit and display the same query rather than three independent implementations |
| Design acceptance scope | Identify which D1–D8 material this milestone actually implements versus what stays open. Only D2 Figure 7, D5's architecture and D6 Figures 1/4 are accepted (in part) today; D7 and D8 remain in review. Do not implement an unaccepted interaction as if the mockup settled it |
| transit-cli shell contract | Specify the session/authentication model (signed, `rey-cli`-style; a new additive tool, not a `rey-cli` replacement), the REPL's `/`-prefixed meta-command set and its relationship to one query state, how output rendering (table/JSON) stays independent of query semantics, and the query-input form (typed/structured for this milestone; parsed SQL text is a named follow-up once `contracts/sql/`'s grammar covers `SELECT`, not a decision this gate makes now) |
| Capacity and authorization | A query is real Fuze execution, not a cached inspection read: bound concurrent/queued queries per principal, reuse M10's segment/credit delivery rather than an unbounded response, and require current authorization distinct from Board's existing inspection grant |

## Implementation sequence

1. Host the first real growing `GenServer` process with `.query` populated —
   either extend `Abi.zig`/`transit-station-host` to expose the growing profile,
   or ship a dedicated runnable example first, proving capture, delivery and
   flow control work end to end outside a test harness.
2. Specify and implement the query capability boundary: a public request/read
   contract for Table queries only, current authorization, bounded execution
   and delivery reusing M10's segment credit, with Board's existing typed,
   filtered inspection style rather than a raw endpoint.
3. Implement the accepted relief-atlas foundation in `transit-board-web`: D5's
   resource architecture and D6's subtle process fabric with resource
   landmarks (Figures 1 and 4), coordinated with Browse per D1.
4. Take D7's neighborhood → resource → data workspace navigation and
   Canvas/Browse query views back through design review to select Auto
   emphasis, the resource-entry transition and the worksheet's first
   representation; implement the accepted subset against the real query
   capability from step 2, not the D7 fixture.
5. Build `transit-cli` (`transit`), starting with `query`: an interactive
   shell over the same query capability, with `/` meta-commands, editing and
   displaying the one query state step 3 established.
6. Take D8's shared-venue and growth/readiness questions through design
   review only after steps 3–5 land; treat its layout choice and horizon
   interactions as an open follow-up, not a scheduled deliverable of this
   milestone unless review resolves them in time.

## Exit criteria

- [ ] A growing Station process runs outside a test harness with `.query`
  configured, processing `result_chunk`/`result_complete`/`result_ack` frames
  under real disk Ursula/node conditions, reachable by at least one of Board
  or `transit-cli`.
- [ ] The query capability is specified and qualified as its own bounded
  public contract: authorized Table queries only, qualified Fuze operations,
  explicit source/schema revision, bounded concurrent queries per principal,
  and delivery through M10's segment/credit protocol rather than an unbounded
  response. It is provably distinct from Board's existing inspection grant,
  not an implicit widening of it.
- [ ] Board implements the accepted D5/D6 foundation (resource architecture,
  subtle process fabric, Figures 1 and 4's overhead detail) coordinated with
  the existing Browse mode per D1, using real authorized data rather than the
  design reviews' synthetic fixtures.
- [ ] Board's data workspace (design reviewed and selected from D7) lets a
  human enter one authorized resource, compose a bounded query, run it
  explicitly, and see the same draft/result in both a Canvas and a Browse
  representation without silently re-running or losing part of the query
  when switching views.
- [ ] `transit-cli` ships as `transit`, with `query` launching an interactive
  shell: `/`-prefixed meta-commands (at minimum help, schema/table listing,
  session/connection info, quit), typed result rendering, and the same
  authenticated query capability Board uses — not a second implementation of
  query semantics.
- [ ] Neither frontend can execute unqualified operations, decode opaque
  values, access a KV or Document source, or export/write results back into
  a source resource. Denial and revocation clear protected data in both
  frontends and in any remembered workspace state.
- [ ] Partial, expired, cancelled and denied query results are distinguishable
  from complete ones in both frontends; a result never silently completes
  from a partial batch, and current authorization is re-checked at read time,
  not only at query start.
- [ ] Test crash/restart of the growing host mid-query, revocation during an
  open Board workspace or CLI session, and denial before/after partial
  delivery. A remembered Board workspace or CLI history creates no retention
  pin and no offline copy of query results.
- [ ] Document the query capability's contract, `transit-cli`'s command
  reference and meta-commands, and Board's implemented workspace behavior
  beside their code; record which D7/D8 proposals remain open follow-ups
  versus implemented in this milestone.

## Outside this milestone

KV and Document query adapters and unified cross-source querying stay
[M13](M13.md)'s scope; this milestone is Table-only, matching M10's qualified
engine. No SQL or other textual query language is required — `transit-cli`'s shell
ships composing the same typed operations Board does, not a new dialect.
[QUERY_LANGUAGE.md](../QUERY_LANGUAGE.md) and its checked
[`contracts/sql/`](../../contracts/sql/) grammar exist, but that grammar does
not define `SELECT`/expression syntax — the one thing this milestone's query
capability actually does — so it is not a usable input surface for anything
here yet, only for `CREATE`/`SHOW`/`DESCRIBE`-shaped statements this milestone
doesn't need. Wiring parsed SQL `SELECT` into `transit-cli` once that grammar
exists is a natural, explicitly named follow-up to this milestone, not a
requirement of it; do not silently drop it either — track it here rather than
losing it between this document and QUERY_LANGUAGE.md. Export, result
write-back, cross-resource joins/transactions and continuous/subscribed
queries are excluded.

D3/D4's process-fabric-at-scale visuals (100 to 1 billion processes) and D8's
shared-venue/growth-readiness treatment are not required deliverables here.
They are large enough, and distant enough from "run a query," to warrant their
own milestone if design review does not resolve them within this one's
timeline; insert one under the [sequencing rule](README.md#maintaining-the-sequence)
rather than silently deferring them or cramming an unreviewed interaction in
to close this milestone's exit criteria.

`transit-cli` does not replace or absorb `rey-cli`'s protocol-administration
commands in this milestone; that remains a separate, later decision. Browser
or offline query execution, a saved/scheduled query capability and any export
format beyond typed rows in each frontend's native rendering are excluded.
