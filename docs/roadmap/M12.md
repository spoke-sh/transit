# M12 — Declarative interface readiness

[Roadmap](README.md)

Status: Planned; follows [idiomatic SDKs M11](M11.md), before [Board relief
atlas and public query access M13](M13.md). Its real technical dependencies
are [Fuze's v1 profile](../../contracts/FUZE_V1.md) and the typed logical plan it
already defines (`Stream.Plan`/`PlanCodec`) — not M11's SDKs, not M13's Board
work, not any connector milestone. This is deliberately positioned before M13
so a real `transit-cli` can consume it as a named follow-up rather than an
indefinitely deferred one, but M13 does not require it: M13's typed query
capability is the foundation either way, exactly as scoped there.

Scope: make the declarative interface surface [`QUERY_LANGUAGE.md`](../QUERY_LANGUAGE.md)
designed and [`contracts/sql/`](../../contracts/sql/) started actually
**usable**, not merely specified. Complete the grammar through `SELECT`,
compile parsed statements to Fuze's real typed plan, pin the verification
toolchain so it runs in CI rather than an ad hoc session, prove the Postgres-superset
claim against a real corpus, and extend the Lean rewrite-safety program beyond
its first lemma. This is Table-only, matching Fuze's v1 profile — it does not
extend query semantics, only how they're reached.

## Entry gates

| Gate | Required decision / evidence |
| --- | --- |
| SELECT/expression grammar | Extend `TransitExtensions.g4` (or a sibling grammar file) with `SELECT`, `WHERE`, projection and aggregate productions matching Fuze v1's exact model (all/is-null/typed comparisons; row/count/sum; a 0–32 limit) — no operator or clause the plan doesn't already support. ANTLR-checked, zero ambiguity/conflict warnings, same discipline as the existing DDL grammar |
| Compilation, not just parsing | Specify and implement `parse(text) -> Stream.Plan`/`PlanCodec` for the covered grammar in Zig. A parsed statement that cannot compile to an existing plan shape is a rejected statement, never a best-effort approximation |
| Toolchain pinning | Pin `antlr4` and `lean4` in `flake.nix`, the way `nixpkgs#tlaplus` is already pinned for `just test::model`, and add owning `just` recipes. Ad hoc `nix shell` invocations from a chat session are not a reproducible verification story |
| Postgres compatibility evidence | Select and vendor/pin a `libpg_query`-based differential-testing harness and a real compatibility corpus (a curated subset of Postgres's own regression-test SQL, scoped to the statement forms this grammar covers). Define what "compatible" asserts and what it explicitly does not (general CFG ambiguity is undecidable; this is corpus evidence, not a proof) |
| Zig production parser strategy | Decide hand-written recursive-descent vs. a Zig-targeting generator (none exists for ANTLR today) and implement it for the grammar this milestone covers, AST-equivalence-tested against the ANTLR reference parser on the shared corpus |
| Rewrite-theorem scope | Name which additional Lean theorems this milestone proves beyond `filter_reorder_preserves_selection` — at minimum state projection-pruning and predicate-pushdown-through-projection safety, the two rewrites `FUZE.md`'s planning section already names as candidates — and which remain `sorry`/deferred with a stated reason |

## Implementation sequence

1. Extend `TransitExtensions.g4` with `SELECT`/`WHERE`/projection/aggregate
   productions bound exactly to Fuze v1's model; regenerate and verify zero
   conflicts, then extend the sample-statement corpus this milestone's grammar
   work already established.
2. Pin `antlr4`/`lean4` in `flake.nix` and add `just` recipes for grammar
   generation/checking and Lean type-checking, matching `test::model`'s
   existing pattern for a locked, non-default-devshell tool.
3. Build the `libpg_query` differential-testing harness: fetch/pin a Postgres
   regression-test SQL corpus subset, parse it through both parsers, and
   assert agreement on the statement forms this grammar claims to cover.
4. Implement the Zig production parser for the covered grammar and the
   `parse(text) -> Stream.Plan` compilation step; test AST-equivalence against
   the ANTLR reference parser on the same corpus, and plan-equivalence against
   hand-built `Stream.Plan` values for a set of representative queries.
5. Extend `FuzeRewrite.lean` with the additional named theorems from the entry
   gate, each either proved (`#print axioms` reporting no `sorryAx`) or left
   as an explicitly justified `sorry` with a stated reason it isn't tractable
   yet — never a silently incomplete proof presented as done.
6. Document the compiled grammar's coverage precisely: which statement forms
   compile to a real plan, which parse but are rejected at compilation
   (unsupported operators/clauses), and which aren't in the grammar at all yet.

## Exit criteria

- [ ] `SELECT`/`WHERE`/projection/aggregate grammar productions exist,
  ANTLR-verified with zero ambiguity/conflict warnings, covering exactly
  Fuze v1's supported predicate/projection/limit/aggregate shape — no more,
  no less.
- [ ] A real Zig `parse(text) -> Stream.Plan` compiler exists for that
  grammar. Every statement that parses either compiles to a plan Fuze can
  execute or is rejected with an explicit unsupported-construct error; there
  is no silent partial translation.
- [ ] The Zig production parser's AST agrees with the ANTLR reference parser
  on the full shared corpus; documented, reproducible, and re-run on grammar
  changes, not a one-time check.
- [ ] A pinned `libpg_query` differential harness runs against a real,
  version-pinned Postgres regression-test corpus subset and passes, with an
  explicit written statement of what "passes" does and does not establish
  about Postgres compatibility.
- [ ] `antlr4` and `lean4` are pinned in `flake.nix` with owning `just`
  recipes; grammar/proof verification is reproducible by anyone running this
  repo's tools, not dependent on an ad hoc fetch.
- [ ] At least the two named additional Lean theorems (projection pruning,
  predicate-pushdown-through-projection) are stated; each is either proved
  (`sorryAx`-free) or carries an explicit, reviewed reason it remains
  deferred. `filter_reorder_preserves_selection` gains a stated
  model/implementation correspondence note if one becomes tractable, without
  overclaiming a proof about `transit-fuze`'s Zig code.
- [ ] Document exactly which statement forms this milestone makes usable
  end-to-end (parse → compile → executable plan) versus grammar-checked but
  not yet wired to execution (the DDL/`CONNECTION`/`SOURCE`/`SINK` forms this
  milestone does not touch), so nothing here is mistaken for more coverage
  than it has.

## Outside this milestone

`CREATE TABLE`/`DOCUMENT`/`KV`/`CONNECTION`/`SOURCE`/`SINK`/`GRANT`/`REVOKE`/
`SHOW`/`DESCRIBE` stay grammar-only and ANTLR-checked as they already are;
this milestone does not wire them to execution. `CONNECTION`/`SOURCE`/`SINK`
specifically cannot be wired to anything real before a connector exists
([HTTP M15](M15.md)); this milestone does not depend on or block that work.
No dataframe/builder API ships — that remains [M11](M11.md) SDK-per-language
scope, compiling to the same plan this milestone's `SELECT` compiler targets.
KV/Document sources, joins, windowing, materialized/continuous queries and
SQL writes (`INSERT`/`UPDATE`/`DELETE` compiling to execution, as opposed to
already-grammar-checked syntax) are excluded — this milestone is a read-only,
Table-only `SELECT` compiler plus its verification toolchain, nothing wider.

This milestone does not require [Board relief atlas and public query access
M13](M13.md) or vice versa; either can complete first. If M13 completes
first using typed/structured `transit-cli` input as it already scopes,
wiring this milestone's compiled `SELECT` into `transit-cli` afterward is a
small, explicitly tracked follow-up, not a redesign of either milestone.
[M17](M17.md)'s bounded read-only Flight SQL frontend should reuse this
milestone's grammar/compiler rather than defining a second one; it remains
free to add whatever Flight-specific transport and metadata layering it
needs on top.
