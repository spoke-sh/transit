# M25 — Local application installation and replacement

[Roadmap](README.md)

Status: Complete for the trusted local Linux/Zig profile. Implements [issue #9](https://github.com/rupurt/rey/issues/9)
after the qualified [M24 local neighborhood](M24.md), using the downstream Nix
packages introduced by [PR #10](https://github.com/rupurt/rey/pull/10).
[Publication M26](M26.md) and [clustered execution M27](M27.md) follow this work.

## Selected outcome

Start a realm, install a separately compiled Zig application, submit and inspect
committed work, replace a compatible worker, migrate application data, and resume
the same realm after shutdown. The installation and bootstrap contracts are
language neutral. This milestone qualifies the Zig consumer; additional SDK
host integrations require their own evidence before being advertised.

Transit owns installation, scoped activation and physical lifecycle. Application
code owns commands, codecs, transforms, write barriers and complete target
verification. Bank is a downstream consumer, not a runtime dependency or a
source of banking policy in Transit.

## Owners and implementation sequence

1. Define a versioned declaration and management/bootstrap contract. Separate
   stable application/role/resource identities from deployment revisions,
   executable/configuration digests, native ownership generations, data epochs
   and published interface revisions. Declare dependencies and scoped grants;
   associations do not confer access. Keep operator and inspector credentials
   distinct from installer and worker authority.
2. Compose recoverable provisioning from public growing operations. Persist an
   exact signed operation before dispatch and its receipt before deriving IDs.
   Reinstall/attach must recover the same identities and reject conflicting
   declarations. Interrupted or denied provisioning cannot broaden permission.
3. Extend the local neighborhood with application lifecycle management. Fresh
   workers use the public growing bootstrap handshake; replacement fences old
   execution and preserves PID, resources and accepted inputs. A compatible
   application replacement does not upgrade the pinned Transit neighborhood or
   restart unrelated application roles. Bound admission, active children,
   restart attempts, registration, shutdown, diagnostics and retained-record reads.
4. Publish a minimal separately built Zig consumer using public package
   interfaces and generated language-neutral declarations. Reuse the existing
   `transit_station_app.Migration` ledger for a real multi-page evolution. Keep
   installation, readiness, migration progress, verified data activation,
   interface publication and explicit write release observable separately.
5. Qualify exact recovery and current authorization on disk-backed storage,
   publish an iteration guide and measured limits, and carry the resulting
   installed-consumer/compatibility obligations into M26 and M27.

The existing v2 Substrate runtime binding is qualified for its own profile.
The growing bootstrap provides fresh ownership but no growing provider binding.
Reuse its exact identity/fencing rules without claiming a controller or cluster
capability that it does not implement. This local manager is trusted Linux
placement, with native authority rechecked for every operation.

## Exit criteria

- [x] Public CLI/API commands start, install, submit, inspect, stop and resume a
  separately compiled application without private installation-record edits or
  a downstream supervisor.
- [x] Reinstallation, interrupted provisioning and lost native replies recover
  exact receipts and stable identities without duplicate resources or changed grants.
- [x] Explicit compatible artifact/configuration replacement gives a fresh key
  and generation, fences the previous writer and recovers accepted work; an
  incompatible declaration is rejected before replacement.
- [x] Public connection/status surfaces expose authorized role/resource and
  operation evidence without handing realm root credentials to workers or callers.
- [x] A multi-page migration survives worker interruption and lost step/activation
  replies, with retained progress, exact receipts, complete target verification
  and explicit write release. Domain mutations are not repeated.
- [x] Manager, worker, node and disk-store interruption preserve history and join
  owned children. Current revocation is enforced; unavailable dependencies and
  storage pressure never authorize destructive initialization.
- [x] Ordinary callers cannot manage installations or workers. Denied/malformed
  input cannot bypass authority or indefinitely obstruct authorized control.
- [x] Record executable recovery evidence, measured resident/admission/lifecycle
  bounds and qualification limits. Run existing M24 regressions and repository
  checks; new focused proofs do not silently expand the hosted PR budget.

## Qualification and findings

The [proof guide](../../tests/README.md#m25-local-application-qualification)
records the executable schedules and measurements. `just check`, native tests,
independent signing/schema checks, both M24 lifecycle/fault schedules and the
selected application lifecycle/reply-loss/physical-capacity schedules pass.
The separate work-item package builds and runs through public interfaces.

Three implementation findings matter for subsequent milestones. First, pending
application root operations must recover before built-in worker activation can
consume a new root sequence. Second, readiness must name the observed worker
generation; an accepted replacement fence is not a ready replacement. Third,
activation must preserve the principal's permission epoch and scoped grants,
otherwise routine restart can accidentally undo current resource revocation.
Private checkpoints retain bounded current state while request/receipt history
stays on disk; latest receipt floors close the local checkpoint ordering gap.

The public `Status` is a sampled deployment view. Domain initialization must be
observed through domain state before submitting dependent work: the ENOSPC
fixture explicitly waits for that evidence before pausing the data worker.
Release packaging must carry the bootstrap schema/fixture and independently
compiled consumer forward. Distributed placement needs a native growing provider
contract, not adoption of local PIDs, files or readiness markers.

## Outside this profile

Distributed placement/upgrades, authority movement, hot code loading, automatic
source rebuild/watch, arbitrary migration languages, executable administrative
SQL and cross-resource atomicity remain separate. Runtime package upgrades are
distinct from application replacement. Retention remains unlimited by default;
missing or incompatible history fails visibly instead of creating an empty realm.
