# M19 — Arrow Flight, Flight SQL and ADBC interoperability

[Roadmap](README.md)

Status: Planned; builds on [M16 gRPC transport](M16.md),
[M13 public queries](M13.md), [M18 unified source contracts](M18.md) and the
exchange/reference/lifetime components introduced by M15.

Scope: a Zig-native Flight gateway to authorized Station Table services, a
bounded read-only Flight SQL frontend to the same Fuze query plans, and tested ADBC
access using an existing Flight SQL driver. [ARROW.md](../ARROW.md) owns layering,
query/result identity, ticket lifetime and gateway failure semantics.

## Entry gates

| Gate | Required decision / evidence |
| --- | --- |
| Client/protocol profile | Pin Flight/Flight SQL protobuf versions and independent Arrow/ADBC client versions; enumerate required RPCs, metadata schemas, errors and unsupported features |
| SQL | Reuse the M12 compiler and M18 capability matrix; map the supported Flight SQL subset to the same [Fuze](../FUZE.md) plans, with no second parser/engine or implicit transaction extension |
| Native implementation | Qualify the inbound Zig gRPC server adapter over M16 transport; outbound connector success does not prove server support. Reuse M18 Arrow codecs while independently proving the standard metadata union/list/map schemas |
| Identity | Select gateway credentials mapped to dedicated scoped Transit principals and published Table service PIDs; prove trusted provenance without inventing general delegation |
| Result and capacity | Resolve tickets through durable evidence; budget query/SQL framing, metadata, handles and retained results against the actual profile; insert a prerequisite if larger resource guarantees are necessary |

## Implementation sequence

1. Review M16/M18's executed compatibility matrices and pin independent clients.
   Specify the minimum RPC, SQL, metadata and optional prepared-statement profile
   those clients require before implementing the gateway.
2. Qualify an inbound server adapter over M16's transport, then compose it with
   the M13/M18 query client and current scoped identity mapping. Reuse exact
   retry/result references and availability checks; add Flight-specific tickets,
   status/metadata and lifecycle here.
3. Prove discovery, statement execution and interrupted `DoGet` with independent
   clients, then add the outbound Flight adapter over the existing gRPC connector.
   Inbound query authorization and outbound effect authorization remain distinct.
4. Qualify restart, revocation, slow clients, launchers and client cleanup. Record
   source/type/protocol coverage, operational limits and measured CI costs.

## Exit criteria

- [ ] Expose authorized Table discovery/schema and Flight result retrieval.
  Start with a single endpoint per result and specify the supported protocol
  surface. Return explicit unsupported errors for other methods/actions.
- [ ] Implement bounded read-only SQL statement queries by translating into the
  existing structured plan. Prove the same snapshot/rows/schema as the Station
  API; the gateway and engine never execute inside Transit authority.
- [ ] Return correct Flight SQL catalog/schema/capability metadata, including
  required union/list/map encodings. Advertise the actual SQL/type profile and
  absence of writes, transactions/savepoints and bulk ingestion accurately.
- [ ] Qualify independent Arrow Flight clients and the existing ADBC Flight SQL
  driver through pinned C and Python consumers, including schema discovery,
  null/empty results, aggregates, error/status mapping and explicit cleanup.
  Record any required prepared-statement subset and prove its scoped lifecycle.
- [ ] Resolve accepted queries to exact result/schema/resource revisions and
  persist the evidence needed to retrieve the same result after gateway/worker
  restart. A connection-local buffer cannot be the only result copy.
- [ ] Reject tampered, foreign-scope, revoked and expired tickets; recheck current
  data-sharing/read policy for metadata and every bounded result read. Prove
  pooled connections and caches cannot cross principal/resource boundaries.
- [ ] Exercise dropped `DoGet` connections, duplicate fetches and restart.
  Retrieval restarts the same captured result or reports its unavailability;
  never substitute a fresh query or claim standard offset resumption.
- [ ] Define new-query versus explicit retry identity. Repeated SQL text alone
  cannot deduplicate; re-executing a read does not revive an expired result.
- [ ] Prove slow-client backpressure, bounded query concurrency, cancellation,
  malformed IPC/protobuf, decompression limits and control progress. Transport
  disconnect and ticket expiry cannot silently delete retained durable results.
- [ ] Demonstrate an outbound call to an independent Flight service through the
  gRPC connector, with recorded schema/batches/outcome and network-free replay;
  ordinary Flight client use cannot bypass the application effect boundary.
- [ ] Package the gateway with explicit TLS/authentication, budgets and discovery
  configuration in all three launchers. Add metrics/logs and Board query metadata
  with provenance, retained-result gaps and no application-value interpretation.
- [ ] Expose reproducible interoperability checks through `just` and CI. Document
  the qualified client/protocol matrix and scale limits beside the owning code.
- [ ] Reuse M15/M16 exchange capture for outbound calls and M13/M18 durable query
  identity for inbound work; there is no Flight-specific retry database, capture
  subsystem or alternate Fuze engine. Run the common regression suites unchanged.

## Outside this milestone

Full SQL/dialect compatibility, Flight SQL writes, cross-table/resource or remote
database transactions, continuous `DoExchange`, multi-endpoint distributed query
execution, federation, general user-code execution, and a dedicated native ADBC
driver are separate work. M9's co-located Table batches retain their existing
atomicity; the read-only gateway does not expose a transaction API. General
Transit/Station language bindings and public SDKs belong to M9 and M11.
Interoperability does not imply production-scale storage or support for every
Arrow client.
