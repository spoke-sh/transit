# M35: SQL language completeness and declarative dataflows

Status: implementation in progress. The reference inventory and performance
probe are present. Wider finite projections, exact state predicates, numeric literals and scoped
inspection are implemented. Bounded Table mutation compilation/private application
is implemented; public mutation admission, administration and dataflows remain.
This milestone follows M34 in the linear roadmap. Its local first steps reuse
existing authority interfaces and do not require a new clustered topology.

## Problem and intended outcome

The public SQL reference must answer both “how do I do this?” and “does this
operation exist?”. A statement list limited to today's grammar hides missing
user workflows. `INSERT`, `UPDATE` and `DELETE` have neither grammar nor runtime
support. `DESCRIBE` is already grammar-checked but has no executable metadata
contract. Connector declarations are recognized without typed configuration,
catalog publication or query/effect binding.

Make SQL a usable declarative surface over the existing owners, with discoverable
inspection, bounded mutations and explicit dataflow definitions. SQL, CLI, Board
and SDKs must use the same neutral definitions and validation. Keep current
behavior in the [SQL reference](../reference/sql.md); this plan owns proposed
semantics, sequencing and acceptance work. No example here is executable Transit
SQL unless already identified as supported in that reference.

## Baseline and gap inventory

The baseline is the checked query grammar, Fuze parser/lowering, explicit source
contracts and the separate application compiler. Reference-parser acceptance,
runtime execution and public-interface availability are independent columns.

## Implementation sequence

The target composition is a named dependency graph: connector configuration →
captured source → reusable query → maintained relation → subscription or effect
binding. This language sketch is **proposed and non-executable**, including its
new `AS SELECT` and `SUBSCRIBE` forms:

```text
CREATE CONNECTION incoming TO HTTP (endpoint = 'https://input.example.test');
CREATE SOURCE readings FROM HTTP CONNECTION incoming;
CREATE VIEW selected AS SELECT id, value FROM readings WHERE id >= 0;
CREATE MATERIALIZED VIEW accepted AS SELECT id, value FROM selected;
SUBSCRIBE accepted;

CREATE CONNECTION outgoing TO HTTP (endpoint = 'https://output.example.test');
CREATE SINK deliveries INTO HTTP CONNECTION outgoing
  AS SELECT id, value FROM accepted;
```

The sketch shows composition, not a complete deployment. Decoder/schema,
capture scheduling, progress, payload mapping, trigger policy and activation
are unresolved required parts of the neutral definitions below. It deliberately
does not select default dispatch or backfill behavior. A reusable query stores
a definition; a maintained relation owns computation/state; a subscription
observes changes; a sink binding proposes recorded effects. Those roles must
remain distinct even if the final SQL spelling changes.

### 1. Make inspection executable

Implement scoped `DESCRIBE name` and `SHOW` through public metadata reads. Define
result columns, object kinds, qualified identity, schema/revision basis,
continuation, ordering and unknown/denied behavior before wiring the console.
Metadata permission must not imply payload access. Bound each page and active
request independently of catalog size; stale completion data cannot authorize a
later statement. Resolve how the existing four SHOW families relate to KV and
Document objects before extending the grammar.

Add an offline query-description/plan operation with its own typed result before
selecting `DESCRIBE SELECT` or `EXPLAIN` syntax. Explain source requirements,
operators, schema and budgets without submitting work. Inspecting a proposed
definition must distinguish it from the active revision and observed runtime.

### 2. Add a bounded Table mutation profile

Proposed first forms, not accepted grammar:

```text
INSERT INTO items (id, value) VALUES (7, 12);
UPDATE items SET value = 13 WHERE id = 7;
DELETE FROM items WHERE id = 7;
```

Start with one declared writable Table, an explicit key and a literal value.
Support insert of a bounded literal batch only when the whole statement fits
one mutation commit. Start UPDATE/DELETE with key equality; general predicates,
expressions, subqueries, `RETURNING`, upsert and cross-resource changes remain
outside that first profile. This supplies useful operations while making the
atomicity claim testable.

The proposed conflict policy is insert-only with duplicate-key rejection;
UPDATE/DELETE on a missing key complete with zero affected rows. These choices
must become shared typed semantics and fixtures before syntax is enabled. Define
nullability, key immutability, duplicate keys within a batch, result counts,
no-op identity and errors explicitly. Do not infer defaults or a writable codec
from a read projection.

Route mutations to the resource's current fenced writer through an authorized
application/Station operation. Fuze may compile expressions but cannot acquire
kernel authority, impersonate the writer or bypass domain command policy. An
application must explicitly expose SQL mutation capability for the selected
Table. Query access alone remains insufficient.

Selection/read validation and mutation share the existing one-resource commit
boundary with input progress and outputs. A statement exceeding the turn budget
rejects before mutation; it must not silently become a partially committed job.
Freeze request identity and content before admission and preserve the original
receipt under uncertain transport. A reconnect or client retry must not select
different rows or apply the same accepted mutation twice.

### 3. Publish typed declarations and dependencies

Use one neutral definition graph for named state, connections, captured sources,
derived relations and effect targets. Parsing/formatting/validation is offline.
Publication is a conditional, authorized operation with an exact definition
revision, dependency basis, capability checks and recoverable result.

Validate connector-specific typed options and reject unknown/duplicate fields.
Keep credential references distinct from values and define their resolution
scope. A source specifies captured observation identity, decoder/schema and
progress. It does not imply that HTTP/gRPC can resume arbitrary remote streams.
A connection definition grants no authority to connect; source read permission,
publication permission and effect dispatch permission are separate.

Specify replacement and removal with dependency checks and explicit pending-work
disposition. Prefer rejection of removal with active dependents for the first
profile; no implicit cascading effects or data expiry. Map grant/revoke forms
to the actual owning policies. Preserve the current v1 hard-cutover rule when
changing an incompatible grammar, wire/ABI or stored definition, including
definition identifiers and rejection fixtures.

### 4. Define maintained queries and subscriptions

Separate a named query definition, its maintained state and a client's
subscription. Proposed `CREATE VIEW`, `CREATE MATERIALIZED VIEW` and `SUBSCRIBE`
families are subject to a neutral contract review; no accepted syntax is implied.
Begin with the finite operator subset whose incremental meaning can be specified.
Richer joins, grouping and windows need independent operator/state bounds.

Specify the initial snapshot-to-change handoff, input identities, update/delete
representation, ordering, progress evidence, checkpoint recovery and publication
of each complete result revision. Distinguish source revision, data progress,
logical query progress and event time. Backfill and catch-up need bounded pages,
durable backlog and explicit active-work/storage budgets. Source retention
remains unlimited by default; watermarks or capacity pressure cannot implicitly
expire recovery evidence.

Subscriptions need a versioned row-change envelope, schema/definition identity,
snapshot option, progress records, resumable coverage and an explicit reset when
history is unavailable. Current grants fence every disclosure. Define lease,
cancellation, slow-reader and retained-history behavior; a network disconnect
does not erase a maintained query. Existing coalesced watch invalidations are
not a complete changelog and cannot stand in for this contract.

Event-time windows additionally need timestamp/interval types, late-data and
retraction policy, and a precise statement of when output is final. Defer their
grammar until those semantics are agreed and implemented. Do not advertise
continuous execution by repeatedly running finite queries.

### 5. Bind dataflow output to recorded effects

A declarative sink binding identifies its input, destination policy, payload
mapping, credential references and budgets. Review/publication and dispatch
activation are distinct operations. Decide explicitly whether initial snapshot
rows, later inserts, updates or removals trigger work; a retraction cannot undo
an external request.

Derive a stable intent identity from the activated definition revision and
accepted input/change identity. Define when changed definitions may create new
work and how outstanding old-definition attempts reconcile. Atomically record
input progress and the intent through the existing authority boundary. The
connector separately authorizes attempts and captures outcomes. Replay never
dispatches. Preserve unknown outcomes; remote idempotency, retries and status
lookups remain connector-specific policy, never a generic exactly-once promise.

## Acceptance and proof gates

Each stage lands its public typed contract and fixtures before consumers. Every
new statement reference includes support/interface coverage, synopsis, parameter
types, results, authorization, atomicity, errors, recovery, limits and examples.
Update the shared grammar/corpus, compiler, completion, CLI, Board and SDK
capability reporting together. Reference-only forms must continue to report
their actual status until runtime proof exists.

Required executable evidence, all planned:

| Boundary | Required cases |
| --- | --- |
| Parsing/lowering | Complete-input acceptance/rejection, round-trip ASTs, source/type errors, unsupported clauses, bounded allocation and shared fixtures |
| Inspection | No payload disclosure, hidden/denied objects, permission loss between pages, stale schema/revision, catalog larger than resident page cache |
| Mutation | Duplicate keys, missing keys, null/type failures, atomic batch rejection, stale writer, concurrent commit conflict, revocation and accepted-but-lost receipt recovery on disk |
| Publication | Dependency conflict, missing/foreign definition ID, changed-intent rejection, interrupted staging and conditional activation |
| Maintained queries | Independent finite recomputation agrees at each declared basis; updates/deletes/retractions, snapshot handoff, restart, catch-up and overflow preserve exact results |
| Subscription | Slow reader, resume inside/outside retained coverage, reset, current denial, schema change, cancellation and bounded active state |
| Effects | Lost authorization/outcome acknowledgement, stopped worker, duplicate input, replacement, replay without dispatch, unknown outcome and late evidence after closure |
| Interfaces | Same neutral validation/results through enabled SQL/CLI/Board/SDK surfaces; unsupported Flight or other transports explicitly reject |

Keep query execution in Zig outside the authority. Durable collection size must
exceed resident caches in growth proofs; raising fixed cardinality limits is not
acceptance. Preserve current recovery, fencing and permanent-retirement checks.
Record actually executed commands and limits in [tests](../../tests/README.md),
not as passing checkboxes here. The implementation ledger below identifies
completed increments; it does not qualify the remaining proposed operations.

For each iteration, run the independent SQL oracle and affected caller proofs,
compare equivalent workloads with the preceding revision, and keep the measured
change only if correctness and bounded ownership remain intact. Record limitations
and remaining operations here; publish supported semantics in their reference
owners. Pure engine timings cannot establish interactive or durable latency.

## Next implementation boundary

Complete outstanding KV/Document worksheet and installed source coverage. Then add bounded Table mutation admission over the shared compiler and
private-turn helper, with frozen identity, a recorded result and separate writer
authorization. The private helper and canonical request do not establish a public mutation route.
Use Station publication/part staging for the bounded request and separate stored
mutation policy from query policy. One active upload per writer can be represented
by a current pointer to a paged durable namespace record. The final application
turn has room for three row mutations plus one terminal result record; a completed
active pointer can be replaced on the next begin, rather than consuming a fifth
mutation to clear it. Preserve the original namespace/reference and exact signed
input across uncertainty. These admission details are the next proposed
implementation, not executed guarantees. `SHOW SOURCES`, `SINKS` and `CONNECTIONS` retain the
connector meanings in their reference and require their declaration catalog.
The configured-source listing is not a complete realm catalog. Inspection
cannot acquire snapshots, upload work or dispatch effects implicitly.
