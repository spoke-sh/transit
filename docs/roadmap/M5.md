# M5 — Kubernetes tooling and the Transit operator CLI

[Roadmap](README.md)

Status: inspection-only profile implemented; qualification is recorded in the
[test guide](../../tests/README.md#kubernetes-tooling-qualification). The complete
plugin direction was planned before implementation. M5 delivers phase 1 below;
phases 2–4 describe future capabilities outside this milestone and their commands
are unavailable. Schedule that work as new numbered milestones when selected.
Implemented usage and limits belong to the
[plugin README](../../apps/kubectl-transit/README.md).

## Purpose and boundaries

Make the reference installation accessible with ordinary `kubectl`, `k9s`, and
`kubectl ate`, then introduce `kubectl transit` as Transit's Kubernetes operator
interface. It should help a human or agent move from an installation to its
infrastructure, logical processes, and recorded execution evidence.

`kubectl ate` remains the provider interface for Substrate Actors, templates,
workers, snapshots, and atespaces. `kubectl transit` owns the Transit-facing
workflow. Neither Kubernetes RBAC nor provider access grants Transit permissions.
The distinction between PID, activation, runtime binding, Actor, and pod remains
visible. A healthy pod is an infrastructure observation, not execution authority.

Implement the plugin as a Zig executable, `apps/kubectl-transit`, installed on
PATH as `kubectl-transit`. Kubectl discovers that executable as `kubectl transit`.
Use the installed `kubectl` for Kubernetes authentication, transport, and context
handling. Use public Transit/Board clients for future protocol observations and
commands; do not import core, read raw Ursula history, or infer process state
from pod names. No second authoritative registry or local execution store is added.

## Development environment

- Replace K3s with the Kind CLI version used by the pinned Substrate reference.
  Pin the CLI independently of the Kind node image; keep the latter's digest.
- Package upstream `kubectl-ate` through Nix at the existing Substrate revision.
  Preserve its build identity so the runtime adapter can enforce compatibility.
  Reference scripts and controllers must consume the same packaged executable.
- Default the checkout's environment to its private reference kubeconfig, even
  before `up` creates the file. Support a deliberate per-checkout override.
  Do not merge into or modify `~/.kube/config`, and do not silently fall back to
  another cluster when the reference has not been created or has been removed.
- Keep explicit kubeconfig/context selection inside the reference harness, so
  a developer's interactive override cannot redirect setup or teardown.
- `reference infra-up` creates infrastructure; `reference up` also installs the
  persistent Transit application. Discovery lists actual releases and explains
  an empty result. See the [M6 reference launcher](M6.md).

## Command families

This is the complete direction. Only phase 1 ships in the first implementation.
Names in later phases can evolve with their public contracts.

| Family | Intended commands | Authority and evidence | Phase |
| --- | --- | --- | --- |
| Discovery | `get installations`, `status`, `get workloads` | Labelled chart resources, Kubernetes readiness, namespace and release | 1 |
| Service diagnostics | `logs COMPONENT`, including follow and bounded tail | Kubernetes pod logs, explicitly distinct from protocol history | 1 |
| Board access | `board`, optional loopback port-forward | Advertised Board origin and Service; private deployment boundary admits viewers | 1 |
| Logical inspection | `get processes`, `describe process`, `mailbox`, `history`, `journey`, `effects` | Authorized public inspection cuts, retained bounds, uncertainty and source references | 2 |
| Runtime explanation | `bindings`, `describe activation`, `watch` | Join durable Transit bindings with qualified Substrate/Kubernetes observations | 2 |
| Diagnostics | `doctor`, `diagnose`, `support-bundle` | Bounded, redacted operational evidence; report permission failures and partial coverage | 2 |
| Process operations | `send`, `suspend`, `resume`, `retire` | Supported public protocol operations, current grants and fenced ownership | 3 |
| Policy administration | Grant/revocation and retention administration | Explicit administrative contracts, effective revisions, irreversible outcomes | 3 |
| Installation lifecycle | `install`, `upgrade`, `uninstall`, capacity changes | Helm/Kubernetes operations plus explicit bootstrap and credential provisioning | 4 |
| Recovery administration | Restore planning and approved recovery procedures | M17 disaster-recovery proofs; old state never restores live authority automatically | 4 / M17 |

## Phase 1 — infrastructure inspection

Provide help/version and the following concrete interface:

```sh
kubectl transit get installations -A
kubectl transit status --namespace demo --release transit
kubectl transit get workloads --namespace demo --release transit
kubectl transit logs node --namespace demo --release transit --follow --tail 100
kubectl transit board --namespace demo --release transit
kubectl transit board --namespace demo --release transit --port-forward
```

Support `--kubeconfig`, `--context`, and `--namespace` / `-n` after `transit`.
Discovery can use `--all-namespaces` / `-A`; commands targeting one installation
require an explicit release and use one namespace. Machine-readable Kubernetes
views use `--output json` / `-o json`; retain Kubernetes' resource schemas rather
than creating a second installation-state API. Human output identifies release,
namespace and component. Missing resources, denied reads and connectivity failures
remain distinct, with nonzero status for failed requests.

Discover chart resources through `app.kubernetes.io/name=transit`,
`app.kubernetes.io/instance`, and `app.kubernetes.io/component`, honoring name
overrides. Discovery is limited to the chart's current conventions. Labels are
operational associations, not authenticated Transit identities. The initial log
roles are node, Board, maintenance, Ursula, and initialization; Substrate worker
logs remain in `kubectl ate` until binding-aware inspection exists.

`board` reports the configured public origin. Port-forwarding binds only to
loopback and must respect Board's exact Host/Origin, scheme, and port checks.
An origin requiring a remote HTTPS ingress cannot become a usable localhost
HTTP browser origin merely by tunnelling TCP: explain the mismatch rather than
patching configuration, weakening origin checks, or silently adding a proxy.
Do not retrieve signing seeds from Kubernetes Secrets. Board has no viewer key
or session; its deployment controls reachability to the shared inspection scope.

Use argument arrays, validated selectors and component names, finite query
timeouts and bounded captured output. Streaming logs and port-forwards inherit
terminal I/O and stop on interruption. Do not leave detached tunnels behind.
The plugin never changes contexts, deployments, grants, or service configuration
as a side effect of inspection. Port-forwarding requires its separate Kubernetes
RBAC permission despite being part of this observation workflow.

## Phase 2 — explain logical execution

Add explicit connection profiles for private Board endpoints and credential
profiles for Transit signing identities, keeping Kubernetes and Transit
authentication distinct.
Accept private credential files; exclude credentials from command-line arguments,
URLs, logs, shell completion and exported bundles. Never extract a pod's service
identity to impersonate a Transit caller.

Reuse public `transit-client` inspection contracts or the Board OpenAPI, with
runtime validation and version negotiation. Display the observed cut, freshness,
continuation validity, retained floor and inaccessible relationships. Paginate
explicitly; watches need bounded state, backoff, cancellation, and reauthorization.
Do not stitch observations across changed cuts or turn unavailable data into empty
state. Framework lenses enrich evidence without hiding the underlying PID.

Resolve a provider location from an authorized durable binding before requesting
provider diagnostics. Show incarnation/UID and observation time; disappearance
or a mismatched identity is not permission to recreate an Actor. Diagnostics
must label Kubernetes readiness, provider state, and protocol state separately.
Bundles default to metadata and bounded diagnostics, redact credentials, and
require explicit opt-in for payload/private-data export.

## Phase 3 — protocol operations

Add mutations only after their kernel/client contracts and authorization tests
exist. Persist exact signed request identity before submission and make retries
explicit. Report durable admission, turn completion, and effect settlement as
different outcomes. Previews can explain scope and consequences but do not
reserve authority; revalidate at the actual boundary.

Commands must surface current realm/PID, expected revisions, lifecycle/retention
constraints, and permanent retirement. A provider resume or pod restart cannot
stand in for Transit activation. Reject unsupported suspension, settlement or
retention guarantees. Unknown external outcomes cannot be made safe by a generic
retry command; connector policy owns reconciliation and compensation.

## Phase 4 — installation and recovery lifecycle

Compose the Transit Helm chart and explicit provisioning operations. Version
configuration, image digests, protocol compatibility, and rollback constraints.
Separate Kubernetes resource removal from logical process retirement and physical
history deletion. Keep storage and control evidence unless the operator explicitly
requests a supported destructive procedure. Dry runs must state what cannot be
validated without current authority or actual provider access.

Do not implement restore/clone promotion until the M17 recovery procedure fences
old execution and reconciles outstanding effects. A successful Helm rollback is
not proof of safe protocol rollback. Kubernetes scaling does not automatically
provide additional authority writers or safe controller concurrency.

2. Update Kind, packaged `kubectl ate`, kubeconfig integration, reference consumers
   and toolchain documentation without upgrading Zig, Ursula, or Substrate.

4. Verify help/plugin discovery offline; query/selection boundaries, explicit

   Do not claim that infrastructure inspection completes phase 2 or later gates.
