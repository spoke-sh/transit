# M33 — Publication

[Roadmap](README.md)

Status: **Planned**; follows [protocol consolidation M31](M31.md) and
[public Internals M32](M32.md), before [clustered execution M35](M35.md). Formalize and implement release publication
of Transit artifacts from a tagged repository revision. This is software
distribution; [M14](M14.md)'s immutable application-record publication and
[M23](M23.md)'s interface publication retain their separate meanings.

Scope: a coherent versioned release across Nix flakes and derivations, downloadable
archives, an install-script one-liner, Homebrew, Docker/OCI images and Helm
packages, with an explicit inventory of libraries, SDKs and supporting artifacts.
A release-tag push triggers GitHub Actions qualification and publication to
GitHub Releases and GitHub Packages as appropriate. Build outputs in a developer
checkout or transient CI artifacts alone do not constitute a published release.

## Baseline and owners

[M31](M31.md) must complete the v1 hard cutover before publishing release
artifacts. Package only the current contracts and implementations. Bind the
release manifest to their exact compatibility identifiers; a common v1 label
does not make pre-1.0 builds interchangeable.

[M26](M26.md) supplies the user documentation site and generated interface
reference; [M32](M32.md) adds the public Internals section and scientific standard. Publish a version of those pages and specifications with the exact
release artifacts; replace checkout-only onboarding only after installed release
commands have executed successfully.

[M25](M25.md) adds local application installation and replacement before release
publication. Qualify that workflow from installed packages with a separately
compiled consumer; application revisions must remain independent of neighborhood
artifact upgrades. PR #10 already supplies pinned `transit` and `transit-local`
flake packages, `serve` and an explicit console configuration default. Preserve
those downstream entry points and extend their evidence for release channels.
M25 now has a qualified public schema/signing fixture, standalone consumer
manifest, exact operation recovery and a v2 local configuration. Package those
interfaces and build the consumer outside the source checkout against installed
public dependencies. Test a changed application executable independently from a
Transit/provider upgrade, preserve current revocations, and reject compatibility
mismatches before effects. A local path dependency or working-tree proof alone
does not establish a published consumer toolchain.

[M27](M27.md) adds default embedded Board, configuration version 3 and version-2
application inspection declarations while retaining v1 signed bytes. Preserve
`--no-ui`, independent inspection authority, retained revocations and the full
Nix executable manifest in each release channel. UI toggling is not a pinned
neighborhood upgrade.

The [Nix tooling](../../nix/README.md) pins development dependencies and selected
tool packages; it does not establish a complete release distribution.
[Launchers](../../launchers/README.md) and the
[reference deployment](../../deploy/reference/README.md) build local images;
the [Transit Helm chart](../../charts/transit/README.md) currently asks consumers
to supply immutable service images. [M11](M11.md) qualifies installed SDKs on
Linux x86_64, not universal platform or public-registry availability.
The existing [CI workflow](../../.github/workflows/ci.yml) runs on version tags;
tag-triggered CI is not yet this publication pipeline.

Keep build/package definitions with their Nix, app, language and chart owners.
Release orchestration composes them from one manifest and exact commit, without
duplicating protocol types or inventing a separate application version model.
[Deployment](../history/DEPLOYMENT.md) owns the installation/runtime boundary;
[Testing](../history/TESTING.md) and [M10](M10.md) own qualification and CI costs.

## Artifact and channel inventory

At entry, enumerate every user-consumable executable, library, SDK, contract,
frontend bundle and deployment package with its owner, dependency closure,
license/notices, version/ABI compatibility and supported OS/architecture.
Cover `transit`, the server's service neighborhood, Board, Station and Fuze,
`kubectl-transit`, and any retained compatibility tools. Identify embedded versus
separately shipped assets and required external Ursula/Substrate components.
Do not ship example applications as mandatory infrastructure or rename external
projects as Transit artifacts.

| Channel | Required release contract |
| --- | --- |
| GitHub Releases | Canonical tagged release notes and downloadable platform archives, source/package bundles, checksums, release manifest and verification/provenance material |
| Nix flake | Documented version-pinned package/app outputs for the supported Transit commands and components, with reproducible locked inputs and a usable install/run path |
| Nix derivations | Reusable package definitions, declared build/runtime dependencies, immutable source hashes and a documented consumption path independent of the development shell; decide and document binary-cache distribution/trust |
| Install shell script | A documented HTTPS one-liner and inspect/download-first path that select a qualified version/platform, verify its artifact, install to an explicit prefix and report unsupported systems safely |
| Homebrew | A versioned formula/tap and qualified bottles or a tested source-build path, derived from the same release artifacts/checksums, with install/upgrade/uninstall behavior |
| Docker / OCI | Versioned Transit service images in GitHub Container Registry (GHCR), immutable digests and only qualified architecture manifests; document runtime user, entry point, persistent volumes, signals and external dependencies |
| Helm | A versioned `transit` chart archive attached to the GitHub Release and an OCI chart in GHCR; align chart/app versions and digest-pinned images, schema/defaults, prerequisites, installation and upgrades |
| Libraries and SDKs | Installable native headers/libraries, generated contracts and language packages for the qualified matrix; record which ship as GitHub assets and which additionally require target-language registries, including ownership and credential prerequisites |

The named channels are milestone deliverables. Inventory additional package
registries and platforms explicitly as included or deferred; a Nix system entry
or cross-compiled binary is not evidence of working installation. Start from the
qualified Linux x86_64 profile and select/test each additional Linux/macOS and
architecture target before advertising it. Do not invent live download URLs or
onboarding commands before the corresponding release path exists.

## Release identity and workflow

Define the release-tag convention, version source and prerelease/stable rules.
Bind every output to the exact tag commit and locked dependency revisions. The
release manifest records component versions, platform/ABI constraints, artifact
hashes, OCI/chart digests and qualification evidence. Explain CLI/server/protocol,
SDK/native-library and chart/image compatibility separately; a shared release
number does not make every historical combination compatible.

1. A pushed release tag validates the tag/version/commit relationship and starts
   the release workflow. Ordinary PR validation never publishes artifacts.
2. Build the declared matrix from clean checkouts with pinned inputs. Reuse
   identified immutable outputs across tests and packaging; generate notices,
   checksums, SBOMs and signed provenance tied to those exact bytes.
3. Run required package/installed-consumer checks and relevant reference release
   qualification for that revision. A skipped, failed or unavailable required
   platform cannot silently become supported in the release manifest.
4. Stage GitHub Release assets and versioned OCI images/charts and verify the
   complete manifest. Prepare the install script and Homebrew metadata from
   the same verified set without promoting stable/prerelease channel pointers.
5. Re-download/install published outputs on clean supported hosts and exercise
   the real server/console and selected deployment artifacts. Expose the completed
   release and promote channel pointers only after verification. Retain the
   evidence alongside release notes and the exact immutable references.

Specify token permissions and signing trust, separating untrusted build inputs
from release credentials. Release tags/assets are not silently moved or replaced
with different bytes. Reruns reconcile the same manifest and resume incomplete
uploads; conflicting existing hashes fail. Cross-channel publication has no
assumed atomic transaction: show partial status, order pointer promotion and
define repair/withdrawal procedures without erasing a bad release's identity.
Handle prereleases, failed qualification, tag conflicts, interrupted uploads,
registry outages and post-publication verification failures explicitly.

## Installation and lifecycle

Installation obtains artifacts; starting a server, initializing authority and
granting credentials remain explicit runtime actions. The shell installer and
Homebrew package must not silently require root, change shell profiles, start
services, replace an unrelated installation or delete durable data. Define
version selection/pinning, offline archive use, user/system prefixes, platform
detection, checksum/signature failure and interrupted-install cleanup. Publish
a trust/verification path for the bootstrap script itself as well as its payloads.

Qualify `transit server` and `transit console` from the installed package outside
the repository with no inherited `zig-out`, frontend build or developer PATH.
Account for Board's embedded assets and every required server dependency. Keep
storage and credentials outside immutable packages/images. Container restart,
Helm upgrade or package rollback cannot initialize missing history, revive old
authority or claim a safe data/schema downgrade. Publish compatibility checks,
data-preserving uninstall and tested upgrade/rollback limits; broader restore
procedures remain [M35](M35.md).

## Exit criteria

- [ ] Publish an owner/version/platform/dependency matrix for every Transit
  artifact, including explicit registry/platform exclusions and upstream licenses.
- [ ] A release tag drives a reproducible, reviewable GitHub workflow from clean
  source to GitHub Release assets and GHCR images/charts. Non-release events
  cannot publish, and failed required qualification prevents channel promotion.
- [ ] Every named channel has working version-pinned documentation and actual
  install/run evidence: flake outputs, derivations, downloaded archives, the shell
  one-liner, Homebrew, Docker images and Helm packages. No placeholder task or URL
  counts as delivery; additional registry/platform support requires its own proof.
- [ ] Installed CLI smoke and recovery tests exercise real server/console paths
  with persisted local state; supported images and packaged charts pass their
  own startup, readiness, signal, credential and storage-boundary checks.
- [ ] Verify all published bytes against the release manifest, checksums and
  signing/provenance policy. Test tampered/truncated downloads, wrong platform,
  missing dependencies and dependency/version mismatches before installation.
- [ ] Exercise repeat installation, upgrade, supported rollback and uninstall on
  each advertised channel, preserving durable data and credential separation.
  Unsupported downgrade or storage compatibility fails before activation.
- [ ] Exercise release reruns, duplicate/conflicting tags or assets, partial
  channel failure, prerelease isolation and withdrawal/repair. Stable pointers
  only advertise a verified set; failures and incomplete publication stay visible.
- [ ] Install each advertised native/SDK package into an independent consumer;
  verify ABI/generated-contract alignment and required runtime libraries rather
  than only checking that an archive was built.
- [ ] Record executed proof, release limitations, provisioning/build/install/test
  costs and hosted release budgets in [tests](../../tests/README.md). Keep release
  matrices distinct from M10's ordinary PR budget and run clean committed-HEAD
  checks before claiming reproducibility.

## Outside the selected profile

Publishing an artifact does not qualify new runtime semantics, every Nix target,
HA topology or provider. Automatic fleet upgrades, unrestricted platform support,
new package registries without declared ownership, and disaster-recovery/data
migrations are not implied by a release tag. The artifact matrix must say where
support ends; [M35](M35.md) retains clustered execution and portability obligations.

## M24 installation handoff

The implemented [local server profile](../../apps/transit-cli/docs/server.md)
needs `transit`, matching `transit-node` and `transit-query-host`, Ursula 0.5.1,
and the pinned native MinIO cold provider. MinIO is an external artifact with
its own license; packaging must include its dependency and notice rather than
quietly substituting unbounded in-memory cold storage. The runtime has no shell,
Python, Docker, Process Compose or source-checkout dependency. Docker is used
only to extract/setup the current qualification fixture. Linux parent-death and
process-group proofs do not establish macOS or container-init equivalence.

Installation identity currently pins the normalized configuration and SHA-256 of
all executable bytes, including the CLI. It rejects changed paths/configuration
or binaries on ordinary startup. M33 must design an explicit, recoverable upgrade
transition before advertising package upgrades: flush original pending signed
operations, verify old/new compatibility, preserve native PIDs and storage,
record the new artifact set, then activate fresh worker keys/generations. Editing
the installation JSON or deleting activation markers is not an upgrade procedure.
Channel rollback must distinguish supported code rollback from forbidden provider
history rollback below the recorded authority observation.

Package examples must keep data and the private provider home outside immutable
artifacts. The generated console configuration refers to a scoped caller key and
an explicit recovery file; the native gateway holds neither that key nor root.
Retention, finite admission/control quotas and provider free-space thresholds
remain installation policy. Installing a new package cannot reset admission or
extend accepted lifetimes. Reuse the actual server/console, interrupted-bootstrap,
gateway-pressure and physical-capacity proofs against installed release bytes.

Clean qualification exposed two proof-harness dependencies: a Document branch
shadowed the C runner's ordinary codec fixture, and a Board proof assumed another
lane had created its evidence directory. Installed release checks must exercise
ordinary SDK behavior alongside feature-specific paths, and each lane must own
its output directories. The corrected 59-task ordinary inventory now passes in
isolated clean lanes. Its local costs do not requalify M10's earlier hosted
33-task samples; measure release/SDK matrix costs and hosted feedback explicitly
before making current budget claims, without silently raising accepted budgets.

## M23 artifact handoff

The shared application compiler emits validated proposal modules; generated files
select compatible renderer artifacts but do not supply the current published
interface or any access grant. Package compiler/model/component compatibility
with the artifact inventory. Installation and upgrades must still read the
current publication and retain accepted-operation recovery when declarations or
source contracts change. Example operator seeds and provisioned resource IDs
are fixture inputs, never release defaults. The standalone work-item frontend
uses the shared application/query packages without importing Board; preserve
those direct package boundaries in published libraries and example artifacts.
