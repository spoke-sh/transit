# M42: PostgreSQL and MySQL wire access

Status: implementation in progress; tracked by [issue #48](https://github.com/rupurt/rey/issues/48).

## Outcome and current decision

Implement **PostgreSQL and MySQL read/write wire access over the existing Transit query and catalog owners**, with PostgreSQL first and MySQL following the same shared gateway boundary. Both must execute the selected SELECT, typed prepared SELECT/DML, INSERT/UPDATE/DELETE and CREATE TABLE profile. A read-only listener or literal-only demo is an intermediate checkpoint, not issue completion.

**Priority selected on 2026-10-13:** take #48 next after merged [vectorization PR #80](https://github.com/rupurt/rey/pull/80). This review checks merged main [`b775e2b7`](https://github.com/rupurt/rey/commit/b775e2b7a50bf46192acadf5e36102beef05057c), including general Tables (#75/#77), relational execution (#70/#78), typed query compilation and vector execution (#71/#79/#80). #76 remains separate storage/read/write amplification work, not an entry prerequisite.

The recommendation is now **catalog-routed general Tables with a bounded, explicit wire type matrix**, replacing the old one-configured-two-column-Table design. An authorized client should be able to CREATE a supported Table and then INSERT/SELECT it through the same catalog mapping. Resource provisioning, principals, policy and grants remain explicit; creation grants no additional permission.

Implementation is in progress on `feat/sql-wire-access`. The client transcript and Zig TLS-server probes now execute; neither database listener exists yet. W0 remains open until the numerical gateway budgets and neutral contracts are fixed. The [proof ledger](../../tests/README.md#database-wire-foundation) distinguishes these probes from gateway interoperability. This record replaces the former two-column implementation proposal without reopening completed milestone outcomes.

## Selected delivery profile and boundaries

- **Catalog scope:** multiple Tables discovered in explicit configured catalogs, using current native and catalog permissions. SQL database selection chooses a configured mapping; it never provisions a resource, guesses an owner, switches credentials implicitly or grants access. Start with one active fenced gateway owner per deployment and dedicated upstream principals; no shared principal concurrently used by unrelated applications.
- **Reads:** finite single-Table SELECT, projection, filtering, COUNT and ordered checked int64 SUM; reuse the existing int64 inner/left equijoin and grouped COUNT/SUM profile for literal relational SELECT. Preserve its explicit per-resource snapshot vector; do not advertise a global database snapshot. No new join algorithm, maintained-query subscription or distributed scheduler.
- **Writes:** current bounded single-Table INSERT/UPDATE/DELETE and CREATE TABLE, using the general catalog owner. Preserve defaults, NULL, keys/unkeyed rows, complete successor publication, atomic duplicate rejection, zero-row outcomes and identity-safe name reuse. Do not retain the obsolete one-to-three-row/primary-key-only compiler restrictions. SQL's 4096-byte bound, the current 1–1024 INSERT-row/4 MiB intent bounds and deployment/work quotas remain separate constraints; a gateway may impose tighter published limits.
- **Prepared execution:** single-Table SELECT and DML with typed parameters are required through both protocols. Keep named statements and executions as bounded session objects. Literal relational reads are included; **parameterized relational plans are a separately identified extension**, not implied by the single-source LogicalPrepared compiler. CREATE has literal typed definitions; parameters never substitute identifiers or SQL syntax.
- **Required wire types:** int64, uint64, finite float64, Boolean, UTF-8, binary and SQL NULL in nullable positions, over general Table schemas. The int64 path is the first vertical slice, not the final matrix. Other stored logical types remain valid in Transit but do not acquire wire support implicitly. Wider integers, decimal/temporal/UUID/JSON/container mappings need their own explicit admission and evidence; unsupported projected/parameter types reject before dispatch where knowable. State/count operations retain their owning admission rules.
- **Autocommit only:** each accepted write is one native domain operation; each read execution gets a fresh authorized cut. Reject BEGIN/COMMIT/ROLLBACK, savepoints, autocommit-off, multi-statement SQL and unsupported execution groups before write admission. No fake rollback, implicit cross-statement atomicity or automatic retry after a transport error.
- **Explicit exclusions:** gateway ALTER/DROP in this first profile, broader DDL/DML, RETURNING/upserts, COPY/LOCAL INFILE/bulk protocols, replication/binlog, stored routines, LISTEN/NOTIFY, MySQL X/MariaDB parity, arbitrary system catalogs, general ORM/BI/JDBC/ODBC compatibility and new platform support. External ALTER/DROP remains a required stale-preparation/recovery test.

The type mapping must be lossless and independently checked. Proposed core mappings are PostgreSQL int8 / numeric(20,0) / float8 / bool / text / bytea and MySQL signed/unsigned LONGLONG / DOUBLE / a documented Boolean integer convention / UTF-8 text / binary bytes. uint64 and counts must never pass through a float or narrow silently. Define text/binary formats, OIDs/type flags, nullability, lengths, charset and comparison semantics from the actual logical schema. [PostgreSQL text's NUL restriction](https://www.postgresql.org/docs/18/datatype-character.html) and unsupported collations require explicit behavior. MySQL Boolean parameters accept only the qualified representation. Native SUM and byte-order string comparisons remain Transit semantics, not blanket server SQL equivalence. Missing/type-error/conflict cells never become SQL NULL during row encoding. An error after a disclosed row prefix leaves an incomplete result and receives no successful terminal marker.

## Shared architecture and binding work

Keep two Zig wire adapters over one reusable gateway session/execution library, composed by an opt-in `transit-sql-gateway` entry point. These names describe proposed components, not existing packages. Give each real library its own manifest, direct dependencies, tests and public interface when implemented. No raw Ursula access, kernel SQL execution, foreign query engine or per-protocol mutation implementation.

The shared boundary owns account/catalog mapping, authenticated metadata, statement classification, typed preparation/binding, execution lifetime, diagnostics and write recovery. Fuze owns syntax/types/plans; transit-query owns snapshots and result validation; transit-catalog/Station own accepted intent and publication. Console implementation is useful evidence, not a library to import. Extract genuinely shared behavior into its owner and migrate callers if necessary.

Render existing semantic diagnostics into explicit SQLSTATE and MySQL numeric-error mappings, preserving syntax/unsupported/interface/binding/limit distinctions, current denial, schema conflict, cancellation, capacity and uncertain outcome. Convert source coordinates deliberately; never parse prose to infer whether a write committed. Authenticate and check scope before schema-sensitive metadata/errors, and redact credentials, SQL values and unrelated stored data. Unknown runtime failures stay on their original recovery path.

Before wiring prepared messages:

1. Add a catalog-bound preparation/execution boundary that freezes resource/catalog/object/schema/definition and output/parameter metadata **without retaining a data snapshot at preparation**. Execution rechecks identity and current rights, acquires its new cut and creates a fresh bound execution plan for TableQuery's normal vector path. This requires a new owning API: preserve LogicalPrepared's existing basis-equality checks and immutable saved plans rather than bypassing them to reuse a different cut. A stale prepared object requires explicit new preparation; saved uncertain writes always keep their original intent.
2. Extend the owning TableDml/parser contract for typed INSERT values, UPDATE assignments and WHERE operands. Bind into existing typed rows/assignments/predicates, preserving DEFAULT versus explicit NULL, all eager errors, key/constraint validation and operation bounds. Add MySQL positional `?` handling at the shared lexer/AST boundary, excluding strings/comments; never interpolate SQL or substitute with regular expressions.
3. Define nullable bindings explicitly. Nullable DML inputs are required. A NULL comparison binding needs shared three-valued semantics and independent eager-error tests; it must not become `IS NULL`, zero, an omitted predicate or a gateway-only evaluation rule. The existing Atom-only parameter contract does not establish this. Resolve the exact representation and plan compatibility before enabling it.
4. Map PostgreSQL declared/inferred parameter OIDs and MySQL supplied/remembered types to those same descriptors, with exact validation, owned byte lifetimes and stable metadata on empty results. Reject unbound, mixed/sparse, conflicting, oversized or incompatible parameters before dispatch.
5. Follow current-v1 hard cutover rules for any incompatible plan, stored intent, ABI or semantic change: replace the shared definition, migrate generated consumers/fixtures and preserve missing/foreign-definition rejection. Do not assume a cutover is necessary merely to add an internal adapter, and do not hide one if nullable predicate encoding changes.

## Durable writes, recovery and disclosure

The gateway needs **paged durable operation ownership**, not a map that grows with history or a renamed copy of the console's single recovery file. Prefer a provisioned Station/native-state owner above public clients, with explicit quotas, bounded active work, a fenced coordinator and separate control/recovery capacity. W1 must specify the persistence and dispatch boundary, including how recovery records themselves are durably submitted; no recursive unsaved-command gap.

Freeze account/native principal, catalog/resource/object/schema/contract, typed bound request, operation/upload identities and exact signed steps. Persist each step before sending. Record native receipts, processed-input dispositions and attributed terminal outcomes separately. Allocate principal sequences under the same durable coordinator; a replacement may reconcile the saved step, never silently re-sign a conflict or dispatch a different successor. Provider leadership or a socket is not a fence. Preserve the current catalog's publication/upload exclusivity rules instead of inventing a per-connection writer.

Only an observed terminal outcome under current disclosure rights permits CommandComplete/OK and its row count. [PostgreSQL UPDATE tags](https://www.postgresql.org/docs/18/sql-update.html) use the committed matched count; MySQL selects changed or matched counts according to negotiated `CLIENT_FOUND_ROWS`. Canonical stored-byte changes remain the [Table count semantics](https://github.com/rupurt/rey/blob/b775e2b7a50bf46192acadf5e36102beef05057c/contracts/TABLE_DATA_V1.md); no later read reconstructs the outcome. Do not fabricate generated IDs, warnings or transaction status. [MySQL's affected-row contract](https://dev.mysql.com/doc/c-api/8.4/en/mysql-affected-rows.html) defines the flag distinction.

Disconnect/reset/deadline/cancel can release a read but cannot erase an admitted write. Use the original upload/DML/DDL cancellation operation only where its current contract permits, and wait for original terminal evidence. A rejected continuation need not close its accepted upload. Lost authority can suppress disclosure while work remains accepted; never turn denial or timeout into a rollback claim. Restart and drain preserve or transfer recovery ownership under its native fence.

Specify a **signed, account-scoped gateway-control API with a CLI wrapper** for paged operation discovery, status, exact reconciliation and qualified cancellation. This is proposed work; no runnable SQL or CLI syntax is assumed yet. Inspection does not send. Discovery must work when the connection dies before an operation handle reaches the client, preserve current rights and report ambiguity honestly. Do not overload MySQL insert IDs or invent successful SQL results to carry a recovery handle.

Neither ordinary database protocol supplies a reconnect-stable Transit write identity. Identical SQL or a fresh prepared execution is **new work**. Qualify driver settings without transparent write replay. Recovery records retain accepted work without automatic expiry; pressure refuses new admission instead of discarding history. Secrets remain references; bound values in private recovery storage are protected data, not logs or telemetry.

## Protocol, authentication and driver gates

### PostgreSQL first

Implement protocol 3.0 startup/SSLRequest, negotiation, SCRAM-SHA-256, parameters/backend key/ready messages, simple query, and Parse/Bind/Describe/Execute/Close/Flush/Sync. Respect named/unnamed object replacement, text/binary formats, NoData/empty metadata, command tags, errors and secret-bearing cancellation. PostgreSQL 18 also defines protocol 3.2; negotiate/reject deliberately and preserve the selected cancellation framing rather than interpreting a 3.2 packet as 3.0. [Protocol versions](https://www.postgresql.org/docs/18/protocol-overview.html), [message formats](https://www.postgresql.org/docs/18/protocol-message-formats.html).

**Execution-cycle gate:** PostgreSQL Sync ends the implicit transaction; a portal cannot silently retain it across Sync. Proposed initial admission buffers a bounded write cycle through Sync, validates exactly one execution and all fallible cycle commands, then dispatches. Reject a second execution or write-result Flush pattern before any write. Read-only Execute/Flush continuations may consume the **same** suspended portal/cut until completion, Close, error or Sync; Sync closes its implicit-transaction portal. Reject mixing another execution into that cycle. Describe-only preparation must work without a data snapshot. Errors discard until Sync. Pin actual client transcripts to prove this restricted profile without a deadlock or committed prefix; if a required client needs broader behavior, revise the contract before dispatch. [Extended-query lifecycle](https://www.postgresql.org/docs/18/protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY).

A repeated Execute of an already completed write portal cannot apply it again; a new Bind/execution is new work. Cancellation may target only the live session incarnation and active request; stale/foreign keys cannot cancel a later client. Successful cancellation is not evidence that an earlier commit was undone.

### MySQL second

Implement classic HandshakeV10/Protocol 4.1, SSLRequest, `caching_sha2_password`, checked packet lengths/sequences/continuations, COM_QUERY/PING/QUIT/INIT_DB, and PREPARE/EXECUTE/CLOSE/RESET with exact parameter types and binary rows. Handle EOF versus OK only under negotiated capabilities. COM_RESET_CONNECTION clears ephemeral objects/settings without dropping durable writes or bypassing an unresolved principal sequence. Do not advertise multi-statements, compression, LOCAL INFILE, server-side cursor or long-data commands; reject unsupported commands explicitly. [Connection phase](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_connection_phase.html), [prepared commands](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_command_phase_ps.html).

Use current committed matched/changed counts for both client modes. Define truthful status flags and reset settings; autocommit-off rejects. Initially cancel reads by disconnect/deadline and writes through their original recovery controls. KILL QUERY is a separately authorized capability, not implicit permission to cancel another account.

### TLS and credentials

Prefer in-process database TLS termination behind a Zig-owned interface to a pinned, reviewed TLS-server implementation; evaluate the existing Nix-pinned [OpenSSL server API](https://docs.openssl.org/3.0/man3/SSL_accept/) as a concrete candidate in W0. Existing CLI tooling does not prove a usable Zig server binding. Select and pin the actual library/API/license and test both upgrade handshakes before enabling listeners. A protocol-aware edge is an alternative only with its own credential/channel-binding and private-hop proof; a plain TCP proxy is not TLS termination.

Require verified TLS in the qualified client configuration. Define verifier provisioning/rotation, bounded authentication work, password normalization, secure nonces, constant-time checks, secret erasure and failure budgets. PostgreSQL SCRAM-SHA-256-PLUS is advertised only with tested endpoint channel binding. For MySQL, initially use the full `caching_sha2_password` exchange over TLS; fast-auth caching is optional and needs rotation/invalidation tests. Exclude insecure downgrade and unencrypted RSA-password exchange. Native signing keys and Flight bearer hashes are not SQL password verifiers. [PostgreSQL SASL](https://www.postgresql.org/docs/18/sasl-authentication.html), [MySQL authentication](https://dev.mysql.com/doc/refman/8.4/en/caching-sha2-pluggable-authentication.html).

### Pinned client and metadata matrix

Require `psql`/libpq and Psycopg 3; Oracle MySQL `mysql`/libmysqlclient and Connector/Python. Pin exact releases/builds, independent reference-server fixtures, supported settings and both literal/prepared paths in W0. A MariaDB-packaged client is not an implicit substitute. Python drivers require explicit autocommit configuration; their default transaction behavior cannot be accepted as a no-op. [Psycopg transactions](https://www.psycopg.org/psycopg3/docs/basic/transactions.html), [Connector/Python settings](https://dev.mysql.com/doc/connector-python/en/connector-python-connectargs.html).

Capture sanitized startup/preparation/reset/catalog transcripts before freezing the compatibility surface. Qualify the necessary SET/SHOW/version/encoding/database probes and configured Table metadata through bounded typed handlers with truthful values. Do not silently accept unknown settings or emulate arbitrary pg_catalog/information_schema queries. Specify MySQL quoting, escaping, charset/collation and SQL-mode lowering through the shared SQL owner. Wire compatibility, SQL compatibility and GUI/ORM compatibility remain separate claims; even SELECT 1 and client health checks need explicit admission and tests.

## Acceptance and failure evidence

1. **Independent interoperability:** literal and prepared single-Table reads/writes, CREATE then discovery/use, existing literal relational queries, text/binary core types, exact uint64/counts, NULL/default distinctions, empty/no-result metadata, zero/same-value counts, atomic duplicate rejection, catalog conflicts, and new-cut read-after-write. Exercise both MySQL count modes. Do not infer wire-driver support from the existing native-language SDK suite.
2. **Protocol integrity:** malformed lengths and packet fragments, bounded cycles/queues, named-object replacement, stale cancellation keys, prepared type mismatches, fragmented large values and allocation failure. Prove multi-statements, autocommit-off, unsupported cycles and write Flush patterns reject before any mutation. Verify a valid subsequent request after recoverable protocol errors, and close safely after irrecoverable partial framing.
3. **Authority/schema:** TLS trust/hostname/rotation/downgrade failures; invalid and rotated verifiers; cross-account/database denial; read-only write rejection; unauthorized metadata suppression; revocation before execution and after buffering/commit; stale prepared object/schema after ALTER/DROP/name reuse; noncontributing relational dependency denial. A buffered row, cached descriptor or pending result never carries permission.
4. **Durability:** disk-backed Ursula and actual owners; lose native receipts and final socket replies; interrupt gateway/control owner/catalog/worker before and after persisted steps and publication. Reconcile identical saved bytes and identities without a second application; test old/new owner races, missing/foreign definitions, rejected inputs with live uploads, terminal cancellation races, and discovery with no delivered handle. Inspection must not dispatch. Reissued SQL is explicitly new work.
5. **Bounds and liveness:** retained Tables/operation histories exceed caches; slow sockets and suspended reads backpressure acquisition; saturate per-account connection/authentication/prepared/portal/output/principal/upload/storage budgets while preserving recovery/control progress. Maintain separate storage pages, compute vectors, wire frames and publication chunks. Keep native snapshot quotas and the 60-second renewable/five-minute hard lease contract; suspension neither renews forever nor silently opens a new cut.
6. **Regression and measurement:** preserve existing SQL/parameter/general-Table/catalog/relational/vector/console/Flight/SDK checks. Measure handshake, preparation, first row, complete read, write completion, encoding/network work, native/provider requests and resident memory separately. Compare equivalent workloads through native interactive execution; #76 storage cost remains separately attributable. Freeze budgets before tuning and retain failures; do not infer wire latency gains from SIMD microbenchmarks or change vector defaults without evidence.
7. **Delivery:** use pinned Zig 0.17 and Nix; deliberately pin new libraries/clients and follow toolchain checks where changed. Install locked frontend dependencies, run `just check`, affected focused/browser/SDK/deployment proofs and committed-HEAD `just ci-clean`. Record actual revisions and any composed clean runs. Hosted CI's prior billing blocker is not a pass or an excuse to relabel missing gateway proofs; recheck its status for the implementation PR.

The completion target is useful conventional **autocommit read/write access to authorized general Tables through both protocols**, with exact shared semantics and recoverable accepted writes. It does not promise PostgreSQL/MySQL server equivalence or a latency SLO.
