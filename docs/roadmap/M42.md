# M42: PostgreSQL and MySQL wire access

Status: proposed; read/write scope selected, tracked by
[issue #48](https://github.com/rupurt/rey/issues/48). Neither listener is implemented
or qualified. The original investigation checked revision `5c98499e` on
2026-09-30. The baseline now includes merged
[PR #50](https://github.com/rupurt/rey/pull/50) at `2704c153`, and the selected
scope includes writes through both protocols. Upstream references below supply
the protocol requirements, not interoperability evidence. This milestone follows
[M41](M41.md); it consumes selected contracts from [M39](M39.md) and
[M40](M40.md) without treating their planned capabilities as implemented.

## Outcome and recommendation

Offer conventional database clients a finite, autocommit Transit SQL endpoint
through PostgreSQL's frontend/backend protocol and MySQL's classic protocol.
Use two Zig protocol adapters over the shared Fuze compiler, authorized
interactive query client, explicit Table mutation client and catalog client.
Keep SQL evaluation outside the kernel. Start with one explicitly configured
two-column int64 Table for reads/mutations per database mapping and a separately
configured catalog for CREATE TABLE. Require bounded SELECT, INSERT, UPDATE,
DELETE and compatible CREATE TABLE through both protocols, bounded results and
a small, published driver matrix. Implement PostgreSQL first, then MySQL using
the same session and execution boundary. A read-only checkpoint is not completion.

Wire compatibility, SQL dialect compatibility, catalog coverage and application
compatibility are separate claims. Connecting `psql` or `mysql` does not prove
that an ORM, BI tool, migration tool or arbitrary PostgreSQL/MySQL application
works. This proposal includes typed parameters for SELECT and Table mutations;
a literal-only command-line demonstration is an intermediate checkpoint. Writes
retain single-statement atomicity; explicit and multi-statement transactions
remain outside this profile.

## Protocol work

### PostgreSQL

Target upstream protocol 3.0 first. PostgreSQL 18 also defines 3.2 with longer
cancellation secrets; its documented libpq default remains 3.0. Specify
minor-version negotiation or explicit rejection, and reject unknown majors.
Do not claim 3.2 support using 3.0 cancellation framing.
[Protocol versions](https://www.postgresql.org/docs/18/protocol-overview.html)
are upstream identifiers, independent of Transit's v1 policy.

| Area | Required initial behavior |
| --- | --- |
| Startup | Untagged startup packets, bounded lengths/parameters, database/user mapping, SSLRequest, explicit GSS encryption refusal, authentication, ParameterStatus, BackendKeyData and ReadyForQuery |
| Simple query | Query, RowDescription, DataRow, terminal write CommandComplete, empty query, ErrorResponse and Terminate; reject multiple statements before executing a prefix |
| Extended query | Parse/Bind/Describe/Execute/Close/Flush/Sync, named and unnamed statements/portals, typed SELECT/mutations, no-result statement metadata, text/binary values and read PortalSuspended |
| Recovery | Correct implicit-cycle status, cleanup at Sync and on disconnect, and discard-until-Sync after an extended-query error; never emit a success tag for a failed prefix |
| Cancellation | Separate CancelRequest connection; opaque session identifier and random secret, bounded lookup and connection-generation fencing; no native PID exposure |

These are protocol state machines, not just packet codecs. A suspended portal
must retain one source cut and bounded unread output, never rerun at a new cut
on the next Execute. Limit retained portals and pipelines; preserve message
ordering and protocol recovery when refusing capacity. The upstream
[message flow](https://www.postgresql.org/docs/18/protocol-flow.html) and
[message formats](https://www.postgresql.org/docs/18/protocol-message-formats.html)
define the framing and response transitions. Explicit SQL transaction blocks
remain excluded from the selected Transit profile.

Extended-query cycles can imply a transaction across executions before Sync.
W1 must define and qualify a bounded single-statement admission rule for writes:
validate the complete selected cycle before native dispatch, rejecting additional
executions and unsupported Flush/pipeline patterns without committing a prefix.
Do not acknowledge a write and then imply a later protocol error rolled it back.
Preparation alone has no side effects; repeated Execute on a completed write
portal must not apply it again. A new execution with new bindings is new work.
Test this distinction separately from continuing a suspended read portal.

### MySQL

Target the classic protocol with HandshakeV10 and Protocol 4.1 capability
negotiation, initially against pinned MySQL 8.4 clients. This is neither MySQL X
Protocol nor a MariaDB compatibility claim. The
[connection protocol](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_connection_phase.html)
starts with a server greeting, then optionally upgrades via SSLRequest before
the authentication response. Advertise only capabilities actually implemented.

| Area | Required initial behavior |
| --- | --- |
| Framing | Three-byte payload length, packet sequence validation/reset/wrap, length-encoded fields and bounded multi-packet handling |
| Connection | HandshakeV10, HandshakeResponse41, negotiated charset/capabilities, SSLRequest, plugin authentication, OK/ERR |
| Text commands | COM_QUERY for selected reads/writes/DDL, COM_PING, COM_QUIT, scoped COM_INIT_DB; column definitions, text rows, null representation and truthful EOF/OK termination |
| Prepared commands | COM_STMT_PREPARE/EXECUTE/CLOSE/RESET, typed SELECT/mutations, parameter/result metadata, remembered types, binary rows/null bitmap and terminal write OK/ERR |
| Pool reuse | COM_RESET_CONNECTION clears ephemeral statements/settings and read snapshots; durably retain unresolved writes before releasing the session, without granting rights or implying rollback |
| Unsupported flags | Leave compression, LOCAL INFILE, multi-statements/multi-results, query attributes and optional metadata suppression disabled until individually qualified |

Packets can continue at the `2^24 - 1` boundary, including an empty terminal
packet for an exact multiple. The implementation must reject oversized logical
messages before unbounded allocation; it may close the connection when safe
resynchronization exceeds its drain budget. A protocol packet ceiling is not
an authorized query size. See
[packet framing](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_basic_packets.html).

Prepared commands use a distinct
[binary protocol](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_command_phase_ps.html),
with [binary result rows](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_binary_resultset.html),
while [COM_QUERY](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_com_query.html)
uses text results. Initially reject server-cursor flags/COM_STMT_FETCH and
long-data input; an unsupported command with no normal response must close or
fail its owning execution according to a specified rule, never leave a client
waiting indefinitely. Qualify text streaming and ordinary prepared execution
separately. [Connection reset](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_com_reset_connection.html)
must not be implemented as an unconditional OK.

MySQL has no PostgreSQL-style secret-bearing cancellation packet. Its
[KILL QUERY](https://dev.mysql.com/doc/refman/8.4/en/kill.html) is a SQL control
operation targeting a connection. Initially use disconnect/deadline cancellation
and label driver cancellation via KILL unsupported. Adding it needs authenticated,
same-principal ownership checks, non-reused session generations and a separately
admitted control connection; a connection number alone cannot grant permission.

## Shared session and authority contract

Proposed composition: database listener -> authenticated session -> shared
execution adapter, with explicit routes:

- SELECT -> `transit-query.Interactive` -> signed native snapshot reads.
- INSERT/UPDATE/DELETE -> `transit-query.TableMutationClient` -> configured writer.
- CREATE TABLE -> `transit-catalog.Client` -> configured catalog owner.
- Selected metadata -> current-authorized query/catalog inspection clients.

Two real codec packages, provisionally `transit-postgres-wire` and `transit-mysql-wire`,
would own framing/state machines, each with its own manifest and standalone
checks. A `transit-sql-gateway` app would compose them on separate opt-in listeners.
Shared admission/execution logic composes the public query and catalog packages,
with a separate library only when both adapters need that real interface. Do not create empty
package directories as part of this planning increment.

Choose interactive execution for SELECT: each execution gets a fresh nonce and
snapshot, and a disconnect/restart loses its session. Never
resume a partial answer by silently reopening a new cut. Flight's existing
durable profile requires an explicit native sequence that these drivers cannot
supply; generating hidden durable queries would add sequencing, retry and orphan
ownership obligations. Durable jobs remain explicit native/Flight interfaces.

Map authenticated database accounts to provisioned native principals and allowed
database/source, writer and catalog bindings in private configuration. Neither a
startup database name, SQL identifier nor connection attribute may choose an upstream URL, key,
resource or stronger principal. Keep per-account access distinct even behind a
shared listener. Authentication proves an account mapping; current source/native
grants, principal epoch and liveness still gate metadata, execution and each
bounded disclosure, including buffered rows and empty/terminal results.
Read, mutation and catalog policies remain independent. A read-only account or
an absent write route must reject writes before submission; writable accounts
still require the native and application grants for their exact operation.

Acquire the snapshot at execution, not at Prepare. Bind a prepared definition to
the source/schema/contract identity, revalidate it before execution, and reject
stale schemas instead of reinterpreting a cached plan. Parameters enter typed
shared plans; never interpolate values into SQL text. PostgreSQL `$n` and MySQL
`?` need shared parser/binder support under M40, with exact type inference,
null handling and invalid-count/type/format rejection for query predicates,
INSERT values, UPDATE assignments and mutation keys. Prepared writes retain
their exact writer/catalog target and schema identities and recheck current
policy before execution. Parameter binding creates an owned typed request, never
a private copy of the compiler in either codec. Wire preparation is
distinct from enabling SQL `PREPARE`/`EXECUTE` statements.

Autocommit-only means one finite statement per execution. Reject `BEGIN`,
`START TRANSACTION`, autocommit-off, savepoints and unsupported commit/rollback
requests; do not acknowledge them as successful no-ops or advertise transaction
capabilities. Clients needing transactions must select autocommit deliberately
or remain unsupported. Each selected mutation commits through its existing
single-resource owner; a connection or protocol cycle supplies no additional
transaction boundary. Multi-resource atomicity is not selected by this milestone.

### Write profile and completion

Preserve the current [mutation bounds](../../contracts/TABLE_MUTATION_V1.md):
INSERT names both columns and inserts one to three rows atomically; UPDATE changes
only the value at one primary-key equality; DELETE selects one primary key.
Keys are non-null int64 and values initially nullable int64. Parameter support
does not widen these bounds. Duplicate keys reject the whole INSERT; missing-row
UPDATE/DELETE succeeds with zero affected rows. Reject general predicates,
key changes, defaults, upserts, RETURNING, implicit casts and bulk/executemany
rewrites exceeding the supported statement. Do not split a promised atomic batch.

CREATE TABLE uses the current two-column declaration/catalog adapter, restricted
to the selected int64 wire profile. It atomically publishes an empty Table and
definition in an explicitly provisioned catalog resource. It does not install a
query source, mutation policy, worker or native grant. Newly published Tables need
explicit integration before SELECT/DML; the initial database mapping does not
become automatic multi-Table discovery. Publish that boundary beside the driver
examples. Other DDL and SQL administration remain excluded.

A native send receipt means admission; processed input means progress. Neither
is a successful write. Observe original input dispositions and the attributed
terminal mutation status or catalog receipt before emitting PostgreSQL
CommandComplete or MySQL OK. Preserve input rejection, terminal conflict,
cancellation and unknown outcome separately; a rejected staging input can leave
an upload active. Recheck current result-disclosure rights even after commit.
A following SELECT opens a new authorized cut after the write's terminal result;
it cannot reuse an older session snapshot to claim read-after-write visibility.

Use PostgreSQL's operation-specific
[command tags](https://www.postgresql.org/docs/18/protocol-message-formats.html)
and exact durable counts. MySQL's default UPDATE count is changed rows, while
[`CLIENT_FOUND_ROWS`](https://dev.mysql.com/doc/c-api/8.4/en/mysql-affected-rows.html)
selects matched rows. Transit currently counts an existing same-value UPDATE as
one. Qualifying both MySQL modes therefore requires any missing changed-row
evidence in the shared mutation result at its commit boundary, with the owning
v1 cutover and consumer/fixture migration; never infer it from a later read.
Do not fabricate generated IDs, warnings, successful rollback or transaction
flags. Prepared and text execution must report the same outcomes.

### Durable write identity and recovery

The gateway needs a durable, paged operation inventory above the existing clients;
a socket, prepared handle or in-memory queue cannot own accepted work. W1 must
specify its storage, recovery ownership/fencing and authenticated inspection and
reconciliation controls before write dispatch is enabled. It records intent and
evidence, not an alternate authority for whether rows committed.

Assign an operation identity once, freeze the account/native principal, complete
target, schema/contract definition, bound request and mutation reference or
catalog operation/object/Table IDs. Persist each exact signed native step before
submission, then its receipt, processed-input evidence and observed outcome.
Require mandatory nested compatibility fields and canonical restore validation;
missing or foreign definitions reject before sending. Coordinate all native
sequence use for a principal across connections and gateway replicas, including
other configured callers; use bounded admission and fencing instead of automatic
re-signing on a conflict. Respect the writer's one-active-upload resource limit.

After a lost response or restart, reconcile the saved signed step and its input
disposition before preparing a successor under current authority. Never recompile
SQL, mint a replacement identity or assume absence of a reply means no commit.
Reconciliation remains independently runnable after the originating socket dies.
Bound active recovery work and queues; retain accepted records in paged durable
storage with explicit quotas and no automatic expiry or pressure-driven deletion.
Refuse new work before admission if recovery capacity cannot be secured.

Neither database protocol gives ordinary statements a reconnect-stable Transit
retry identity. Reissuing SQL or a fresh prepared execution is new work, even when
the text and values match. Publish this limitation and disable transparent write
retry in the qualified driver settings. Define current-authorized, paged operation
discovery/status and exact reconciliation for clients/operators, including when
the connection fails before a recovery handle reaches the caller. W1 must specify
that control surface and its neutral contract; no custom runnable SQL is assumed
by this proposal. Transport errors and loss of disclosure permission must preserve
unknown outcome instead of claiming rollback or safe retry.

Disconnect, timeout, reset and gateway drain release ephemeral read state but
retain pending writes and their recovery ownership. Mutation cancellation uses
the original request and is successful only when its terminal outcome says so;
it cannot undo applied rows. CREATE TABLE has no cancellation operation after
submission. PostgreSQL CancelRequest and any future MySQL KILL adapter must
respect those differences. Session reuse cannot erase unresolved intent or let
new work bypass an uncertain principal sequence or active writer upload.

### Authentication and TLS gate

Use SCRAM-SHA-256 for PostgreSQL and `caching_sha2_password` for MySQL, over
verified TLS. Define bounded exchanges, salts/nonces, verifier storage and
rotation, constant-time comparisons, failed-login budgets and secret erasure.
Do not use the Flight bearer-token hash as a SCRAM verifier or treat a SQL
password as an Ed25519 signing key. PostgreSQL's
[SASL contract](https://www.postgresql.org/docs/18/sasl-authentication.html)
distinguishes SCRAM-SHA-256 and channel-bound SCRAM-SHA-256-PLUS; advertise PLUS
only when the chosen termination architecture provides the required binding.

MySQL 8.4 defaults to
[caching-SHA2 authentication](https://dev.mysql.com/doc/refman/8.4/en/caching-sha2-pluggable-authentication.html).
Specify and test its full-authentication path and any fast-authentication cache,
including invalidation on credential rotation. A first implementation can always
request full authentication over TLS. Exclude unencrypted RSA-password exchange
and legacy password methods from the initial profile.

The existing gRPC nginx edge cannot simply terminate these database upgrade
handshakes. Decide between a pinned TLS server dependency behind a Zig interface
and an independently qualified protocol-aware TLS edge. A plain TCP proxy can
forward bytes but cannot supply missing server-side TLS. Record where credentials
and channel bindings terminate, private-hop protection, handshake/read/write
deadlines, CA/hostname verification, rotation and downgrade rejection. Direct
PostgreSQL TLS/ALPN is a separate capability; SSLRequest support does not prove it.
This dependency/licensing/ownership decision is an implementation entry gate,
not a claim that a server TLS component is available today.

## Types, dialect and metadata

Select two-column int64 Tables and nullable int64 values first, matching the
smallest existing Flight conversion profile. PostgreSQL uses `int8` metadata and
network-order binary integers; MySQL uses signed `MYSQL_TYPE_LONGLONG` and its
little-endian binary representation. Test decimal text, binary, null, zero,
minimum/maximum values and empty-result metadata independently. Native uint64
counts require checked conversion for this signed initial result profile;
overflow fails rather than wrapping. Checked int64 SUM retains Transit semantics,
not PostgreSQL's widened numeric aggregate. The existing
[type/cell owner](../reference/sql/types.md) remains authoritative.

Reject missing, type-error and conflict cells on ordinary row output; do not
collapse them to SQL NULL or serialize a guessed value. Predicate/aggregate
behavior still follows the shared engine, including its documented state tests.
If an error appears after rows, the result is incomplete and gets an error
terminal, never a success marker. Column metadata must describe the actual output
schema even when there are no rows.

Later mappings need separate qualification: full uint64 to PostgreSQL numeric
and MySQL unsigned BIGINT, finite float64 to float8/DOUBLE, bool to PostgreSQL
bool and a documented MySQL integer convention, UTF-8 to text with explicit
charset/collation rules, and bytes to bytea/binary fields. PostgreSQL text cannot
carry embedded NUL, so text admission must reject that case or select an explicit
binary type. Decimal, temporal and nested values wait for M39's shared semantics;
do not infer monetary scales or timezone behavior in a wire codec.

Transit's parser uses PostgreSQL-like quoting and limited expressions. MySQL
backticks, backslash escaping, session SQL modes and collation expectations need
an explicit dialect contract; a MySQL socket alone does not enable them. Start
with documented Transit SQL plus reviewed dialect lowering to the same AST.
Never strip quotes or rewrite placeholders with regular-expression substitution.

Capture real client startup and introspection transcripts before freezing the
compatibility matrix. Candidates include PostgreSQL `SET`/`SHOW`, encoding and
search-path probes, `pg_catalog`/`information_schema`, and MySQL `SET NAMES`,
`@@` variables, database/version probes and `SHOW` metadata. Define only the
selected forms, with accurate configured read/write capabilities and autocommit
and server settings. Recognize them through a bounded typed compatibility surface shared with the SQL owner;
unknown settings and arbitrary catalog SQL reject explicitly. Do not fabricate
an entire PostgreSQL/MySQL catalog, advertise an upstream server feature version
as parity, or leak names outside the configured authorized scope. Ordinary
`SELECT 1`, GUI browsing and ORM-generated SQL also need explicit proof.

## Bounds, errors and operation

Keep separate quotas for connections, per-principal active queries, authentication
work, statement/parameter bytes, prepared objects, portals, queued messages,
row/column sizes, output buffers, durable pending writes and active reconciliation.
Set numeric defaults and ceilings in the new contract after measuring the chosen
clients. Reuse the current 4096-byte
SQL parser bound and native snapshot ceilings (64 total/eight per principal,
60-second renewable lease/five-minute hard lifetime); proposed listeners do not
raise them. Connections sharing a native principal share that principal's quota.

Stream bounded batches into bounded row encoders. A slow socket must backpressure
source reads, with a write deadline and reserved cancellation/cleanup capacity.
Recheck authority before later buffered disclosure; a portal is not permission.
Close snapshots on completion, error, reset and disconnect, with leases covering
killed gateways and failed releases. Do not buffer the whole result or silently
truncate at a budget. Empty results require the same final authorization gate.

Reuse `SqlDiagnostic` and located parser evidence for syntax, unsupported
constructs, grammar-only families, interface, binding and limit errors. Supply
protocol-specific renderers rather than copying console excerpts or Flight's
gRPC status mapping. Define SQLSTATE and MySQL numeric-error mappings, including
current denial, stale schema, duplicate-key/catalog conflicts, cancellation,
capacity, overflow, unavailable authority and uncertain writes. Convert parser
byte offsets to the selected protocol's coordinate convention. Authentication
and current scope checks precede schema-sensitive diagnostics. Keep unknown
runtime failures on their owning recovery path; the diagnostic presenter neither
dispatches statements nor decides whether work committed. Preserve incomplete
versus complete responses without exposing keys, SQL literals, values or native
internals.
Treat CancelRequest/KILL races as requests to stop, not evidence that an earlier
completion or admitted mutation was rolled back. Telemetry needs bounded operation,
duration, rejection and cleanup counters; omit raw SQL and authentication data.

Provision explicit listen addresses, ports, certificate/verifier references and
native mappings. Keep both listeners disabled until configured. Local/Compose
and Kubernetes network policy, health/readiness, graceful drain, installation
and replacement require their own artifacts and proof. Write readiness includes
durable recovery capacity, sequence ownership and the configured writer/catalog
capabilities. Drain must preserve or transfer reconciliation ownership under a
fence; a new replica cannot concurrently resend as a new operation. A live TCP
accept does not establish current upstream capability or readiness.

## Reuse alternatives and remaining uncertainty

Upstream [pgwire](https://github.com/sunng87/pgwire) provides Rust server APIs;
[opensrv](https://github.com/databendlabs/opensrv) provides a Rust MySQL server
implementation. They are useful design/fixture references, not selected runtime
dependencies under the Zig ownership rule. [pg.zig](https://github.com/karlseguin/pg.zig)
is a client driver, not a replacement server/session implementation. This was
a targeted review, not evidence that no reusable Zig server exists. Any adopted
code needs license review, immutable revision/hash pins and Zig 0.17 validation.

A foreign-language sidecar adds packaging and lifecycle boundaries and still
needs Transit's authentication/query adapter; it is not selected. Tunneling
through Flight inherits durable sequence management and its result limits without
solving the database session contract. Requiring analytical clients to use the
existing Flight/ADBC endpoint remains an available alternative for its documented
profile while these adapters are built.

The largest uncertainties are TLS-server ownership, real driver bootstrap/catalog
coverage, typed parameter semantics, portal scheduling under revocation, durable
gateway recovery and driver-visible write completion. PostgreSQL implicit cycles
and MySQL changed/matched counts are explicit write entry gates.
Framing is bounded work; broad ORM/BI compatibility could dominate the project.
No calendar or throughput estimate is justified before the client/TLS spikes.
The MySQL developer links track `latest`; freeze upstream source revisions and
fixture hashes in W1 instead of treating those moving pages as implementation pins.

## Acceptance and verification plan

1. Pin and run `psql`/libpq plus Psycopg 3 for PostgreSQL, and `mysql`/libmysqlclient
   plus Connector/Python for MySQL, from independently installed artifacts.
   Cover autocommit SELECT and INSERT/UPDATE/DELETE with literals and typed
   parameters, CREATE TABLE through an explicit catalog, binary results,
   empty/null/full-width rows, reset/reuse and explicit unsupported commands.
   Verify durable row counts, same-value UPDATE, zero-row results, atomic
   duplicate-key rejection, catalog name conflicts and read-after-write cuts.
   Qualify both MySQL count modes and PostgreSQL command tags/cycle restrictions.
   Add JDBC, ODBC, GUI or ORM claims only after that exact client's startup and
   catalog workload passes.
2. Independently encode/decode fixtures; fuzz lengths, fragmentation/coalescing,
   byte order, sequence wrap, malformed capabilities, NULL bitmaps, authentication
   transitions, duplicate object names and PostgreSQL error-until-Sync recovery.
   Test no-result prepared metadata, repeated completed write Execute and
   rejection of multi-statements/multi-execution cycles before any write admission.
   Test negative allocation and read/write deadlines, not only valid transcripts.
3. Prove TLS trust/hostname/downgrade rejection, invalid/rotated passwords,
   cross-account database denial, metadata leakage prevention, current revocation
   after a real prefix, stale prepared query/write schemas and foreign/stale
   cancellation. Reject writes with read-only accounts or missing routes before
   dispatch; prove current mutation/catalog policy checks at application and
   current disclosure checks after commit. Cover redacted diagnostics, rejected
   grammar-only/unsupported DDL and a valid next command after protocol recovery.
4. Use disk-backed Ursula with actual native services. Interrupt sockets, gateway,
   worker and authority; revoke/retire sources during pagination; race completion
   and cancellation. Assert no successful terminal after a failed prefix, no
   replacement snapshot, and eventual lease cleanup without a final client packet.
   Lose write receipts and final socket responses, kill the gateway before/after
   each persisted/submitted step, restart writer/catalog owners and fence gateway
   replacement. Prove exact signed recovery with no second application, unchanged
   native identities, no replay on inspection, mandatory compatibility checks and
   account-scoped recovery discovery even without a delivered operation handle.
   Exercise policy changes during staging, rejected inputs with active uploads,
   cancellation before/after application and uncancellable catalog creation.
   Reset/disconnect cannot erase accepted intent; a repeated SQL statement is
   explicitly new work, not a claimed duplicate-safe retry.
5. Grow source and operation-history cardinality beyond resident caches, saturate
   per-principal, listener, storage and writer-upload quotas, hold slow readers,
   suspended portals and unresolved writes, and show recovery/control
   progress. Record RSS and row-encoding/transport cost separately from compile,
   native snapshot and source-read costs; compare the same SQL/basis with native
   interactive execution and Flight where their lifetimes permit comparison.
6. Run existing SQL, console, Table mutation/combined-writer, catalog,
   interactive-query and Flight regressions before extending them. Preserve their
   safety assertions and migrate fixtures only for explicit owning contract
   changes; Flight remains read-only. Add focused codec/client/auth/fault/placement
   tasks only when executable, then run `just check` and committed-HEAD `just ci-clean`. Publish
   actual versions, settings, raw evidence and incomplete/skipped outcomes in
   `tests/README.md`; measure hosted cost before expanding required CI lanes.

Completion means both protocols execute SELECT, bounded INSERT/UPDATE/DELETE and
compatible CREATE TABLE with their pinned clients, durable write recovery,
documented limits, independent failure evidence and runnable deployment examples.
A read-only listener or unprepared literal demonstration does not meet that exit.
Replication/binlog, COPY/LOCAL INFILE, broader DML/DDL, explicit transactions, stored
routines, LISTEN/NOTIFY, continuous queries, arbitrary catalogs and universal
PostgreSQL/MySQL/MariaDB SQL compatibility remain outside this profile. Promote
implemented semantics into public guides/reference and exact contracts with the
implementation; this roadmap record does not expand current support.
