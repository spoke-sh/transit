[issue #31](https://github.com/rupurt/rey/issues/31). This milestone records design
choices and decomposes the work; it implements no new parser, resource kind,
historical catalog or branch operation. The baseline is `5990aa05`. The supporting
research was performed on 2026-09-29 against `113588b6`, a local continuation of
[PR #27](https://github.com/rupurt/rey/pull/27); capabilities on that branch are
not assumed to be on main.

The handbook-first continuation uses the pushed PR #27 commit
[`9051f0a4`](https://github.com/rupurt/rey/commit/9051f0a4209b874ebb4c1ba69aecd50fa7c8225a)
as its implementation baseline. Later local or pushed PR #27 work is not evidence
for that snapshot. The public [grammar surface inventory](../reference/sql/grammar-surface.md)

runtime work package remain open. Issue #31 stays open for implementation and
qualification.

## Outcome and ownership

Express relational, graph, document and captured external-data computations
through a shared typed model with an explicit standards target. Let applications
inspect old schemas and rows together, fork isolated branches, compare dataflow
changes and publish reviewed merges without overwriting intervening work or
repeating external effects.

The [query-engine account](../internals/query-engine.md#standards-and-multiple-data-models)
owns the standards, resource composition and effect/trait reasoning.
[Historical query binding](../internals/query-engine.md#historical-schemas-and-query-binding)
and the [state-model account](../internals/state-model.md#schema-history-and-branches)
own historical schemas, Dolt/Neon comparisons, branching, storage and merge
reasoning. Those accounts include primary sources, alternatives and evidence
limits; this milestone owns delivery scope and acceptance.

This is additional scope after [M37](M37.md) in the linear roadmap. It does not
renumber or absorb existing work:

| Existing owner | Boundary retained here |
| --- | --- |
| [M34](M34.md) and [issue #29](https://github.com/rupurt/rey/issues/29) | Finite Table joins/grouping, source vectors, maintained operator semantics and their independent oracle |
| [M35](M35.md) | Distributed exchanges, runtime placement and authority rebalancing |
| [M36](M36.md) and PR #27 | Inspection/mutation, declarations, exact resource reads, named maintenance, subscriptions and effect bindings |

The standards ledger can inform those ongoing implementations immediately.
Local finite/historical contracts need no new clustered topology. Later work

## Selected profile and deliberate limits

Use selected SQL:2023 Foundation features, SQL/JSON, SQL/PGQ and SQL/MED. Keep GQL
as a future frontend target and Cypher/PGQL as named comparison/import dialects.
The first graph execution profile is finite, read-only and fixed-length. Choose
filesystem capture as the first foreign binding; S3 follows the same contract
only after separate connector qualification. This ordering is a scope decision,
not an assertion that filesystem reads are intrinsically replayable.

Keep KV, Table and Document as the resource kinds. Add logical graph mappings,
snapshot manifests and branch catalog objects above them. Reconsider a native
kind only when an authority, atomicity, lifetime or storage obligation demonstrably
cannot be expressed at the existing boundary. Media/vector values and derived
indexes fit this model but their computation profiles are outside this milestone.

| Target | Reference | Qualification required |
| --- | --- | --- |
| Relational semantics and schema | SQL:2023 [Foundation](https://www.iso.org/standard/76584.html), [Framework](https://www.iso.org/standard/76583.html) and [Schemata](https://www.iso.org/standard/76586.html) | Selected clauses/features, dependency closure, declared deviations and independent type/error fixtures |
| Structured-value projection | SQL/JSON in Foundation | Explicit paths, row identity, missing/null/error/conflict conversion and accepted Document basis |
| Graph mapping and queries | ISO/IEC 9075-16:2023, SQL/PGQ | Element identity, keys/endpoints, multiplicity, fixed patterns and declared source basis |
| Foreign relations | ISO/IEC 9075-9:2023, SQL/MED | Typed binding, complete captured manifest, availability, current permission and exact recovery |
| Historical catalogs/branches | Transit extension informed by Dolt and Neon | Data plus definitions, typed selectors, isolated publication, current authority and reviewed merge |
| Multi-model maintenance | Transit contracts over M34/M36 | Finite-equivalence oracle, complete change coverage, explicit activation and recorded effects |

Public ISO catalogs and vendor examples do not establish normative conformance.
Audit the relevant licensed standard text and corrections before claiming a
feature. SQL Core, full PostgreSQL/GQL, graph mutation, variable-length paths,
arbitrary recursion, event-time windows, general transactions, cross-realm forks
and generic live realm rollback remain outside the selected execution profile.
Branch merge is distinct from SQL `MERGE INTO`.

## Handbook-driven implementation sequence

Use the public inventory as the review baseline for each implementation PR.
The [work-package table](#work-packages-and-dependencies) retains the owners and
prerequisites; this sequence selects reviewable increments within those packages,
without adding or renumbering milestone scope. No phase below treats a proposal
or unexecuted proof as an implemented capability.

### Documentation checkpoint

- [x] Publish implemented execution, offline compilation, checked grammar,
  proposed syntax and undecided syntax in the handbook and site search.
- [x] Cover the checked SQL and application languages plus selected relational,
  standards, graph, foreign-relation and historical/branch targets.
- [x] Reconcile the system-time explanation and grammar comments without changing
  accepted syntax or promising integer-revision SQL execution.
- [ ] Promote the reviewed inventory to S1's typed feature ledger and generated
  capability view. Documentation tables alone do not complete S1.

The pushed baseline executes finite reads and scoped inspection, explicit bounded
Table mutations, and compatible empty Table creation through catalog callers.
KV/Document definitions compile offline; their catalog publication is absent.
Seven idiomatic catalog SDKs are present at that baseline: Python, TypeScript,
Rust, Ruby, C, C++ and Java. Neither the local .NET continuation nor a generic
native ABI establishes additional language coverage. The individual public
statement pages and contracts own exact bounds; this plan does not widen them.

### First implementation PR: feature ledger and capability evidence (S1)

Start with the implemented/checked inventory, not new syntax. Split family rows
into independently testable features, preserving each existing operation's limits.
For example, finite SELECT, configured-source SHOW, declaration compilation and
conditional Table publication must have distinct records.

Define the neutral descriptor in the owning public Zig types, derive its schema
and binding resources, and generate the handbook capability table from validated
records. Keep explanatory prose with the statement reference. Do not create a
second manually maintained status table, copy an ISO grammar, or add a runtime
SQL capability statement before its own contract exists.

| Ledger field group | Required content and rejection rules |
| --- | --- |
| Identity and source | Stable Transit feature key; standard/edition/correction or named dialect/Transit extension; verified clause/feature ID only after audit |
| Audit and licensing | Normative source revision, reviewed corrections, fixture provenance and redistribution rights; unknown or unaudited is explicit, never inferred from a catalog title |
| Semantics and dependencies | Typed owner, input/output/error contract, prerequisite feature keys and deviations; missing dependencies and cycles reject |
| Independent support axes | Reference grammar, production parsing, typed lowering, finite/maintained execution, recovery and per-transport/SDK exposure; compilation is not publication |
| Evidence and scope | Actual positive/negative fixture or task references, result provenance, source revision, limits and unavailable profiles; planned tasks cannot establish a pass |
| Compatibility | Language edition and application schema identity separate from the current Transit definition; incompatible stored/wire/ABI changes trigger a coordinated v1 cutover |

Audit selected SQL:2023 Foundation/SQL/JSON, SQL/PGQ and SQL/MED features and their
corrections against the normative sources. Where text or fixture rights are not
available, retain an unaudited entry and original Transit-authored tests; do not
claim conformance. The existing licensed PostgreSQL corpus stays an oracle for
its declared overlapping syntax/AST subset only.

Exit evidence: regeneration is deterministic; every checked statement and public
inventory family maps to feature records; positive and negative fixtures agree
with the real parser/compiler; deliberate unsupported transport, missing evidence,
foreign definition and dependency inconsistencies reject. Feature status reports
match actual enabled callers and do not promote SQL/PGQ, foreign capture or
historical execution. Integrate ledger validation into real existing checks.

### Second implementation PR: semantic baseline and historical contract (S2/H1)

Define shared operator effects/traits and historical identities before extending
SQL parsing. M34/M36 retain their operator and declaration ownership. Select one
bounded, single-owner namespace for the first coherent catalog/data snapshot;
independently captured resources remain a basis vector until a separate barrier
is proved. Existing Tables are not silently enrolled.

Extend the current declarative catalog's stable object/column identities and
original-receipt semantics. Historical selectors must not introduce a second
catalog authority or reinterpret an already accepted catalog command.

Specify typed snapshot/branch/tag/resource selectors, stable object/column
identity, ancestry, schema/view/graph/decoder commitments, data inclusion,
current metadata versus row authorization, expected-head publication and exact
operation recovery. A branch name resolves once before compilation; accepted
requests retain the resolved identity. Define read/write/capture/dispatch facts,
determinism, failure order, change mode and budgets with transfer rules that
reject unsafe composition. Review the H1 contract with independent transition
fixtures; this does not itself enable branches.

Exit evidence: independent fixtures reject mixed definitions/bases, stale heads,
missing schema dependencies and forbidden effects; explanation does not acquire
snapshots, reveal source rows or dispatch. Generated contract resources and
missing/foreign-definition rejection agree. The public inventory can advance
contract/compilation evidence only, not historical execution.

### Third implementation PR: historical binding and inspection (H2)

After H1 and the necessary M36 catalog/inspection paths are qualified, bind an
explicit immutable snapshot before name resolution. Start with one declared
source and historical metadata/finite reads. Keep namespace enrollment and
publication explicit. S3 supplies richer values where needed; H2 must not pretend
that today's two-column creation profile supports arbitrary schema migration.

Exit fixtures include add/rename/drop/recreate; changed historical views, graph
mappings and decoders as their owners become available; old-column success and
new-column rejection at the old snapshot; explicit projection into a different
schema; metadata-only rights; unavailable history; revocation after a prefix;
and a branch move after admission that cannot change the accepted basis.
Resource revisions, application revisions and snapshot identities must reject
cross-use. No timestamp convenience or arbitrary AS OF integer is added.

## Publication, authority and activation gates

The first coherent namespace has one data owner and a staged catalog/data
manifest published through one mutated resource. Existing Tables are not
automatically enrolled. Independently captured sources form a basis vector;
a coherent multi-owner checkpoint requires a separately proved barrier.
Histories, manifests, conflicts and branch catalogs must be paged.

An ordinary branch publication advances its head conditionally. Merge/migration
staging stays private and resumable; the initial profile has no Git staging index
or shared uncommitted working set. A branch name cannot redirect a frozen request.
Merge planning freezes base/source/target and produces reviewable conflicts.
Publication checks the unchanged target; stale plans require a new review, even
after a lost acknowledgement. Disjoint keys can still violate cross-row constraints.

Borrowed historical reads retain current source permission and lifetime checks.
An explicitly authorized independent export gives the destination separate data
ownership after publication; later source revocation cannot erase that copy.
Source denial/expiry before publication prevents success. Shared physical pages
must preserve those same logical-copy semantics and separate lifetime ownership.
Retained global catalog roots cannot simply be installed under a new writer.

Schema-only branches copy reviewed definitions with empty data and no inherited
row access paths. They record data exclusion so omitted rows cannot become merge
deletions. Schema text can contain sensitive values; this is not anonymization.
Schema-only promotion validates a migration of current target rows.

Forks create fresh resource/writer/replica identities and default to no live jobs,
production bindings or external effects. Export declarations identify application
data separately from framework controls. Opaque KV continuations remain read-only
evidence without a validated application initializer. Current grants, principal
sequences, retirement evidence, mailbox progress, calls and outboxes are not
imported as executable history.

Restore publishes a new application-state successor and preserves the prior
head. It never rolls back native authority or effect-control evidence. Its
activation contract explicitly handles pending inputs/jobs, recomputation,
backfill, subscription reset and sink triggers. Replay consumes recorded outcomes;
missing outcomes cannot cause dispatch. Irreversible domain outcomes require
reconciliation or refusal, not a promise that restoring rows undoes remote work.

## Staying aligned with standards

S1 pins editions, reviewed corrections and licensed fixtures by feature. Review
successor standards when changing that feature, and record mapping/deviation
decisions. The current PostgreSQL corpus remains an oracle only for its stated
syntax/AST subset. Do not import a full ISO grammar without suitable rights.

Frontends lower into shared semantic operators without guessing a dialect from
parser acceptance. Future GQL/Cypher/PGQL support needs independent fixtures and
explicit selection. Change the semantic model when the standard demands it;
do not force incompatible behavior through a superficially similar operator.
Effects/traits are compiler-checked facts, not annotations that grant authority.

Language editions and historical application schemas can coexist as data in the
current descriptor language. Incompatible Transit plans, stored framework
semantics, wire formats or ABIs still follow the
[single-current-v1 hard cutover](../reference/versioning.md). Replace definition
identifiers, regenerate consumers/fixtures and preserve rejection of missing or
foreign definitions. Accepted jobs retain their meaning; matching-build
reconciliation or an explicitly proved conversion replaces silent recompilation,
fallback decoding or data reset.

## Qualification and exit criteria

| Boundary | Required cases and observations |
| --- | --- |
| Standards and semantics | Verified feature dependencies, positive/negative syntax, typed equivalence, error order and visible unsupported transport/profile combinations |
| Historical interpretation | Add/rename/drop/recreate, changed views/graph mappings/decoders, defaults and narrowing failures; exact historical result, explicit projections and metadata denial |
| Graphs and foreign capture | Parallel edges, self-loops, invalid keys/endpoints, mixed bases, file replacement/removal and interrupted capture; finite oracle and exact manifest coverage |
| Branch authority/lifetime | Revocation after a prefix, expiry during fork, source retirement, child/parent deletion and GC races; no copied grants, leaked rows or reclaimed live pages |
| Merge and restore | Delete/update and schema conflicts, uniqueness/references, ambiguous ancestry, stale target, accepted-but-lost reply, schema-only promotion and Document tombstones; independent three-way oracle |
| Maintenance and effects | Backfill/change handoff, paired updates/deletes, replay, unavailable artifacts, old unknown outcomes and activation/reset; finite equality and no historical redispatch |
| Scale and cost | Data, branches and conflicts beyond cache; bounded RSS, copied bytes, fork latency, ancestry-read cost, merge work and reclamation under disk recovery |

Complete all selected work packages, public contracts and shared caller profiles
before marking M38 complete. Copy-on-write must satisfy H3's logical oracle and
record its own measurements; a correct full copy alone does not meet the cheap-fork
target. The desired improvement over peer models is an inspectable closure of
schema, multi-model data, captured computation and effect evidence. No blanket
parity or performance claim follows from this design.

Use `nix develop`, locked dependencies, `just check`, `just test::sql` and relevant
state/publication/query/connector/migration proofs from [tests](../../tests/README.md).
Extend their actual fixtures and disk-backed failure schedules at each new
boundary; do not add placeholder tasks that report success. Run `just ci-clean`
against committed HEAD before pushing. Record executed results separately from
this planned matrix, including skipped or failed checks. Documentation validation
does not prove branch, graph, continuous-query or standards conformance.
