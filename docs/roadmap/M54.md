## Objective

Make useful Table reads and writes independent of tiny application publication
steps, allow independent immutable work to overlap, and give retained storage an
explicit ownership/reclamation lifecycle. Preserve current authorization, exact
uncertain recovery, immutable source bases and the atomic state/input/output
boundary. No graph, writable branch, merge or general SQL transaction feature is
part of this foundation. Those features consume its roots and lifetime contracts.

## Starting evidence

- Native network I/O is concurrent, but the realm engine holds one mutex across
  provider reads, immutable preparation and publication.
- General Table index/row records use native KV. Larger records use 256-byte
  Publication chunks and four-write turns. Complete history causes some small
  mutations to require an extra turn and internal delivery.
- Interactive SELECT uses snapshots rather than durable query jobs. Its public
  Table pull API nevertheless validates current access per returned row.
- Packed authority pages have no physical reclamation or journal rotation.
  Logical Publication cleanup and authority-prefix trimming do not reclaim pages.
- Existing measurements predate integrated authorization and wire gateways. They
  motivate work but are not current-main baselines or promised speedups.

## Implementation sequence and logical commits

The first implementation group isolates request ownership and volatile pins
while the frozen baseline campaigns run. This brings sequence 4's concurrency
boundary forward so subsequent storage work can use independently owned
candidates. All completion gates below remain required for the single PR.

### 1. Freeze measurements and define the publication contract

Build the baseline in an independent checkout and prefix. Use owned disk-backed
fixtures, fixed toolchain/provider versions and independently checked values.
Record uninstrumented time separately from request/byte attribution. Cover narrow,
wide and nested mutations; point, range, full and empty reads; growing retained
history; and concurrent foreground/control work. Include the console and actual
PostgreSQL/MySQL paths rather than treating a native microbenchmark as wire cost.

Specify generic immutable block identities, bounded staging, current read/write
authority, source cuts, byte/operation quotas, durable availability, exact retry,
atomic reference publication, abandonment and reclamation before wiring Tables.
Distinguish application block publication from native metadata mutation limits.
Keep data format/semantics above the generic core and provider APIs in the backend.

Deliverables: attributable baseline records, shared public types/contracts and
independent positive/negative fixtures. Set regression budgets from executed
controls; do not invent a production latency SLO or relax failed ceilings.

### 2. Implement the immutable storage and ownership boundary

Implement bounded block staging/read APIs, verified immutable references and
resource-scoped publication metadata. Candidate bytes may exist before commit;
only accepted roots grant visibility. Missing/corrupt bytes reject before a
successful publication. A lost staging or commit reply must reconcile the same
identity. Own buffers and cache budgets explicitly; retained cardinality must
not determine resident allocations.

Define the durable root set and publication/staging ownership needed by future
resource forks. Physical placement may change without changing logical content.
Separate live data, retained history, staging and reclaimable-byte accounting.
Choose batching/layout from measured alternatives; splitting roots alone is not
an assumed throughput improvement. Reuse existing provider durability rather
than introducing an unqualified second authority.

Deliverables: production backend integration, core/client boundaries, checksums,
bounded batch/failure tests and disk restart/lost-acknowledgement proofs.

### 3. Integrate general Tables and bounded result disclosure

Move general Table immutable row/index publication onto the shared bulk boundary.
Publish the complete row/index/history/head/outcome successor atomically without
turning each small data fragment into a new application continuation. Preserve
old-or-successor visibility, original row/column identity, exact operation counts,
schema changes, duplicate-key rejection and cancellation cleanup.

Share immutable definition/schema reads, prefetch known row records and expose
bounded result batches. Define the batch's current-authorization disclosure point;
revocation after buffering, empty output, cancellation and incomplete results must
retain explicit semantics. Integrate the owning console, gateway and SDK/query
consumers together. Storage block, compute vector and disclosure batch budgets
remain distinct. Do not silently change per-row interfaces into permission caches.

Deliverables: measured read/write reduction, updated caller contracts and actual
CLI/PostgreSQL/MySQL workflows with wide/nested readback and failure schedules.

### 4. Separate immutable work from authority serialization

Give concurrent requests independently owned transport, working buffers and
immutable bases. Isolate mutable snapshot bookkeeping and cache ownership.
Allow independent reads and candidate preparation to overlap provider I/O.
Keep a narrow publication decision with current grants, owner generations,
expected resource versions, principal sequence and receipt identity rechecked.
An intervening publication must conflict safely, without lost accepted work,
unbounded retries, unbounded candidates or an automatic new operation identity.

Bound readers, preparations, waiting requests and background work. Preserve
control admission and measure denial/closure latency under load. Catalogue owner
serialization is a separate ordering domain; this change does not imply automatic
writer sharding or cross-resource transactions.

Deliverables: instrumented overlap evidence, concurrent read/write/revoke tests,
slow-storage isolation, conflicting publication and cancellation/cleanup proofs.

### 5. Implement crash-safe physical maintenance

Maintain explicit roots/pins for live resources, retained history, open reads,
accepted recovery dependencies and active candidates. Reclamation must account
for a writer staging data concurrently with a collection pass. A byte reference
cannot disappear between validation and accepted publication.

Implement bounded, resumable reclamation and the placement/compaction operations
needed to recover physical space. Verify replacement data before retiring old
placement; restart resumes the same maintenance intent. Preserve current roots,
protected old views and exact uncertain outcomes. Default unlimited retention
still retains reachable history; pressure is not permission to expire it.

Deliverables: actual reclaimed storage evidence, parent-independent root lifetime
fixtures, pin/GC/staging races, corruption and storage-pressure failures, and
process/provider restart at each maintenance publication boundary.

### 6. Cut over, measure and qualify the complete foundation

Replace the one current native v1 definition for incompatible wire/storage or
framework changes. Regenerate schemas, signatures, fixtures and bindings, and
remove superseded paths. Foreign/missing definitions must reject before reads or
execution. Existing local installations are not automatically reset or migrated.

Repeat matched baseline controls only after builds finish. Report requests,
bytes, commits, page/block work, allocations, resident memory, physical retention,
latency distributions and recovery/maintenance costs with exact source hashes.
Record failures and unknown outcomes. Attribute benefits separately to batching,
layout and concurrency rather than adding overlapping measurements.

Run root checks, affected storage/resource/authorization/Station/query simulations,
real disk recovery, public client/SDK/Board/Flight and both SQL wire paths. Run
committed-source clean CI before pushing. Record executed and incomplete scopes
accurately. The PR remains open work until the foundation gates below are met.

## Completion gates

### Storage contract selected for the remaining implementation

The following records the selected implementation. The public storage owners
describe its current interfaces; completion evidence remains tracked below.

- Bulk bodies travel alongside a signed request whose bounded descriptors bind
  every key, length and content digest. They are excluded from the authority
  journal record: that record retains the signed logical request and receipt
  digest, while immutable storage owns the bytes. Frozen pending operations own
  their complete body and preserve it through serialization/recovery. A known
  historical receipt can reconcile without restaging data.
  Keep the signed logical request small: the command transport envelope owns an
  optional body, and a frozen `Session.Pending` retains that body separately.
  Ordinary reads must not acquire a large inline response allocation merely
  because block reads exist. Block reads return a separately bounded body plus
  the ordinary signed-query result metadata and its validated source cut.
- A turn has separate byte/record budgets for immutable publications and the
  existing four small metadata mutations. Both use one resource, one expected
  resource revision and one input/progress/output acceptance decision. A bulk
  record cannot become visible merely because its bytes were staged. Table
  rows, index nodes, schemas and immutable predecessors use this path; mutable
  heads and outcomes remain small metadata.
- Each resource owns a separately paged immutable block index. Captured views
  and retained read versions resolve that index at their original catalog cut.
  A resource root is an explicit ownership edge, independent of another
  resource's lifetime; future forks must create their own such edge. Opaque
  inline application bytes never implicitly create storage dependencies.
- Candidate segments group immutable page/block writes under a unique identity
  and a durable storage epoch. A bounded durable FIFO inventory records segment
  identities before creation, so missing create acknowledgements cannot hide
  orphan candidates. Placement and logical content identity remain distinct.
  Segment closure/verification precedes the authority append; a failure cannot
  return a partially accepted root.
  Build each candidate in a bounded private buffer first, assigning only its
  own segment ordinals. Reserve its known encoded byte count in the private
  allocation inventory before creating the segment, then verify every provider
  readback coordinate/frame and close the segment before returning a prepared root.
  This avoids speculative physical writes before the byte quota is known.
  Candidate buffers, durable byte quotas, control reserve and resident read
  caches have distinct limits. The inventory is placement/accounting state,
  never another source of execution authority.
- Beginning collection advances the storage epoch through the authority journal.
  A candidate prepared before that fence cannot subsequently pass its old
  publication CAS. Newly prepared data uses the new epoch. Thus collection can
  select older unmarked segments without racing a successful old candidate.
  Repreparation, when explicitly requested, retains the signed logical identity
  and revalidates all current execution requirements.
- The collector protects retained journal roots, current resource roots, active
  captured views and retained read versions, including each root's block index.
  It must not recursively treat closed view metadata inside historical catalogs
  as a new execution capability. Snapshot expiry and a trusted-time grace period
  protect pre-fence volatile reads on every host; the barrier's own catalog root
  also protects reads opened while that barrier is being observed. Unknown time
  or incomplete root enumeration prevents deletion.
- Marking finishes before deletion begins. The durable maintenance record binds
  its root cut, epoch, inventory cursor and verified mark result. Restart resumes
  that exact work. Concurrent history trimming must either preserve the mark
  input or cause a closed failure before deletion. Inventory identities remain
  discoverable across repeated passes, including late provider completion after
  an earlier absent-object observation.
- Reclamation deletes only segments with no protected page or block. This can
  recover complete orphan candidates and segments whose last root has been
  released. Partially live segments remain retained until verified rewriting
  removes their last ownership edge; the proof must report actual retained and
  reclaimed bytes rather than claim that logical deletion frees all bytes.

Initial crash schedules pass. These choices still require matched segment
overhead measurements, final quota/configuration checks and broader integration. A failed measurement or proof is work remaining,
not a reason to remove its completion gate.

| Gate | Required evidence |
| --- | --- |
| Publication | Complete immutable data is durable before accepted reference publication; loss at every boundary reconciles original identity or remains explicitly uncertain |
| Table efficiency | Matched narrow/wide/nested and scan controls demonstrate end-to-end improvement and less native/provider work; independent readback validates all values |
| Concurrency | Independent immutable work demonstrably overlaps; publication conflicts preserve ordering, grants, fencing and exact receipts |
| Reclamation | Physical space can be reclaimed without losing any live, retained, pinned or recovery-required data, including staging races and restart |
| Bounds | Dataset/history/staging grow beyond cache with bounded request work and memory; quota refusal preserves accepted work and control capacity |
| Cutover | Current-only formats, generated consumers and rejection fixtures agree; incompatible installations fail without mutation |
| Integration | Root/focused checks and committed-source clean CI run with honest evidence; real CLI/SQL consumers exercise the implemented path |

## Downstream work

M38's standards ledger and historical identity specification may proceed as
design inputs. Historical binding and independent-copy branches then use the
qualified resource/root contract. Cheap copy-on-write branches and merge require
their own authorization, ancestry, conflict and ownership evidence. Hash/index
joins, statistics, persistent columnar projections and incremental maintained
queries follow workload evidence and retain their separate semantic contracts.
