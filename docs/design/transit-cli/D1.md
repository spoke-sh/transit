# D1 — Concise errors and useful help

[Review index](README.md) · [Next: D2](D2.md)

Status: **Accepted**. Implementation: concise errors and command help are
implemented and locally qualified in M28. The studies
below record the accepted direction; executed evidence belongs in the proof ledger.

## Question

How can CLI output become easier to read while preserving the information needed
to fix configuration and recover uncertain operations?

## Proposal

Lead with one specific sentence. Add a location or next step only when it helps.
Use command help for the full syntax and option explanations. Keep the existing
commands and explicit configuration selection.

The earlier explain, locate and guide direction remains a useful writing check,
but does not require a printed field for every answer. The
[public CLI reference](../../handbook/reference/cli.md#output-philosophy-explain-locate-guide)
owns the implemented conventions. For example,
`--config is required` already identifies both the problem and its location.

Routine errors should usually occupy one to three content lines. Recovery
failures may need more; the length target must not erase uncertainty or identity.

## Visual studies

These monochrome text wireframes show the exact proposed reading order. Paths,
ports and parser positions are illustrative. `$` represents the user's shell,
not output printed by Transit.

### Figure 1 — Missing configuration

```text
$ transit server
error: --config is required

Usage: transit server --config PATH
```

The required option and minimum usable command answer the immediate question.
Optional flags and the explanation of initialization belong in server help.
`PATH` is a placeholder for an existing configuration file.

### Figure 2 — Errors that explain their own correction

```text
$ transit server --config
error: --config requires a file path

$ transit console --config console.json --format csv
error: --format must be table or json

$ transit server --config one.json --config two.json
error: --config can only be specified once
```

No additional instruction repeats the sentence. Recognized option names and
supported values come from the schema; the CLI does not echo supplied values.

### Figure 3 — Useful configuration context

```text
error: configuration file "server.json" was not found

error: invalid JSON in "server.json":12:5

error: "server.json": ports.gateway and ports.node must be different
```

These are three separate failures. Each carries the location in the sentence.
JSON positions remain parser detection points, using one-based lines and byte
columns; semantic errors name fields without inventing source positions. Specific
schema failures should say what is missing or repeated when that is known.

For a listener conflict, a separate location is useful:

```text
error: cannot bind 127.0.0.1:8080: address already in use
  "server.json": ports.gateway

Check for another running server.
```

Translate a known operating-system cause into ordinary language. Preserve the
distinction between a missing file, denied access and an unreadable file.

### Figure 4 — Command help

```text
$ transit server --help
Run a local Transit server in the foreground.

Usage: transit server --config PATH [--initialize] [--no-ui]

Options:
  --config PATH  Server configuration file (required)
  --initialize   Create a new installation; omit when restarting
  --no-ui        Run without Board for this invocation
  --help         Show this help

Board starts by default with configuration version 3.
Versions 1 and 2 require --no-ui.
Paths in the configuration resolve relative to its file.

Alias: serve
Configuration: apps/transit-cli/docs/server.md
```

Help supplies the complete supported syntax, a short purpose and one explanation
per option. The synopsis uses the canonical command; the alias has its own line.
The configuration reference shown here is the existing repository guide, not a
promise that its relative path exists in an installed bundle.

### Figure 5 — Root help

```text
$ transit --help
Transit

Usage: transit COMMAND [OPTIONS]

Commands:
  server    Run a local server
  console   Open an SQL console
  app       Manage installed applications
  query     Open the single-line Table query shell
  query-v2  Open the single-line KV/Table/Document query shell

Options:
  --help     Show this help
  --version  Show version

Run transit COMMAND --help for command options.
```

Root help helps choose a command. It does not repeat configuration rules for
every command. Bare `transit` keeps showing root help successfully. Bare
`transit server` remains an invocation error because its required input is absent.
Application help should follow the same hierarchy: list operations at `app`,
then show only the selected operation's options at its own help entry point.
Per-operation help is implemented with the same strict argument validation.

### Figure 6 — Recovery needs explicit wording

```text
error: the application operation's outcome is unknown

Retry the saved request with the same configuration and operation ID:
  transit app retry --config PATH --operation ID
```

The output does not call uncertainty a rejection or suggest a new installation
attempt. `PATH` and `ID` stand for the original values, not newly chosen ones.
Recovery guidance remains visible without requesting technical detail.

## Detail and consistency rules

| Situation | Default presentation |
| --- | --- |
| Missing required input | Name it; show the minimum required invocation when useful |
| Bad or repeated known option | Name the option and its constraint |
| Unknown argument | State its argument position without echoing arbitrary input; point to the relevant command help |
| File, schema or listener failure | State the known reason and its useful coordinate |
| Runtime recovery failure | State the outcome, role/location when known, and the safe next action |
| Unexpected implementation failure | Include the error identifier in the initial diagnostic so the report is useful without rerunning |

Remove automatic `at:`, `cause:`, `next:`, `usage:` and `help:` sections. Print
`Usage:` or a help command selectively. Do not print both merely because the
renderer has fields for them. Keep blank lines between the problem and guidance.

Do not reduce an unmapped failure to "the command could not complete". If a
plain-language translation is unavailable, retain its identifier. An exhausted
restart budget must still distinguish the final failure from the role's
underlying failure, even in concise output.

A proposed `--verbose` option could add command/argument coordinates and raw
cause/code identifiers to the same attempt. It is not supported today and is
not necessary to deliver the compact default. Decide its spelling and placement
before implementation. It must retain the same redaction and bounds, and errors
must not instruct users to repeat a mutation merely to obtain more detail.

Preserve stderr for top-level failures, stdout for help/version and existing
machine records, and the existing exit codes. File paths remain escaped and
bounded; verbosity never enables configuration, credential or payload dumps.
Output must remain readable without color, animation or an interactive prompt.

Startup needs a separate presentation decision: the server currently emits JSON
readiness records consumed by clients and proofs. A human readiness summary must
define its stream and selection rules before replacing or supplementing that
interface. "Ready", accepted intent and completed work remain distinct claims.

## Review outcome

The user accepted the compact errors and help direction and requested
implementation. This includes selective locations and guidance, per-operation
application help, untranslated identifiers when useful, and explicit recovery
wording. It selects Figure 1's density without an additional help hint.

No `--verbose` flag or new startup output mode is selected. Existing server
machine records and console result formats retain their contracts.

[D2](D2.md) subsequently reviews command consolidation and conventional
configuration discovery. D1's explicit configuration selection describes its
implemented scope; it does not preclude that later interface change.

## Open questions

- A future review can consider `--verbose` if concise diagnostics leave a concrete
  investigation need unmet.
- Human startup/status output needs its own stream and compatibility design.

## Evidence and limits

The previous formatter unconditionally printed location, cause, next action and
help, plus usage when present. The implementation selects only useful context
from those existing fields. Paths and ports in the studies remain illustrative;
the public CLI reference describes actual behavior.

M24 establishes the command and recovery baseline.
[Diagnostic qualification](../../../tests/README.md#cli-diagnostic-qualification)
records the executable checks. The implementation updates the public CLI
reference and contract's presentation description and verifies real command
output, useful coordinates, redaction, stream separation, exit codes and failure
before effects. Lifecycle/recovery changes require their existing proofs too.
M28 owns implementation and qualification separately
from this design acceptance.
