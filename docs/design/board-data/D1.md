# D1 — Data gravity: entity relationships, column exploration and interactive workbooks

[Review index](README.md) · [Next: D2](D2.md)

Status: **Reviewed**. Implementation: **Proposed UI/UX direction; builds on implemented `catalog_v1` assistance, TLA+-modeled console editor transitions, catalog `previewDdl`/`inspectComputation` metadata and bounded relational queries**.

## Question

When data, derived computations and governing policies are the primary
declarations in Transit—and durable execution (`Station`), write-ahead change
streams (`TransitLog`) and connectors act as the mechanisms that activate that
data—how should Board evolve from a process-first relief map or a single raw SQL
prompt into a first-class data exploration, entity-relationship and collaborative
decision surface?

## Proposal

Reorient Board around **data gravity**. Make **Explore** a unified, three-pane
data studio inspired by the best workflow patterns of
[DuckDB Local UI](https://duckdb.org/2025/03/12/duckdb-ui),
[MotherDuck's Column Explorer](https://motherduck.com/blog/introducing-column-explorer/),
Databricks Unity Catalog Explorer and Snowflake Snowsight, while grounding every
card, edge, profile and editor transition in Transit's own contracts:

1. **Auto-generated Entity Relationship Diagram (ERD) and join synthesis:**
   Project authorized catalog metadata (`CatalogId`, `DefinitionId`, primary
   keys, foreign keys, eligible `INT64` equijoin paths, Document projections, KV
   decoders and maintained `ComputationSpec` dependencies) onto an interactive
   schema canvas. Display each column's logical type ($\tau$) alongside its
   orthogonal physical codec ($\epsilon$: `RLE`, `BITPACK`, `DICT`, `FSST`,
   `ZONED`, `COMP-3`, `EBCDIC`) and collation ($\kappa$: `UTF8_BINARY`,
   `ASCII_CI`, `EBCDIC_CP037`). Selecting a relationship edge inspects key
   compatibility and synthesizes a verified `INNER JOIN` or `LEFT JOIN` into the
   workbook without implicitly executing SQL.
2. **Zero-SQL Dataset Inspector and 5-state Column Explorer:**
   Selecting any Table, Foreign Table, Document, KV resource or Maintained View
   in the left Catalog Navigator or on the ERD canvas opens an immediate
   snapshot preview and per-column statistical breakdown—eliminating repetitive
   `SELECT COUNT(DISTINCT ...)` diagnostic queries. Render all five logical cell
   states—`value`, `null`, `missing`, `type_error` and `conflict`—explicitly in
   both the data grid and the right-hand Column Explorer's proportion bars,
   histograms and collation-ordered `min`/`max` summaries.
3. **Multi-cell SQL Workbook powered by `transit console` ergonomics:**
   Replace the single static text box of [board-console D4](../board-console/D4.md)
   with named, interactive workbook cells that share or pin an explicit snapshot
   basis. Bring the exact interaction model established in
   [`transit console`](../../../apps/transit-cli/docs/console.md) and
   [Query assistance v1](../../../contracts/QUERY_ASSISTANCE_V1.md) into the
   browser: suffix-aware alias and column completion (`catalog_v1`), unambiguous
   keyword continuation, quiet unique-match acceptance, non-destructive `Ctrl+R`
   history search seeded from the current multiline draft, and a clean separation
   between row-returning result sets (`complete_coverage`) and authoritative
   command completion receipts (`matched` / `changed` counts with non-replaying
   recovery).
4. **Data-gravity activation lineage and branch/`previewDdl` impact:**
   Switch the canvas from **Schema ERD** to **Activation & Gravity** to inspect
   how data activates the surrounding system: inbound `Sources` feeding Tables,
   `TransitLog` (`+row`/`-row`) delta streams driving maintained views (`fresh`
   versus `pending` upstream source revisions) and triggering orbital `Station`
   processes (`PID`) and outbound `Sinks`. Pair this with a dedicated
   **Branch & DDL Preview** surface to evaluate non-mutating `Catalog.previewDdl`
   admissibility (`validate_rows` vs. blocking `RESTRICT` dependents) and compare
   scenario branch outcomes (`branch/reallocate-inventory`) against `main`
   before human-approved publication.

This direction builds on the compact shell of [board-console D3](../board-console/D3.md),
the timing/profile insights of [board-console D4](../board-console/D4.md), the
connector evidence model of [board-console D5](../board-console/D5.md), and the
resource landmarks of [board-atlas D5](../board-atlas/D5.md) and
[D7](../board-atlas/D7.md), while inverting their hierarchy so that processes and
connectors are understood *through* the datasets they serve.

- **Cell 2 (Suffix-Aware `catalog_v1` Assistance):** The user is editing
  `SELECT o.order_id, s.|` on line 1 while `FROM orders o INNER JOIN shipments s ON o.order_id = s.order_id;`
  already exists on lines 2–4. Even though the cursor precedes `FROM`,
  `TableAssistance` discovers the suffix aliases (`orders o`, `shipments s`)
  under current catalog inspection rights and offers the exact `INT64` columns

  `s."shipment_id"`), bound to `Authorized basis: orders@v42, shipments@v38`.
  Edits while a metadata refresh is in flight filter the visible list locally
  and discard obsolete generation replies so late network responses never clobber
  the draft.
- **Cell 3 (`Ctrl+R` Draft-Seeded History Search and Command Completion):**
  Pressing `Ctrl+R` seeds the history filter with the current draft
  (`UPDATE inventory SET reserved_qty = 140 WHERE warehouse_id = 12;`). Pressing
  `Esc` or `Ctrl+G` restores the exact saved draft and cursor; pressing `Enter`
  or `Tab` accepts the match as a single undoable edit group. Below the editor,
  a completed write renders an authoritative command completion receipt
  (`Statement completed · Outcome: applied · Matched: 1 · Changed: 1 · Operation #op-9042 · Catalog revision v43`)
  rather than pretending a DML statement is an empty row grid.

## Inverting the hierarchy: why data has gravity

In [board-atlas](../board-atlas/README.md) (`D1–D4`), the primary visual surface
was a continuous process fabric where inbox shoulders and outbox wells showed
actor queue depth, and resources were later introduced ([D5](../board-atlas/D5.md)–[D8](../board-atlas/D8.md))
as architectural landmarks on that map. In [board-console D4](../board-console/D4.md),
**Explore** moved to the opposite extreme: a blank SQL editor where discovering
tables or columns required invoking a search popup or already knowing what to
type.

Transit's architectural separation of the **Control & Policy Plane**, the
**Direct Data Plane** and the **Process & Effect Plane**
([system model](../../handbook/internals/system-model.md#separating-the-control-plane-data-plane-and-process-plane))
explains why a data-first interface is more natural for both developers and
operators:

| Dimension | Process-first view (`board-atlas` baseline) | Worksheet-only view (`board-console D4`) | Data-gravity studio (`board-data D1`) |
| --- | --- | --- | --- |
| Primary landing object | Process `PID`s, inbox shoulders and outbox wells | An empty SQL text buffer | Authorized Catalog Navigator + interactive **Schema ERD** + connected **SQL Workbook** |
| How relationships are discovered | Dashed process-to-resource association lines | Typing `SHOW TABLES` / `DESCRIBE` or opening `⌘K` search | Auto-generated **PK/FK, equijoin and computation dependency graph** with $(\tau, \epsilon, \kappa)$ column pills |
| Zero-SQL data inspection | Hex entry reads on raw state resources | Requires writing and running `SELECT * FROM ...` | One-click **Data Grid** preview and **Column Explorer** with 5-state cell distributions |
| Role of `Station` processes and `Connectors` | Foreground landscape | Separate `Connections`, `Sources`, `Sinks` and `Activity` tables | **Orbital activation lineage** around the datasets they ingest into, maintain or react to |
| Schema evolution & branching | Not represented on the resource skyline | Textual errors after statement submission | Non-mutating **`previewDdl`** impact cards and side-by-side **scenario branch comparison** |

## Entity-relationship generation and orthogonal column semantics

A conventional database ERD only draws boxes of column names, SQL data types and
primary/foreign key lines. In Transit, a column's interpretation and storage
behavior depend on three orthogonal descriptors
([query engine account](../../handbook/internals/query-engine.md#logical-types-and-physical-codecs-and-collation-semantics)):

1. **Logical Type ($\tau$):** The relational type seen by expressions, joins and
   aggregates (`INT64`, `INTEGER`, `VARCHAR(N)`, `DECIMAL`, Document projection).
2. **Physical Codec ($\epsilon$):** How column buffers are encoded inside
   64-byte-aligned `.tseg` segments or foreign datasets (`RLE`, `BITPACK`,
   `DICT`, `FSST`, or mainframe `COMP-3`, `ZONED`, `COMP-4`, `IBM_HFP`, `EBCDIC`).
3. **Collation ($\kappa$):** How string equality, ordering and `.tseg` zone-map
   `min`/`max` bounds are evaluated (`UTF8_BINARY`, `ASCII_CI`, `EBCDIC_CP037`,
   `ICU:<locale>`).

Making $(\tau, \epsilon, \kappa)$ visible on ERD cards and in the Column Explorer
solves concrete user problems:

- **Cross-format join discovery:** A user can see at a glance that
  `inventory.warehouse_id` (`INT64 · DICT`) and `supplier_ledger.warehouse_id`
  (`INT64 · ZONED`) share the same logical type $\tau = \text{INT64}$ and can be
  joined without manual casting, despite different physical encodings.
- **Collation-safe range and join expectations:** Displaying `[FSST · ASCII_CI]`
  on `orders.region` and `[EBCDIC · CP037]` on `supplier_ledger.depot_code`
  explains why sorting and zone-map pruning follow those declared collations
  rather than raw UTF-8 byte order.
- **Interactive SQL synthesis without hidden execution:** Clicking a join edge
  opens the **Join Inspector Card** (Figure 2), which checks whether the join
  fits Transit's executable relational profile and lets the user insert the
  exact `INNER JOIN` / `LEFT JOIN` clause into a workbook cell as an ordinary,
  undoable editor transition.

## Zero-SQL inspection and the 5-state Column Explorer

In DuckDB Local UI and MotherDuck, clicking a table or query result immediately
profiles every column in a side panel so analysts do not have to write manual
`GROUP BY` or `COUNT(*)` queries to understand data shape. Transit extends that
pattern with two strict provenance and correctness rules:

1. **Explicit 5-state cell breakdown (`value`, `null`, `missing`, `type_error`, `conflict`):**
   Every column profile bar and dataset header partitions observed cells across
   all five states. When scanning a foreign copybook table (`supplier_ledger`) or
   a projected Document (`delivery_notes`), conversion errors (`type_error`) and
   concurrent CRDT edits (`conflict`) are counted and filterable in place—never
   silently coerced to `NULL` or zero.
2. **Bound to an explicit snapshot cut and disclosed coverage:**
   Every Dataset Inspector and Column Explorer header names the exact
   `CatalogId`, `DefinitionId`, `Snapshot vN` (or per-resource snapshot vector)
   and whether statistics describe the **complete relation** or the **currently
   loaded page**. Opening or resizing the Column Explorer never silently scans
   unbounded storage or splice-fetches a newer snapshot into an existing grid.

## Sharing the console interaction state machine and statement lifecycle

Rather than inventing a separate browser-only autocomplete or recovery protocol,
the SQL Workbook reuses the exact state dimensions and invariants established for
`transit console`
([service interfaces account](../../handbook/internals/service-interfaces.md#console-interaction-transitions)):

| Console mechanism | Browser SQL Workbook counterpart | Preserved invariant |
| --- | --- | --- |
| `EditorState` interaction dimension (`editing`, `history_search`, `completion`) | Per-cell editor reducer in the browser workbook | Asynchronous completion replies or history previews never overwrite a newer draft generation; `Esc` restores the exact saved draft and cursor |
| `TableAssistance` (`catalog_v1`) | Anchored completion menu with suffix-alias resolution (Figure 4, Cell 2) | Resolves up to two table aliases even when `FROM`/`JOIN` appears after the cursor; discards responses if catalog revision or `policy_epoch` changes |
| Keyword continuation & separator insertion | `Tab` on unambiguous keywords (`CREATE` $\rightarrow$ `CREATE TABLE`) and adjacent tokens | Inserts required whitespace separators as one atomic undo checkpoint without flashing a one-item menu |
| Statement result vs. command completion | Row-returning grid (`complete_coverage`) vs. DML/DDL completion banner (`matched` / `changed`, Figure 4, Cell 3) | Never guesses command kind from SQL text heuristics; uncertain writes reconcile the original operation identity (`#op-9042`) without re-executing SQL |
| Revocation & realm/branch switch | Immediate clearing of protected drafts, undo journals, cached completions, grids and profiles | A retained browser tab cannot disclose rows, column distributions or history after access is revoked |

## Review outcome

The initial request was a data-first design study centered on entity-relationship
exploration and the recent `transit console` usability improvements, drawing on
DuckDB UI, MotherDuck and Databricks. Subsequent feedback retained the major
concepts but found the screenshots cramped and the theme poor. The reviewer
requested larger, higher-fidelity screens and crisp monochrome styling with
subtle color for impact areas. [D2](D2.md) develops that feedback and revisits
the default layout, profiles, relationship semantics and change review. This
does not record acceptance of every D1 interaction or runtime claim.

## Open questions

- Should **Explore** open by default in the split **Schema ERD + SQL Workbook + Column Explorer**
  layout (Figure 1), or open in full-canvas **Schema ERD** (Figure 2) and expand
  the workbook dock when the user selects a table, join edge or cell?
- In **Activation & Gravity** mode (Figure 5), should orbital `Station` processes
  and `Connectors` appear for all visible tables simultaneously, or only for the
  currently selected dataset to keep large catalogs legible?
- Should zero-SQL **Column Explorer** distributions compute over the bounded
  100-row preview cut first with an explicit action to request full-table `.tseg`
  segment statistics, or automatically read pre-aggregated `.tseg` zone-map and
  dictionary metadata when available?
- How should multi-cell workbooks scope their snapshot basis by default: one
  shared investigation cut across all cells in the workbook
  ([collaborative decisions](../../handbook/reference/collaborative-decisions.md#maya-needs-an-answer-she-can-explain)),
  or per-cell latest snapshots with an explicit **Pin workbook cut** toggle?

## Evidence and limits

This review is a UI/UX design proposal and visual study at repository revision
`84afe73b`. It changes no Zig runtime code, SQL grammar, wire contract or
frontend bundle.

- **Synthetic fixture and visual studies:** All six figures (`d1-01` through
  `d1-06`) are generated high-fidelity concept renders governed by
  [`d1-fixture.json`](d1-fixture.json) and [`d1-prompts.json`](d1-prompts.json).
  They are not screenshots of the current embedded `transit-board` binary, and
  their timings (`14 ms`, `9 ms`), row counts (`1,420`, `1,180`, `640`) and
  `.tseg` byte sizes are illustrative fixture inputs, not measured benchmark
  results.
- **Distinction from current implemented behavior:** Current
  [`transit-board`](../../../apps/transit-board/README.md) implements the M2
  read-only inspection routes, the M13/M23 bounded single-source and relational
  query workspaces, and the M23 monochrome application-definition profile
  recorded in [board-grammar D2](../board-grammar/D2.md). Current
  [`transit console`](../../../apps/transit-cli/docs/console.md) implements the
  TLA+-checked `EditorState` reducer, `catalog_v1` assistance and shared SQL
  session recovery in the terminal CLI. Foreign mainframe tables
  ([Milestone 16](../../roadmap/16-multi-model-and-foreign-relations.md)),
  `TransitLog`-driven maintained view scheduling
  ([Milestone 11](../../roadmap/11-sql-and-dataflows.md)), and writable scenario
  branches with reviewed merges
  ([Milestone 17](../../roadmap/17-branches-merges-and-restore.md),
  [Milestone 26](../../roadmap/26-reviewed-data-collaboration.md)) remain
  planned roadmap items.
- **Validation performed for this review:** Repository documentation link and
  code-fence validation (`python3 -B tests/runner/docs.py`) and `git diff --check`
  verify structural integrity across all Markdown and JSON files.
