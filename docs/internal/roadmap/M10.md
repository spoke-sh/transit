# M10 — Verification and scale foundations

[Roadmap](README.md)

Status: Verification foundations and the explicit growing profile are implemented
and qualified within the recorded limits; follows [Station M9](M9.md), before
[idiomatic SDKs M11](M11.md).
The [post-M9 review](../reviews/PRE_M10.md) supplies the initial findings.
The [testing strategy](../TESTING.md) owns test layers, evidence and CI policy;
[State](../STATE.md#collection-size-and-working-memory) owns the corrected
collection model. This plan does not change the running M7–M9 profile. The separate
[v3 development contract](../../../contracts/TRANSIT_V3.md) and
[growing authority implementation](../../../packages/zig/transit-core/docs/growing.md)
have bounded qualification. An explicit node/Zig client development profile is
available, along with an explicit
[growing Station behavior slice](../../../packages/zig/transit-station/docs/growing.md).
Launchers, the default Station interface and foreign behavior bindings still select v2.
The [service guide](../../../apps/transit-node/docs/growing.md) records the explicit
profile: paged control/state catalogs, bounded Station calls/Tables, retained
sources, opt-in verified result delivery and finite control reserves. Runtime
bindings, growing registries/supervision and Station foreign APIs remain unsupported.
Repeated disk/S3 growth has fourteen passing samples; full clean regression,
launchers, reference recovery/isolation and physical capacity passed. Three warm
CI samples and one explicit cold baseline meet the calibrated budgets; the
[recorded results](../../../tests/verification/results/m10-ci-2026-09-25.json)
retain revisions, task timings, cache bytes and excluded failures.

Scope: establish an executable verification strategy and a scale-correct state
foundation before public SDKs stabilize. Reduce repeated CI work while preserving
fault coverage. Replace the coupling between durable collection size and fixed
resident catalogs in a qualified growing-state path. Small test configurations
remain useful; their sizes must not become the application's data model.

An application must be able to retain a growing KV/Table and durable call/result
history without deleting live data to fit a compiled array. Memory, individual
requests, atomic proposals, active work and deployment quotas remain bounded.
Unlimited retention is the default policy, not a promise of infinite hardware.
The [Rey workload model](../workloads/REY.md) adds analytical demand scenarios for
market history/L2/L3, internet context, collaboration, execution and research.
These inform growth, burst, fan-out and recovery tests; they are not achieved
throughput or a commitment to run production-sized loads in ordinary CI.

## Entry gates

| Gate | Required decision / evidence |
| --- | --- |
| Invariant inventory | Map each critical authority, state, retention, connector and host-ownership claim to its owner, abstract model, executable checks and unqualified failure boundaries |
| Scale profile | Specify workload dimensions, hardware, working-memory budgets, storage, contention/skew, throughput/latency objectives and recovery objectives; agree numeric targets before making a massive-scale claim |
| Limit inventory | Classify every bound as operation/encoding safety, resident working set, configurable admission quota or temporary total-cardinality ceiling; include keys, resources, PIDs, principals, associations, views, waits, outputs, effects, results and checkpoints |
| Storage and visibility | Select paged materialization, stable read versions, checkpoint roots/segments and publication rules; identify required format/API changes and preserve one authoritative turn decision |
| Compatibility | Specify recovery of existing histories, explicit upgrade or rejection, schema/ABI capability changes and rollback restrictions; never reinterpret an old checkpoint or cursor silently |
| Verification cost | Record cold/warm CI baselines by setup, build, scenario, cleanup and cache transfer; set separate fast-feedback, full-qualification and aggregate runner-cost budgets |

The current 32-key/four-resource arrays are genuine implementation ceilings,
not tunable cache sizes. Raising those constants, moving the same entire catalog
to the heap, or requiring applications to delete retained records does not pass
this milestone. Inventory narrow identifier/cursor types as well as arrays:
making storage dynamic while leaving an inadequate public address space is not
a complete correction.

## Implementation sequence

1. Establish the invariant/scenario catalog, repeatable timing artifacts and
   scale workload matrix. Separate fast unit tests, build smoke checks,
   standalone-package checks, real integration and deployment qualification.
   Remove duplicate push/PR work, then measure artifact reuse and lane balance.
2. Build a deterministic transition harness with controllable storage outcomes,
   clock samples and scheduling at meaningful boundaries. Add stateful properties,
   minimized regression traces and shared SDK failure scenarios. Keep real disk,
   native scheduling and provider tests for assumptions the harness omits.
3. Specify and implement the growing-state path through protocol/core, backend,
   client and Station. Read and mutate bounded portions; do not collect every
   entry before a handler or copy all data into each active view. Keep query
   computation in callers and validate bounded proposals at authority.
4. Qualify persistence, partial materialization, checkpoint/rebuild, late replies,
   retained results and quota pressure. Keep payload/history retention separate
   from cache eviction; large results need durable references and bounded batches
   with complete-result evidence, not an unbounded response allocation.
5. Add a small TLA+ model for competing ownership, prepare/commit, lost replies,
   revocation and bounded settlement. Connect abstract traces to real Zig
   transitions; document what is modeled and what remains an integration premise.
6. Add focused codec fuzzing, allocation/scheduler fault injection and selected
   security/protocol mutants. Run a small reproducible corpus in the fast path;
   give longer discovery and soak runs explicit budgets and evidence retention.
7. Measure growth, overload and recovery on declared datasets/topologies. Publish
   results and remaining serialization/scaling limits. Apply conservative CI
   dependency selection and qualify it against full runs before relying on it.

## Exit criteria

Implementation evidence belongs in the [test guide](../../../tests/README.md#m10-verification-and-scale-foundations).
Partial checks do not close the growing-state or SDK handoff gates below.

- [x] The testing strategy has executable task ownership, a versioned invariant/
  scenario catalog, replayable failure artifacts and a local path matching each
  hosted qualification tier. Document any required extra environment.
- [x] CI records cold/warm timings and cache cost, avoids duplicate event runs,
  and meets the agreed feedback/cost budgets on representative samples. Fast
  library tests do not compile unrelated applications. Build/package/deployment
  proofs retain explicit owners rather than disappearing during optimization.
  Accepted warm budget: under 15 minutes, 60 aggregate runner minutes and
  12 GiB restored, derived from the 12m37s / 53m27s five-lane run. Under ten
  minutes remains an improvement target, five a stretch. Further optimization
  is deferred. Three complete warm samples took 12m37s–14m35s and 51m53s–58m08s
  of runner time. The cold baseline took 31m09s / 111m51s against separate
  35-minute / 135-runner-minute budgets, with GitHub dependency restores disabled.
  One cold baseline does not establish cold-run variance; Nix substitutes remain
  available. Failed, cancelled and over-budget runs do not qualify.
- [x] Change selection is dependency-aware, defaults to full qualification for
  unknown/shared changes and fails closed on missing/failed required checks.
  Full main/release qualification and periodic reference/capacity runs have a
  documented execution policy; a skipped job is never reported as proof passed.
- [x] Generated schedules exercise competing proposals, stale owners, grants,
  exact retry, unknown outcomes, time uncertainty, view expiry and replay. A
  failing seed minimizes to a trace reproducible without a deployment.
- [x] Shared conformance scenarios distinguish admission, commitment and reply;
  include same-principal multi-handle contention, durable continuation, decode
  failure, local cancellation, in-flight disposal and response allocation after
  commitment. M11 can reuse them through every public SDK.
- [x] A versioned growing-state profile stores and accesses collections beyond
  the legacy 32-key/four-resource ceilings, with data exceeding the configured
  resident cache. Ordinary handlers touch bounded pages/keys rather than load the
  whole resource. Any retained total-cardinality limit is an explicit justified
  deployment quota or separately documented compatibility ceiling, not an array
  length presented as the target programming model.
- [x] The control/catalog audit includes process/principal/association identities
  and retained work, not only Table rows. Required representation changes are
  implemented for the qualified growth profile and exposed in generated contracts;
  legacy-only constraints cannot leak into the new SDK's supposedly scalable API.
- [x] Repeated calls and captured results remain usable with unlimited retention
  while storage is available. Exceeding a memory budget evicts/reloads derived
  pages or backpressures work; it does not delete retained evidence or require
  an application to opt into reclamation just to reuse a fixed working slot.
- [x] State mutation, input progress and outputs still have one authoritative
  visibility decision. Test crash before/after publication, lost acknowledgement,
  stale proposals, missing pages, index lag and orphan staging where applicable.
  Replay performs no application computation or external dispatch.
- [x] Stable paged reads preserve a declared revision with current authorization
  and explicit expiry/gaps. Checkpoint plus retained tail recovers without loading
  every resource/view into memory; after trim, required checkpoint data remains
  durable. Cleanup cannot resurrect an old value, PID, wait or result.
- [x] Quotas and per-operation limits are observable and explicit. Admission
  refuses work before acknowledging unsupported obligations; accepted backlog
  remains durable. Reserved control/maintenance capacity survives overload and
  full-store faults. No automatic eviction, partial transaction or success-shaped
  truncated result is introduced to satisfy a limit.
- [x] TLA+ checks a finite documented model, detects deliberately removed guards,
  and yields traces exercised against the implementation. State safety/liveness
  assumptions and model bounds. A timeout/incomplete exploration is inconclusive;
  passing is not advertised as a formal proof of Zig or the deployed system.
- [x] Fuzz/property failures have saved minimized regressions. Allocation failures
  cannot convert uncertain commitment to rejection; host cleanup joins owned
  native work. Targeted mutants demonstrate tests catch missing critical guards.
  Mutation score alone is not a gate.
- [x] Growth/load tests vary retained data independently of resident budget,
  active work, views, message sizes and hot-key skew. Measure latency distributions,
  throughput, RSS/stack/threads, disk/index amplification, queue age, control
  responsiveness, checkpoint and recovery cost. Verify correctness under load.
- [x] Independent Arrow/result validation and existing disk, single-CPU,
  launcher, reference and physical-capacity obligations still have recorded
  evidence. Compatibility tests cover existing supported histories and explicit
  rejection of unsupported versions. Components document the qualified profile.

## Scope boundaries and SDK handoff

M10 must establish scalable representations and measured single-authority growth;
it does not certify an unspecified production workload or implement every future
cluster topology. The current realm-wide conditional journal remains a known
serialization point until a new authority-partition protocol is specified and
proved. Record that design boundary now; [M32](M32.md) qualifies distributed
execution, contention, placement and recovery across broader topologies.

Cross-resource transactions, SQL, new connectors, arbitrary suspended-stack
recovery and a rewrite of the kernel in Lean are outside this milestone. Lean
remains a candidate for a specific later CRDT or query-rewrite theorem.

[M11](M11.md) starts after the verification harness, growth profile and capability/
compatibility contracts are qualified. Documentation or larger constants alone
cannot close that gate. If discovery requires separately scoped prerequisite
work, insert another numbered milestone before SDKs; do not silently defer a
known structural blocker to the public wrapper implementation.
