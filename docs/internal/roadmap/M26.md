# M26 — User documentation and interface reference

Status: complete within the documented static-site and onboarding profile.
M25 makes a separately compiled application installable;
this milestone makes the implemented interfaces discoverable before
[M30 publication](M30.md). Documentation does not extend a runtime profile.

## Scope and owners

Add a Docusaurus site as `apps/transit-docs`, using strict TypeScript and the
locked workspace dependencies through Vite+. Present getting started, building
applications, querying, public interfaces and operation as user journeys.
Review every foundational topic for status and the boundary between implemented
contracts and future design. Current explanations live in `docs/guides/` and
`docs/reference/`, shared by users, developers and agents. Move planning,
reviews and historical design to `docs/internal/`; they are optional background,
not prerequisites for understanding a public feature.

Keep one authoritative source for each topic. The site renders repository
Markdown and package guides directly; generated OpenAPI/AsyncAPI descriptions
remain derived from owning Zig types. Wire contracts remain in `contracts/`,
component configuration beside its implementation, and proof details in tests.
Provide readable operation/message/schema references and original downloadable
specifications. Preserve repository links and engineering history.

The reference must cover CLI commands and recovery, both SQL capability profiles,
Board OpenAPI, serving OpenAPI, reactive AsyncAPI, native signed protocol,
Flight/Flight SQL/ADBC, language SDKs and installation/bootstrap. Do not advertise
SQL DDL, unqualified Arrow types, public release channels or generic protocol
compatibility as implemented. Explain receipt, completion, uncertainty and
current authorization at the entry point where a user needs them.

## Exit criteria

- [x] A locked Docusaurus package supports local development and static builds,
  portable hosting paths, accessible desktop/mobile navigation and diagrams.
- [x] Task-oriented entry pages and interface references explain all foundational
  topics, preserve source ownership and correct stale implementation status.
- [x] Users, contributors and agents start from the same public concepts, guarantees,
  recovery rules and limits. Internal engineering records retain plans/history;
  public guides/reference cannot depend on them for current semantics.
- [x] Every published source describes a capability snapshot without milestone
  labels or roadmap sequencing. The guard includes imported component guides,
  every wire contract, link targets and generated/downloadable API descriptions.
- [x] OpenAPI/AsyncAPI operation and schema pages and downloads are generated
  from checked authoritative descriptions, without hand-maintained copies.
- [x] Strict types, lint/format, production broken-link checks and browser checks
  cover the actual site; document their evidence and commands.
- [x] Documentation-only CI changes build the site. Existing ordinary checks
  remain intact; new hosted timing is unmeasured until observed.

## Qualification

The initial qualification published 63 pages, including all 31 foundational
Markdown files. The subsequent public-documentation pass replaces those mixed
design/history pages with dedicated guides and references. It keeps internal
records out of the catalog/search and enforces coverage of every public page.
The current catalog has 56 pages, including all 36 public guides/references;
component and exact wire guides retain their owners.
Strict types, source/reference checks, broken-link production builds, desktop/mobile
Chromium checks and the `/handbook/` hosting profile pass. The local quickstart,
separate work-item installation, committed write and ordinary restart were run
from the documented commands. `just check`, `just doctor` and generated description
drift/schema checks pass. [The proof ledger](../../../tests/README.md#m26-documentation-handbook)
records limits; hosted cost, public hosting and a full ordinary clean CI rerun
are not claimed.

## Handoff

M30 must publish documentation and downloadable specifications for the exact
release, with tested installation commands and explicit compatibility labels.
A preview built from a checkout does not imply any public release is available.
M31 must update deployment and recovery guidance with the topology it actually
qualifies; a documentation diagram alone cannot establish distributed authority.
