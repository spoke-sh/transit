# M29 — Unified CLI and conventional configuration

[Roadmap](README.md)

Status: **In progress**. Implements accepted [CLI D2](../design/transit-cli/D2.md)
after [M28](M28.md), before [publication M32](M32.md).

## Scope and owners

The CLI owns conventional server defaults, bounded YAML and environment overlays,
first-existing server discovery, merged console startup preferences, dot commands,
installation-derived console defaults without a generated connection file, YAML
connection/management/declaration inputs, batch SQL and automatic progress through the existing public query operations.
Default executable lookup prepends the physical transit directory to inherited
PATH; explicit executable paths override it. The local bundle places its pinned
dependencies beside transit and does not require a runtime manifest. Query identity,
exact intent persistence, scoped reads and complete result verification remain
with their existing client and recovery contracts.

Public CLI and component guides must describe the implemented configuration,
compatibility, output, limits and recovery behavior. Keep the old query shells
available during migration. Existing server initialization and retained-artifact
checks remain explicit. This work does not add arbitrary topology or SQL support.

## Exit criteria

- [x] Server defaults, selected-file overlays, environment precedence and failure
  without fallback pass bounded configuration and real-command checks.
- [x] Installed bundle starts and restarts without a configuration file.
- [x] Console rc precedence, dot commands, interactive SQL, command/file/stdin
  execution and lossless bounded results pass for Table, KV and Document.
- [x] Lost replies, interruption, saved identity, concurrent managers, current
  authorization and server retained recovery pass their focused proofs.
- [x] Public contracts/guides, design outcome and executed proof ledger agree.
- [x] `just check` and relevant focused proofs pass; pre-push clean qualification
  is reported separately against committed HEAD.

The transcript/interface commit is `d306099`. Follow-up renderer and timing
evidence is in [the proof ledger](../../../tests/README.md#native-table-rendering-and-query-timing).
Debug node execution amplified the measured delay, but consistently ReleaseSafe
empty queries still take 13–20 seconds on the measured machine. Rendering is
below one millisecond. Cache sensitivity and hundreds of native point reads
motivated whole-node profiling: a first empty query at the server defaults
issues 1,120 native requests, misses 31,466 cached pages and stages 1,471 pages
across 51 durable updates. Source-worker time is almost entirely native calls.
Larger-cache, polling, LRU and range-scan controls are recorded in the proof
ledger. Increasing a cache budget alone is not the accepted resolution; repeated
point reads, intermediate path copies and publication turns remain the primary
implementation targets. The renderer and profiling changes make no engine-latency
claim. The aligned `.show` presentation from
[issue #17](https://github.com/rupurt/rey/issues/17) is integrated with the timing
setting and its origin; latency work remains the architectural priority.

## Architecture decision brief — 2026-09-29

This dated decision record is retained as history. The public
[workload priorities](../../reference/workloads.md),
[performance reference](../../reference/performance.md),
[planned query sessions](../../reference/queries.md#interactive-sessions)
and [multilanguage examples](../../guides/workload-examples.md) now own the shared
explanation and direction. Runtime implementation status remains unchanged.

Requested by the user after whole-node profiling. The user requires a fresh query
session for every interactive SELECT and cancellation of an active query when
the console exits. This lifecycle is accepted direction, not implemented behavior.
The storage changes below remain proposals.
Current behavior belongs in [queries](../../reference/queries.md),
[state](../../reference/state.md), [Tables](../../reference/tables.md),
[Documents](../../reference/documents.md) and [storage](../../reference/storage.md).
The [executed measurements](../../../tests/README.md#native-query-latency-whole-node-attribution)
and local profiling manifest identify the experiments and their limits.

**Required interactive behavior:** each SELECT opens a fresh query session and
source snapshot; console exit cancels its active query. Interactive execution does
not resume a previous query after reconnect. Query identity is scoped to this
session, not a new durable process or principal for every statement.

**Recommendation:** implement that lifecycle through authorized snapshot reads,
while retaining one authority for accepted data and current permissions.
Improve the shared storage and publication path as well: the latter affects
writes, durable jobs and Documents even if interactive reads avoid query jobs.
Keep Fuze Zig native and outside kernel authority. A query-engine replacement
is not supported by the current empty-query evidence.

Accepted application data remains durable. Interactive plan upload, execution
progress and completed answers no longer need exact recovery after console loss.
Existing callers that explicitly depend on captured durable jobs keep their
separate contract; console SELECT must not inherit that workflow implicitly.

| Evidence | Observation | Decision implication |
| --- | --- | --- |
| Same uninstrumented ReleaseSafe binaries, fresh empty Table | 14.01 s at eight cache pages; 5.69 s at 64, both at 100 ms worker/courier intervals | Cache tuning helps immediately; seconds remain after it |
| Whole-node profile at server defaults | 12.96 s, 1,120 native requests: 1,069 reads and 51 durable updates | Most calls are reads; they repeatedly reconstruct and check small pieces of state |
| Storage work in that profile | 31,466 page misses, 22,815 hits, 1,471 staged pages, 1,836,481 attempted page payload bytes | The empty result incurs substantial read and write amplification |
| Node handler attribution | 8.63 s handling read requests; 3.94 s handling updates, each including its own checks and I/O | Both read acquisition and durable update granularity need attention |
| Page I/O within those handlers | 9.16 s; this overlaps the preceding read/update totals | The provider interface and amount of work dominate this case |
| Source-worker spans | 8.756 s total step time, 8.701 s in native requests | About 55 ms remains for local work; this is not an isolated Fuze CPU benchmark |
| Controls | LRU: 12.50 s; bounded catalog scans: 11.99 s; 200 ms polling: 15.67 s | These changes alone did not resolve the observed latency |

These are local diagnostic samples, not p95/p99 or sustainable throughput
measurements. The developer's existing Debug server remained running. That Debug
build amplifies the user's 86.9-second trace; the optimized measurements establish
that there is also an architectural cost. Detailed current latency attribution is
for the empty Table case. KV and Document share the query and publication machinery,
but their workload latencies have not been measured by this experiment.

**Why a read causes 51 updates.** The complete measured decomposition is four
console upload sends, 17 durable view opens, 17 worker turns and 13 deliveries.
The requester uses four turns for begin/part/seal/submit and one for completion;
the source uses 12 turns for capture and publication. Each continuation repeats
source/request policy and state reads. The
[capture implementation](../../../packages/zig/transit-query/src/UnifiedCapture.zig)
recomputes the current source page and candidate Arrow segment while its chunks
are being staged, then advances the captured progress only when the segment is
published. This supports restart without relying on worker memory.

The [publication contract](../../../contracts/STATION_PUBLICATION_V1.md)
retains 256-byte values and four mutations per turn. Capture stages at most two
256-byte result chunks per turn; the final manifest has its own begin, chunk and
publish steps. Empty Arrow output still has a schema. These choices explain
many turns but are not a lower bound required by durability in general.

Every accepted update also maintains protocol metadata, receipts, resource/view
state and sometimes mailbox/outbox indexes. The
[catalog](../../../packages/zig/transit-core/src/catalog.zig) applies successive
key updates through copy-on-write tree paths. The current tree has four entries
per leaf and five children per branch. The
[packed backend](../../../packages/zig/transit-backend-ursula/src/PackedPageStore.zig)
issues one provider request for each page miss or staged page. Thus the 51
updates produce about 28.8 page appends each on average; this ratio is measured,
not a format guarantee. A bigger cache does not reduce the 1,471 page appends.
At unchanged per-query amplification, 1,000 such queries would attempt about
1.84 GB of page payload alone. That is arithmetic from one sample, not a measured
1,000-query workload or a forecast of retained disk usage.

**What already exists.** Growing KV uses immutable ordered catalog roots and
retained read versions. Tables encode typed rows over that index. Documents add
an immutable ordered index, accepted revision roots and checkpoints that preserve
causal/deletion evidence. The authority opens its latest published root and reads
pages on demand; it does not reconstruct every query by replaying all history.
There are snapshots and indexes, but they are accessed through repeated small
native reads and, for Documents, another publication/index layer. More frequent
checkpoints do not remove query uploads, result staging or those access costs.
Arrow output alone does not provide columnar persistent storage, predicate
pushdown or reusable materialized query results.

The useful database precedent is separation of concerns. SQLite readers keep a
fixed committed view, and its WAL index locates pages; checkpointing is a distinct
storage operation ([SQLite WAL](https://www.sqlite.org/wal.html)). DuckDB uses
row groups for storage, compression and parallel work
([DuckDB storage](https://duckdb.org/docs/current/internals/storage)). Its
[checkpoint operation](https://duckdb.org/docs/current/sql/statements/checkpoint)
synchronizes WAL contents with the database file. RocksDB also distinguishes
[read snapshots](https://github.com/facebook/rocksdb/wiki/Snapshot), which do not
survive a database restart, from persisted data. These are architectural references,
not proposed runtime dependencies or performance comparisons with this distributed
query lifecycle.

**Proposed choices, in priority order:**

1. Add a shared authorized snapshot-read profile, with the console using a fresh
   session for every SELECT. A session fixes one explicit source basis and owns
   its plan, bounded buffers, cursor and snapshot pin. Completion releases it;
   exit cancels an active session and releases its resources. Normal exit sends
   an idempotent cancellation and obtains acknowledgement within a defined bound.
   A broken connection or killed console needs a server-enforced lease/deadline
   so cleanup does not depend on a final client packet. Define the completion/
   cancellation race, control capacity and maximum cancellation latency. A failed
   or canceled stream is incomplete; the next SELECT starts a new session and
   snapshot. Preserve live authorization and complete-result framing. Shared
   verified immutable caches may outlive sessions, but query progress and grants
   may not. Some bounded snapshot/pin accounting may remain durable; remove durable
   progress and result writes per small fragment. Keep the existing durable job
   profile for callers explicitly requiring exact recovery. This needs a new
   neutral contract before changing the existing console/recovery implementation.
2. Reduce storage and native-read amplification for both profiles. Batch bounded
   reads under the same required current-policy checks; share verified immutable
   bytes without caching authorization. Stage a bounded candidate's changed tree
   paths together, preserving the single final publication boundary. Benchmark
   a deployment-sized cache independently. Page layout/fanout changes require
   explicit version compatibility, not a constant change that reinterprets old
   pages. Do not assume faster polling improves completion.
3. Add a generic bulk immutable-data publication contract for large histories,
   results and index nodes. Persist finite blocks through the backend, then
   atomically commit their verified references and source progress. Define bounds,
   quotas, ownership, availability, orphan handling and recovery first. Reads stay
   behind authorized public interfaces; Fuze and application code receive no raw
   provider access. This avoids expressing every data block as a long sequence of
   tiny application-level KV mutations while retaining durable acceptance.
4. Build workload-specific read structures on accepted versions: KV point/range
   indexes and hot-state caches; Table primary-key access plus columnar blocks and
   pruning statistics for scans; Document path/sequence indexes and separately
   versioned search/analytical projections. Every materialization needs an exact
   source watermark, lag/freshness semantics and rebuild/recovery behavior.
   Required checkpoints can become authoritative recovery evidence after trimming;
   they cannot all be treated as disposable caches.

The required interactive lifecycle changes query execution recovery. Storage work
benefits all operations while retaining current contracts where possible. Bulk
publication and new physical formats have wider compatibility/failure scope.
Authority partitioning remains necessary to qualify horizontal write scale, but
replicating the current per-query work does not address its amplification.

The [Rey workload model](../workloads/REY.md) contains application intentions and
synthetic demand scenarios, not achieved rates. Its earlier closed-page-stream
description has been corrected to the current packed backend; the public storage
reference owns today's mapping.

| Workload | Read/write structures to prioritize | Separate success criterion |
| --- | --- | --- |
| Console, Board and agent inspection | Authorized snapshot reads, bounded Arrow batches, efficient point/range acquisition | Time to first batch and complete result, concurrency, current revocation |
| Shared context and enrichment | Accepted Document roots, indexed paths/sequences, versioned projections | Edit acceptance, read latency, conflict fidelity, recovery and projection lag |
| Market capture, books and features | Bulk ordered capture, incremental per-partition materialization, hot keyed state | Capture gaps, sustainable/burst rates, freshness and catch-up under continuing input |
| Historical research and optimization | Partitioned columnar blocks, pruning, reusable features, recorded dataset/plan/model versions | Bytes scanned, scan throughput, concurrency and reproducibility |
| Trading execution | Small bounded turns/effects, explicit ordering domains and isolated CPU/I/O/control budgets | Market-event-to-order-send tails including durable pre-dispatch authorization |

The recorded market-capture scenarios span 100,000 to 10,000,000 events/s; the
execution intention is millisecond-class with exact percentiles and conditions
still undecided. Empty-SELECT timings do not measure either workload. Research,
backfill and crawling need independent budgets so they cannot exhaust execution
or control capacity. General joins, sorting and continuous SQL also remain
unsupported; faster finite scans alone do not supply those semantics.

**Evidence required before selecting a design:** prototype snapshot reading and
batched publication separately, using the same optimized binaries/hardware and
same source semantics as the baseline. Compare KV point/range reads, Table
selective/full scans and Document path/list/text reads. Include empty and populated
sources, retained data beyond cache, aged query history, concurrent writes, cold
and warm starts, and independently offered load. Report time to first batch,
completion p50/p95/p99, throughput, native calls, durable decisions, provider
requests, bytes staged/retained, node/provider memory, source lag and catch-up.
Verify revocation after a prefix, expiry, concurrent source changes, uncertain
commits, host loss and exact durable-job recovery. A fast prototype that skips
these boundaries does not qualify the proposed profile.

The interactive lifecycle is decided: fresh session per SELECT, cancellation on
exit. Remaining decisions are the first broader workload to optimize, its measured
latency/throughput/freshness objectives, and the scope of storage-format work.
Recommended first implementation slice: the required interactive session lifecycle
plus shared bounded read acquisition; retain explicit durable jobs and develop
efficient bulk publication as the shared storage foundation. No new millisecond
latency promise or external database dependency is selected by this brief.
