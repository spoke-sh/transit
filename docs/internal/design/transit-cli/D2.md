# D2 — One query console and conventional configuration

[Review index](README.md) · [Previous: D1](D1.md)

Status: **Accepted** for the interface direction recorded below. Implementation:
the new commands, defaults, discovery and overrides are not implemented.
The existing console still requires explicit query identities and progress
commands; it does not support `-c`, `-f`, dot commands or startup-file discovery.

## Question

How should Transit offer one comfortable SQL interface for terminal use and
scripts, with familiar configuration defaults?

## Proposal

Make `transit console` the query interface. Follow DuckDB's command, script and
stdin workflows, ordinary result tables, and dot commands. A submitted SELECT
should produce its result without a manual `/new`, `/status` and `/next` sequence.
Keep [D1's](D1.md) concise errors and command help.

Use `transit.yaml` for the server's declared local topology and `.transitrc` for
console preferences and selection of an existing caller connection. Configuration
file discovery becomes an intentional part of the CLI contract. The server
starts from complete built-in defaults and overlays one project, home or system
file if present. The console merges system, home and project preferences.
Server properties accept `TRANSIT_` environment overrides, with `__` separating
nested field names.

The existing commands reflect implementation history:

| Command today | Purpose | Proposed place |
| --- | --- | --- |
| `query FILE` | Original single-line Table v1 shell | Compatibility entry point during migration |
| `query-v2 FILE` | Single-line unified KV/Table/Document shell | Compatibility entry point during migration |
| `console` | Multiline unified v2 shell, editing, completion, TLS and optional saved recovery | Sole advertised SQL interface, with interactive and batch execution |

`console` already shares the v2 session implementation with `query-v2`. The v1
shell uses a different query protocol and configuration; neither old command can
simply be renamed to `console` while promising identical behavior.

## Visual studies

These monochrome terminal wireframes describe proposed behavior. `$` is the
user's shell prompt. Example rows are synthetic; SQL still requires an existing
authorized source. Examples are not commands supported by the current binary.

### Figure 1 — One interface, three input modes

```sh
transit console
transit console -c 'SELECT * FROM items'
transit console -f report.sql
transit console < report.sql
transit console --format json -c 'SELECT * FROM items'
```

Interactive mode supports multiline SQL. `-c` executes one SQL statement, waits
for its result and exits; a trailing semicolon is optional. `-f` and redirected
stdin run statements sequentially and stop at the first failure. Scripts use
semicolon termination and may finish with one complete unterminated statement
at EOF. Incomplete strings, comments or syntax fail without submitting that
statement. Earlier successful statements remain completed.

Use one `-c` or one `-f` per invocation; reject combinations and repetitions.
Neither mode subsequently reads stdin. Explicit options apply to the invocation
regardless of their position. This deliberately keeps a smaller argument model
than DuckDB's ordered sequence of commands and format changes.

### Figure 2 — SQL produces a readable answer

```text
$ transit console
Transit
Type .help for help.

transit> SELECT id, value FROM items LIMIT 2;
+----+-------+
| id | value |
+----+-------+
|  1 |    10 |
|  2 |    20 |
+----+-------+
2 rows

transit> .tables
items
transit> .quit
```

The normal interaction is SQL followed by rows. Identity selection, upload
progress, waiting and verified page reads belong in the console's execution
flow. `.info` exposes the last query identity, source basis and completion
evidence; recovery operations remain available when needed.

Use bounded page formatting and escape terminal control characters. Do not
collect the entire result to determine column widths or silently truncate rows.
Keep missing, null, conflict and type-error cells visibly distinct. The simple
integer cells above do not define representations for every supported type.

### Figure 3 — A small set of familiar console commands

```text
.help
.tables
.schema
.mode table
.mode json
.connect local-transit/console.json
.show
.info
.quit
```

Dot commands occupy their own line and need no semicolon. `.tables` and `.schema`
describe the configured authorized source; they do not imply a new global
catalog or arbitrary SQL DDL support. `.show` explains effective settings and
which file selected them without printing credentials or saved query contents.
`.connect` selects a provisioned caller configuration, including its workspace
and credential references. A URL alone does not establish that connection.

Retain slash spellings during migration. Group advanced status, resume, retry,
cancel and result-lifecycle commands in detailed help. Their public operations
and authorization remain the same; changing punctuation does not create a new
control API. Switching connections must preserve and explicitly resolve or
detach from any saved outstanding operation, never overwrite its recovery state.

### Figure 4 — Conventional server configuration

```sh
transit server
transit server --config development.yaml
transit server --initialize
```

Start from complete defaults. Select the first existing file in this order and
overlay its explicitly supplied properties onto those defaults:

1. `./transit.yaml`
2. `~/transit.yaml`
3. `/etc/transit/transit.yaml`

Load only the selected file. A project file inherits defaults, not missing
properties from the home or system file. If none exists, use the defaults;
no configuration file is required. `--config PATH` bypasses discovery and loads
exactly that file over the defaults. An explicitly selected missing file is an
error. An existing unreadable, malformed or invalid file fails without trying a
lower-priority file. Do not search parent directories. If the home directory is
unavailable, skip its candidate.

Initialization remains explicit: `transit server --initialize` creates the
default installation without a configuration file; subsequent `transit server`
invocations recover it. Defaults never turn missing or rolled-back storage into
a new installation.

Recommended concrete defaults reuse the local server's supported settings:

| Setting | Default |
| --- | --- |
| Configuration profile | Version 3, local Table source |
| Installation directory | `.transit` under the invocation's current directory |
| Realm | `1`, with private installation identity and generated keys |
| Listener addresses | `127.0.0.1` |
| Gateway | Port `19105` |
| Board | Enabled, port `19107`; `--no-ui` disables it for the invocation |
| Application manager | Enabled, port `19106`, at most 8 applications and 32 roles |
| Provider and node ports | Cold `19101`, cold console `19102`, store `19103`, node `19104` |
| Admission and control budgets | 65,536 journal positions plus 4,096 control positions |
| Executables | Matching artifacts from the installed local bundle |

Executable discovery must make these defaults usable from the installed bundle,
including its pinned Ursula and MinIO dependencies. The current bundle provides
an executable manifest but the CLI does not discover it; packaging and runtime
lookup need qualification together. A missing dependency produces a concise
error; startup does not download tools or silently select another installation.

Customization can be a small partial file, such as:

```yaml
ports:
  gateway: 10000
board:
  port: 10001
```

All other properties retain their defaults. Merge object properties recursively;
an explicitly supplied list replaces the default list. Apply defaults for the
selected schema version, so an older explicit configuration does not inherit
unsupported fields from version 3. Existing version and installation checks
still apply.

The file owns installation location, supported service roles, ports, provider
and executable references, resource limits and Board settings. YAML lowers to
the same strict, versioned server model;
unknown fields, duplicate keys and unsupported topology fail before startup.
Keep explicit JSON configurations working through migration. Relative paths
from the file use its directory; built-in `.transit` keeps its current-directory
basis even when a discovered file overrides only ports. Relative environment
paths use the selected file's directory, or the current directory when no file
was selected.

Apply environment overrides before final typed validation. `--config` changes
file selection, not environment precedence. Where a CLI option overrides a
configuration property, the precedence is:

```text
explicit CLI option > environment variable > selected file > built-in default
```

Lifecycle switches such as `--initialize` remain explicit operations, not
configuration properties that can be enabled through this convention. Normalize
the effective configuration before hashing it for retained installation checks;
equivalent settings have the same identity regardless of their source.

The current server owns a fixed local service neighborhood with an initial
Table source. A YAML filename does not add arbitrary worker graphs, remote
placement, connectors or alternate source definitions. Those need their owning
runtime/application contracts. Editing the file also does not bypass retained
installation identity checks or imply a live topology upgrade.

### Figure 5 — Merged console preferences and connection selection

Load all existing rc files in this order, with later files overriding individual
settings:

1. `/etc/transit/transitrc`
2. `~/.transitrc`
3. `./.transitrc`

The system file uses the non-hidden filename `transitrc` inside `/etc/transit`;
home and project files use `.transitrc`. Missing files are skipped. If the home
directory is unavailable, skip its file. Do not search ancestor directories.

Proposed personal `~/.transitrc`:

```text
.mode table
```

Proposed project `./.transitrc`, alongside `transit.yaml`:

```text
.connect local-transit/console.json
```

`local-transit/console.json` illustrates the caller file generated by a server
whose installation directory is `local-transit`. The project file references it;
it does not duplicate the server's topology or embed a private key.

With these two files, the effective settings select `table` output and the
project's caller connection. Merge by setting: an absent setting inherits its
earlier value, while a later assignment replaces that setting. `.connect`
replaces the whole connection reference; never combine credentials or workspace
fields from separate caller configurations. Resolve each relative path against
the rc file that supplied it, even if another file changes a different setting.

`--init FILE` replaces all three automatic rc files; `--no-rc` disables them.
These options are mutually exclusive. An unreadable or malformed file in the
selected chain is an error, even if a later file could override its setting.
An explicitly selected missing file is also an error.

For connection selection, explicit `--config FILE` wins over
`TRANSIT_CONSOLE_CONFIG`, then rc `.connect`. Within rc files, project settings
win over personal settings, which win over system settings. Connection-file
defaults are overridden by rc settings, then explicit flags such as `--format`.
Validate the complete selection before connecting. All input modes use the same
rules.

Limit automatically loaded rc files to settings and connection selection.
Loading them must not submit SQL, retry saved operations or invoke a shell.
Explicit scripts use `-f` or stdin. DuckDB also permits SQL in its startup file;
the proposed Transit file intentionally configures the client only.

### Figure 6 — Environment variables map to server properties

Use the `TRANSIT_` prefix and uppercase field names. A single underscore remains
part of a field name; a double underscore steps into a nested object.

| Variable | Configuration property |
| --- | --- |
| `TRANSIT_HOST` | `host` |
| `TRANSIT_PORT` | `port` |
| `TRANSIT_FOO__BAR` | `foo.bar` |
| `TRANSIT_PORTS__GATEWAY` | `ports.gateway` |
| `TRANSIT_BOARD__PUBLIC_ORIGIN` | `board.public_origin` |
| `TRANSIT_ADMISSION_CEILING` | `admission_ceiling` |

The first three rows preserve the user's illustrative schema; they do not add
`host`, `port` or `foo` to the current server schema. For the current nested
port model, proposed usage is:

```sh
TRANSIT_PORTS__GATEWAY=10000 transit server
```

The file and built-in defaults provide the remaining properties. Decode values
according to the declared property type: strings stay strings, integers must
fit their declared range, and booleans accept `true` or `false`. Empty values
are supplied values, not a request to fall back; the property's validation
decides whether an empty string is allowed.

Lists and whole objects use JSON values. Objects overlay supplied fields
recursively; lists replace the entire list. More specific nested variables
override fields of a whole-object variable, independently of enumeration order:

```sh
TRANSIT_PORTS='{"gateway":10000,"node":10001}' \
TRANSIT_PORTS__GATEWAY=10002 \
transit server
```

Here `ports.gateway` becomes `10002`, `ports.node` becomes `10001`, and other
ports keep their file/default values. Validate port conflicts and other semantic
constraints after overrides. Reject malformed structures, duplicate object keys
and paths outside the declared schema. Array-index overrides and arbitrary YAML
fragments in environment values are outside this convention. Optional non-string
properties may use JSON `null` where the schema permits it; string values such
as `null` remain literal strings.

Keep override recognition scoped to the server schema. Known variables owned by
other commands, such as `TRANSIT_CONSOLE_CONFIG`, are not server properties.
Other unrecognized `TRANSIT_` names should produce a concise unknown-setting
error so a misspelled override does not silently use a default. Existing launcher
environment names retain their meaning in their owning commands. Use canonical
uppercase override names without case-insensitive aliases.

Use the process environment directly; automatic `.env` loading and shell
interpolation in YAML are outside this selection. Overrides cannot add
undeclared capabilities or bypass credential-reference rules. Errors name the
variable and property without echoing the supplied value:

```text
error: TRANSIT_PORTS__GATEWAY must be a port from 1024 through 65535
  overrides ports.gateway
```

Keep each property's source for diagnostics, including whether the value came
from a built-in default, file, environment variable or command option.

## Execution and compatibility

Normal SQL submission must allocate a fresh identity and retain the exact intent
before a possible acceptance. It then advances that same query, waits within a
declared deadline, verifies complete result coverage and reads bounded pages
under current permission. Automatic progress is authorized by the user's SQL
submission; simply opening the console does not resume saved work.

Do not report success for an admission receipt or a timed-out wait. A batch
invocation exits zero only after the complete result has been written. Errors
go to stderr; batch stdout contains result output, without prompts, banners or
upload receipts. Interrupted waits preserve the existing exit-130 distinction.
An interrupted connection never implies server-side cancellation. On uncertainty,
retain the original query and provide a concrete resume action; do not create a
fresh query as a retry. Do not interleave independently signed sessions that
share a caller identity.

Prefer the existing lossless JSON page representation initially: automatic
execution emits verified result pages while retaining exact integers, cell
states and source evidence. A row-object JSON format or CSV needs its own scalar
and multi-result rules; this review does not silently redefine existing JSON.
Human table presentation can become simpler independently.

Remove `query` and `query-v2` from the primary command list when the new console
is qualified. Keep their original behavior available as documented compatibility
commands initially. Migrate examples and integration callers before deleting
either entry point. Do not alias old configuration files to a different profile
or inject migration messages into machine stdout.

## Review outcome

The user accepted the single console interface, DuckDB-inspired dot commands
and flags, batch behavior, automatic query progress, configuration split and
compatibility direction. This includes `-c`, `-f`, `--format`, `--init`,
`--no-rc` and the existing explicit `--config` override.

The user then selected server discovery in project, home, system order and
explicitly chose the first existing file rather than merging server files.
Server environment overrides use the requested `TRANSIT_` prefix with `__` for
nested fields. The console instead merges the recommended system, home and
project rc hierarchy. Finally, the user requested complete server defaults so a
configuration file is optional and customization overlays only supplied values.
These decisions replace this review's earlier required cwd-only server file and
two-file console lookup. The earlier explicit initialization choice remains.

Implementation remains outstanding. The concrete defaults, decoding rules and
diagnostics above describe how to realize the accepted interface direction.

## Open questions

- Before implementation, specify persistent identity allocation, recovery-file
  selection/retention and total wait deadlines for automatic execution. The
  current optional recovery file and caller-supplied namespaces do not provide
  these defaults. Preserve explicit consent for retaining private query text.

## Evidence and limits

[DuckDB arguments](https://duckdb.org/docs/current/clients/cli/arguments) document
`-c`, `-f`, alternative startup files and ordered argument processing.
Its [CLI overview](https://duckdb.org/docs/current/clients/cli/overview) documents
`~/.duckdbrc`; [dot commands](https://duckdb.org/docs/current/clients/cli/dot_commands)
cover settings, schema inspection and exit. Project rc overrides are a Transit
choice, not an attributed DuckDB behavior. This borrows interaction
conventions, not DuckDB's engine, SQL feature set or embedded database lifecycle.

[Pydantic Settings](https://pydantic.dev/docs/validation/latest/concepts/pydantic_settings/#parsing-environment-variable-values)
provides the reference convention for an environment prefix, nested delimiters,
typed values and JSON structures, with nested overrides taking precedence over
whole-object JSON. File selection, rc merging, strict variable naming and error
rules are Transit choices. Borrowing the convention adds no Python dependency.

Current implementation evidence is the [CLI reference](../../../reference/cli.md),
[console guide](../../../../apps/transit-cli/docs/console.md),
[server guide](../../../../apps/transit-cli/docs/server.md) and
[CLI v1 contract](../../../../contracts/TRANSIT_CLI_V1.md). The contract currently
excludes discovery, requires explicit query identities and supports the old
shells. Implementation must revise its compatibility boundary and public owners
together with the behavior, rather than treating this review as a new contract.

[M24](../../roadmap/M24.md) owns the implemented lifecycle and console baseline;
[M28](../../roadmap/M28.md) owns concise diagnostics. This additional scope needs
a separate implementation milestone under the roadmap's
[sequencing rule](../../roadmap/README.md#maintaining-the-sequence).
No new runtime behavior or executed runtime proof is claimed here. Qualification
must cover real batch/TTY commands, startup and restart from packaged defaults
without a config file, partial-file overlays, first-existing server selection
and failure without fallback, rc merging and per-file relative paths,
environment precedence and diagnostics, bounded YAML/environment decoding and
equivalent effective configuration identity, all three query sources, loss of
replies, interruption, concurrent managers and retained server recovery.
